## 设备、恢复与符号表

- API 35 arm64 模拟器 Debug：分别触发主线程和命名后台线程致命异常。后台事件保存 40 条其他线程，其中两个线程同名、一个处于 BLOCKED，主线程存在；存在无帧线程。主线程事件的系统 TID 与进程 PID 一致。日志及内存分区成功，FD 观测 154 个、保存 128 个并标记部分采集；具体可用内容取决于 Android 版本、权限和进程现场。
- 停止隔离服务模拟断网，在 API 35 触发后台 Crash；应用新进程保留原事件、进程及线程身份，恢复服务后成功补传。以完全相同事件再次请求得到 `duplicate=1`、`accepted=0`，ClickHouse 逻辑事件数为 1。
- API 35 实际进程中断：观察到崩溃线程核心落盘日志后立即终止该隔离测试进程，短暂看到 `capturing` 中的事件文件，新进程恢复计数为 1。ClickHouse 只接收一次，保存的进程 PID 和线程 TID 与原进程的 FATAL 日志一致，原异常和 5 个主栈帧可查看，未完成分区标记 `skipped/interrupted`。另注入复制的合成核心记录验证原 `processId`、PID、Java 线程 ID 和 TID 均不变；这两项实验的证据范围不同。
- API 29 arm64 模拟器 Release：上传与 APK 同次构建的 mapping 前主栈等待处理；上传后主栈成功还原，34 条辅助线程中 25 条成功还原、9 条无帧而不适用，成功结果均引用同一实际 mapping。删除并重新上传相同 mapping 后，已发布主栈、辅助栈、非堆栈上下文及来源摘要保持不变。
- `CrashFaultPipelineTest` 将 logcat 单行超限、权限失败和超时一起注入真实采集组合，经过异常处理器委托、核心冻结、离线重试和 duplicate 确认，核对脱敏、原身份与队列删除；另一用例用受控 OOM 验证保留主异常、跳过昂贵采集和委托。单侧落库/确认恢复另由内存和隔离 ClickHouse 测试注入。尚未在同一设备运行中同时注入这些故障，也未执行真实磁盘满或系统断电实验。

## 采集开销观察

本组为两个模拟器、每种各一次受控后台 Crash，包含其他 SDK 工作线程，两个采集不是独立性能基准。`wait_ms` 是处理线程等待辅助结果的时间；`capture_ms` 从协调器入口到冻结后，不包含之后的上传和原异常处理器。Java 堆差值是进程采集前后 `totalMemory - freeMemory` 的差，受 GC 和其他线程活动影响，可为负数，既不是分配量也不是峰值。

| 环境 | 保存的其他线程 | 等待 | 采集至冻结 | Java 堆差值 |
|---|---:|---:|---:|---:|
| API 35 Debug | 40 | 149 ms | 165 ms | +1,870,512 B |
| API 29 Release | 34 | 70 ms | 97 ms | -4,325,472 B |

处理器最多等待辅助采集 1500 ms，但 JVM 抓栈、内核与磁盘操作不能由此获得硬实时上限。示例 App 的 minSdk 为 23，Crash Library 的 minSdk 为 21；本机最低可用模拟器为 API 29，尚无 API 21 独立消费者或 API 23 设备验证，也未测真机功耗、内存峰值或生产线程规模。
