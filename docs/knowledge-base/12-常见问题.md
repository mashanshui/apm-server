# 常见问题

## 为什么不用 PostgreSQL 存所有数据？

可以用于原型或小规模验证，但 APM 原始事件增长快，并需要大量时间范围、多维和分位数聚合。方案因此使用 PostgreSQL 管事务数据、ClickHouse 管分析数据。

## 为什么第一版不用 Kafka？

第一版可以在 ClickHouse 成功写入后再响应 Android，失败则依赖客户端本地队列重试。这样组件最少，也最容易排查丢数。需要削峰、回放、多消费者或数据库故障期间持续接收时再加 Kafka。

## 为什么选择 Spring MVC，而不是 WebFlux？

目标架构中的 JPA、JDBC 和常用 ClickHouse 客户端主要是阻塞式，Spring MVC 与它们更匹配，调试和学习成本也更低。当前 Crash 实现使用 JDK `HttpClient`，同样是阻塞式调用；除非未来明确采用全链路响应式技术，否则 WebFlux 的收益有限。

## 为什么不能用 JPA 操作 ClickHouse？

APM 查询会大量使用分位数、物化视图、聚合状态和 ClickHouse 专有函数。显式 SQL 更可控，JPA 更适合 PostgreSQL 中的用户、应用和权限关系模型。

当前仓库已加入 JPA、Flyway 和 PostgreSQL 驱动，并使用 PostgreSQL 保存用户、应用、成员和 Session；这不意味着 ClickHouse 事件数据也迁移到 PostgreSQL。

## Grafana 与 Vue 为什么同时保留？

Grafana 适合内部趋势、筛选、临时分析和告警；Vue 负责登录、应用/符号表/查询 Token 管理、Crash、卡顿和内存排障。两者不是替代关系，详细范围和产品化待办见[前端知识库](../../frontend/docs/knowledge-base/README.md)。

前端不会直接连接 ClickHouse，只访问 Spring Boot 管理/查询 API；网页已使用 Session、CSRF 和应用成员授权，应用范围校验与错误处理仍集中在服务端。

## 为什么卡顿要同时返回精确耗时和估算耗时？

主线程消息的起止耗时由客户端直接测量，是卡顿事实；堆栈采样只能覆盖部分时间片，调用树耗时是基于采样间隔推导的估算。服务端会保留采样空洞和质量计数，不能把估算字段解释成精确方法耗时或 CPU 自耗时。

## FPS 和挂起率为什么要分算法版本？

不同算法的分母、刷新率归一化或挂起阈值可能不同，直接混合会改变统计含义。服务端按 `algorithmVersion` 拆组；挂起率还会先按应用、匿名设备、UTC 日期和稳定维度合并，缺少有效前台分母时返回 `denominator_insufficient`。

## 为什么采样时间使用相对单调时钟？

采样偏移只用于当前消息内部排序和覆盖计算，不依赖设备墙上时间，也不能跨设备比较。事件发生时间仍使用公共事件信封的墙上时间做查询分区；两种时间语义不能混用。

## 为什么卡顿指纹由服务端生成？

服务端可以统一规范化路径并版本化算法，忽略行号、地址、动态数字和采样次数，避免同一根因被不必要拆组；客户端提供的指纹只作为普通输入或调试信息，不决定正式 Issue 身份。

## App Key 是客户端秘密吗？

不是。APK 可以被逆向，App Key 主要用于应用识别和防止跨应用误配置。当前 Key 永久有效且不可轮换，安全还需要 HTTPS、请求限制、异常检测和可选的 Play Integrity；不要把它当作用户密码或 APK 真实性证明。

## `appId`、应用包名和 `X-App-Key` 有什么区别？

`appId` 是服务端生成的 UUID，用于网页路径和数据隔离；`packageName` 是创建应用时绑定的 Android application ID；`X-App-Key` 携带系统随机生成的永久 App Key。上传请求头必须使用设置页显示的 Key，不能使用页面中的 `appId`。JSON v2 事件和 manifest v3 使用 `packageName`，且必须等于 Key 绑定的包名。

## 重试会产生重复数据吗？

会。方案采用至少一次语义，每条事件带 `eventId`。当前内存仓库和 ClickHouse 适配器都按应用与 `eventId` 做有限去重，批次响应会返回 `duplicate`；ClickHouse 查询使用 `FINAL`。这仍不是跨系统全局事务，原始表与明细表之间的部分写入恢复需要单独验证。

## 为什么不能采集完整 URL、请求头和请求体？

这些内容可能包含令牌、个人信息和业务敏感数据。应采集标准化路径和必要性能字段，并用白名单、哈希和服务端脱敏限制风险。

## Grafana 如何保证多租户隔离？

不能仅隐藏 `app_id` 变量。对外多租户场景需要数据源隔离、ClickHouse 行级策略或由后端查询代理强制授权。

当前 Grafana Dashboard 仍直接查询 ClickHouse 原始表，Vue 的 Crash 与卡顿查询已由 Spring Boot Session + 成员关系授权；生产对外多租户仍需要 Grafana 数据源/行级隔离、同源网关和完整运维验收。

## 当前仓库使用哪个 Java 版本？

当前 Gradle 工具链统一配置为 Java 21；开发、CI 和部署环境应使用 Java 21。历史性能记录中的 JDK 17 仅代表当时的验证环境，不代表当前构建基线。

## 什么时候需要 Kubernetes？

当多个服务需要独立扩缩容、频繁滚动发布、复杂服务发现和流量治理，而且团队具备相应运维能力时再评估。第一版使用 Docker Compose。

当前 `compose.yaml` 单独提供本地 PostgreSQL；`compose.cloud.yaml` 提供 PostgreSQL、ClickHouse、Spring Boot、Nginx/Vue 和 MCP 五容器，`compose.local.yaml` 把本机端口限制在回环地址。当前 HTTP 编排不包含生产 HTTPS、备份恢复和容量保障。
