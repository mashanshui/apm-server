# 常见问题

## 为什么不用 PostgreSQL 存所有数据？

可以用于原型或小规模验证，但 APM 原始事件增长快，并需要大量时间范围、多维和分位数聚合。方案因此使用 PostgreSQL 管事务数据、ClickHouse 管分析数据。

## 为什么第一版不用 Kafka？

第一版可以在 ClickHouse 成功写入后再响应 Android，失败则依赖客户端本地队列重试。这样组件最少，也最容易排查丢数。需要削峰、回放、多消费者或数据库故障期间持续接收时再加 Kafka。

## 为什么选择 Spring MVC，而不是 WebFlux？

目标架构中的 JPA、JDBC 和常用 ClickHouse 客户端主要是阻塞式，Spring MVC 与它们更匹配，调试和学习成本也更低。当前 Crash 实现使用 JDK `HttpClient`，同样是阻塞式调用；除非未来明确采用全链路响应式技术，否则 WebFlux 的收益有限。

## 为什么不能用 JPA 操作 ClickHouse？

APM 查询会大量使用分位数、物化视图、聚合状态和 ClickHouse 专有函数。显式 SQL 更可控，JPA 更适合 PostgreSQL 中的用户、项目和权限关系模型。

当前仓库甚至尚未加入 JPA 或 PostgreSQL 依赖；这条结论是目标架构取舍，不表示当前已经有 PostgreSQL 管理模块。

## 为什么第一版不用 Vue？

Grafana 可以快速提供趋势、筛选、下钻和告警，先验证指标价值。项目管理、事件详情、问题归组和多租户产品体验成熟后，再用 Vue 实现。

## 项目上报 Key 是客户端秘密吗？

不是。APK 可以被逆向，Key 主要用于项目识别、配额和限流。安全还需要 HTTPS、轮换、请求限制、异常检测和可选的 Play Integrity。

## 重试会产生重复数据吗？

会。方案采用至少一次语义，每条事件带 `eventId`。当前内存仓库和 ClickHouse 适配器都按项目与 `eventId` 做有限去重，批次响应会返回 `duplicate`；ClickHouse 查询使用 `FINAL`。这仍不是跨系统全局事务，原始表与明细表之间的部分写入恢复需要单独验证。

## 为什么不能采集完整 URL、请求头和请求体？

这些内容可能包含令牌、个人信息和业务敏感数据。应采集标准化路径和必要性能字段，并用白名单、哈希和服务端脱敏限制风险。

## Grafana 如何保证多租户隔离？

不能仅隐藏 `project_id` 变量。对外多租户场景需要数据源隔离、ClickHouse 行级策略或由后端查询代理强制授权。

当前 Dashboard 直接查询 ClickHouse 原始表，且查询 API 使用开发期请求头；因此当前实现只适合受控本地/内网验收，不能作为对外多租户安全边界。

## 当前项目到底使用 Java 17 还是 Java 21？

当前 Gradle 工具链配置为 Java 17，原技术方案推荐 Java 21。两者尚未统一，应在正式开发前形成 ADR，并同步本地、CI 和部署环境。

## 什么时候需要 Kubernetes？

当多个服务需要独立扩缩容、频繁滚动发布、复杂服务发现和流量治理，而且团队具备相应运维能力时再评估。第一版使用 Docker Compose。

当前仓库还没有 Docker Compose 文件，第一版的 Compose 仍是部署目标而非已提交的运行资产。
