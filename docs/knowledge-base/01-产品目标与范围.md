# 产品目标与范围

本页描述产品目标和范围演进；仓库当前能力与验证层级统一见[当前实现与验证边界](00-当前实现与验证边界.md)。

## 背景

Android 端已经具备性能数据采集能力，平台下一步需要补齐数据上传、服务端处理、存储、聚合分析、Dashboard 展示和告警。当前团队更熟悉 Java/Kotlin，因此第一版强调低学习成本和端到端可验证。

## 建设目标

平台需要做到：

1. 弱网环境下可靠上传 Android 性能事件。
2. 在服务端完成应用识别、协议校验、脱敏、标准化和存储。
3. 支持按时间、版本、渠道、设备、系统、页面和接口等维度查询。
4. 提供 p50、p90、p95、p99 等分位数。
5. 识别版本退化、慢设备、慢页面和慢接口。
6. 对异常指标进行告警。
7. 为后续多租户和产品化演进保留边界。

## 原始方案的第一版目标范围

以下启动、网络和完整 ANR 能力是原方案目标。当前 `app_start` 用于 Crash 会话分母，不代表已实现启动耗时分析；网络和完整 ANR 采集/查询页面仍未落地。

### App 启动

- 冷启动、温启动、热启动。
- 总耗时以及 Application、Activity、首帧等阶段耗时。
- 版本、设备和 Android 系统分布。

### 网络性能

- 总耗时，以及 DNS、连接、TLS、TTFB、下载耗时。
- 请求方法、状态码、错误类型和请求/响应字节数。
- 标准化后的域名和接口路径。

### 卡顿或 ANR

- 卡顿次数、卡顿率、帧耗时分布。
- 页面、堆栈、受影响设备数。
- App 版本和 Android 系统版本分布。

原始方案将内存、CPU、耗电和完整 Trace 放在第一条闭环之后；当前已通过独立变更增加 PSS、VSS、Java 堆采样分析和 SDK 内存异常报告的问题/趋势/引用链。CPU、耗电和完整 Trace 仍不在当前范围，NDK/native Crash、非致命异常和 ANR 仍不在当前 Crash 首期范围。

## 目标 Dashboard 需要回答的问题

- 某版本冷启动的 p50、p90、p95、p99 是多少？
- 新版本相对旧版本是否退化？
- 哪些设备、系统、渠道、页面或接口最慢？
- 哪些接口错误率最高？
- 慢样本发生时的设备、会话、网络和阶段耗时是什么？
- 问题影响了多少用户或设备？
- 最近是否出现异常突增或数据中断？

## 当前最小可用闭环

```text
网页登录 → 创建应用（唯一 packageName）→ 获取永久 App Key
→ JSON/gzip 指标批次、卡顿 ZIP 或内存异常 multipart 报告 → 校验与脱敏 → ClickHouse
→ Vue 查询总览/趋势/问题 → 查看 Crash 详情、卡顿采样证据或 SDK 引用链
```

管理员还可创建只读查询 Token，经 Agent HTTP 或 MCP 查询当前应用。Grafana 资源保留为内部分析入口；阈值告警和 Android 生产级持久队列仍是目标能力。

## 原始第一版范围控制

- 微服务拆分。
- Kubernetes 编排。
- Kafka 消息总线。
- Redis 基础设施。
- 自研 Vue Dashboard（原始计划；当前 Crash、卡顿和内存 PC 控制台已经落地）。

这一列表记录原方案的首期取舍，不代表当前仓库仍停留在该阶段。范围演进和扩展触发条件见[实施路线图](09-实施路线图.md)。

## 当前已落地子范围

当前已把 Java/Kotlin JVM 致命 Crash、服务端卡顿监控、PSS/VSS/Java 堆指标和 SDK 内存异常报告纳入可运行闭环；异常报告提供 multipart 接收、问题/趋势和引用链展示，可选 HPROF 只保存、不解析。既有事件查询链路为：客户端使用 `app_start` 去重会话作为 Crash 分母，服务端提供 Crash 查询、卡顿个例总览/趋势/Issue/详情、FPS/设备日挂起率/白名单多维查询，以及内存 summary/trend。当前服务端已接受 `app_start`、JVM fatal Crash、卡顿个例、场景帧汇总、前台挂起汇总和 `memory_sample`；NDK/native、非致命异常、完整 ANR 采集、Issue 生命周期和完整产品管理能力仍未落地。

当前仓库已经实现 Spring Boot 接收 API、JSON/JSON+gzip 指标批次、事件校验、脱敏、服务端指纹、部分接受、`appId + eventId` 去重、内存仓库和 ClickHouse HTTP 适配器；公共 JSON 使用 v2 `packageName`，卡顿个例入口只接受 v3 manifest 边界，并统一要求 UUID v4 `processId`。卡顿解析可按认证应用和 `buildId` 使用网页上传注册的 ProGuard/R8 mapping；processor `1.0.2` 已用客户端实际设备 ZIP 完成本机 UUID v4 主线程-only 解析及云端首次写入、重复和详情验收。服务端不保存原始 ZIP，也不向客户端返回完整解析报告。默认遥测存储使用 ClickHouse，测试或不连接 ClickHouse 的联调可显式切换到 `APM_STORAGE_MODE=memory`；正常运行的管理域仍需 PostgreSQL。

这意味着当前交付是“协议到查询下钻 + 网页应用工作区”的开发闭环，不是完整 APM 产品：当前已实现 PostgreSQL 管理数据、邮箱密码登录、Session/CSRF、输入唯一包名后生成 UUID `appId` 和永久 App Key、成员关系授权、浅色 PC 控制台、按 `appId + buildId` 的 mapping 网页上传/审计替换和 Crash 请求内 Retrace；仍未实现开放注册、OIDC、成员邀请/角色编辑、Key 轮换/撤销、构建自动上传、mapping 下载/删除、应用删除、HTTPS 生产网关、客户端生产级文件队列、Protobuf、限流、告警规则和容量压测。

网页登录与应用管理接口、首次管理员配置和本地 PostgreSQL 步骤见[应用管理 API](../api/app-api.md)。

卡顿服务端协议、Schema、固定数据集、接收错误和查询接口见[卡顿监控服务端 API](../api/jank-server-api.md)。Android/btrace 采集代码不在本仓库，完整生产接入尚未验收；移动端 UI 仍未实现；桌面端卡顿 Dashboard 页面已经落地，详见[前端知识库](../../frontend/docs/knowledge-base/README.md)。

btrace `.rheajank.zip` 的原始请求体、mapping、幂等落库和错误契约见[卡顿压缩包解析与落库 API](../api/stack-artifact-api.md)；它已替代批量入口中的结构化卡顿个例。
