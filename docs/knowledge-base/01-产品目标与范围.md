# 产品目标与范围

## 背景

Android 端已经具备性能数据采集能力，平台下一步需要补齐数据上传、服务端处理、存储、聚合分析、Dashboard 展示和告警。当前团队更熟悉 Java/Kotlin，因此第一版强调低学习成本和端到端可验证。

## 建设目标

平台需要做到：

1. 弱网环境下可靠上传 Android 性能事件。
2. 在服务端完成项目识别、协议校验、脱敏、标准化和存储。
3. 支持按时间、版本、渠道、设备、系统、页面和接口等维度查询。
4. 提供 p50、p90、p95、p99 等分位数。
5. 识别版本退化、慢设备、慢页面和慢接口。
6. 对异常指标进行告警。
7. 为后续多租户和产品化演进保留边界。

## 第一版范围

### App 启动

- 冷启动、温启动、热启动。
- 总耗时以及 Application、Activity、首帧等阶段耗时。
- 版本、设备和 Android 系统分布。

### 网络性能

- 总耗时，以及 DNS、连接、TLS、TTFB、下载耗时。
- 请求方法、状态码、错误类型和请求/响应字节数。
- 标准化后的域名和接口路径。

### 卡顿或 ANR

- 卡顿次数、卡顿率、帧耗时分布。
- 页面、堆栈、受影响设备数。
- App 版本和 Android 系统版本分布。

除本页后续单独说明的 JVM Crash 子范围外，内存、CPU、耗电和完整 Trace 不属于第一条闭环的必要范围，应在上报、存储和分析链路稳定后增加。NDK/native Crash、非致命异常和 ANR 仍不在当前 Crash 首期范围。

## Dashboard 必须回答的问题

- 某版本冷启动的 p50、p90、p95、p99 是多少？
- 新版本相对旧版本是否退化？
- 哪些设备、系统、渠道、页面或接口最慢？
- 哪些接口错误率最高？
- 慢样本发生时的设备、会话、网络和阶段耗时是什么？
- 问题影响了多少用户或设备？
- 最近是否出现异常突增或数据中断？

## 最小可用闭环

```text
创建项目 → 获取上报 Key → Android 批量上报 → 服务端校验与脱敏
→ ClickHouse 入库 → Grafana 展示 p95 趋势 → 下钻慢样本 → 阈值告警
```

## 第一版明确不做

- 微服务拆分。
- Kubernetes 编排。
- Kafka 消息总线。
- Redis 基础设施。
- 自研 Vue Dashboard。

“不做”是当前阶段的范围控制，不代表永久排除。具体触发条件见[实施路线图](09-实施路线图.md)。

## JVM Crash 首期实现状态

本次变更把 Java/Kotlin JVM 致命 Crash 纳入首条可运行闭环：客户端使用 `app_start` 去重会话作为分母，服务端提供 Crash 率、崩溃会话、受影响设备、问题指纹和原始堆栈下钻。当前服务端只接受 `app_start` 与 JVM fatal Crash 两种事件；NDK/native、非致命异常、ANR、Issue 生命周期和 Vue 产品页仍不在首期范围。

当前仓库已经实现 Spring Boot 接收 API、JSON/JSON+gzip 解析、事件校验、脱敏、服务端指纹、部分接受、`projectId + eventId` 去重、内存仓库和 ClickHouse HTTP 适配器。默认配置使用 ClickHouse，测试或无外部依赖联调时可显式切换到 `APM_STORAGE_MODE=memory`。ClickHouse 原始表、Crash 明细表、小时聚合表和物化视图已提供，但当前查询服务仍读取仓库中的原始事件并在 JVM 内计算统计，尚未把聚合表接入后端查询链路。

这意味着当前交付是“协议到查询下钻”的开发闭环，不是完整 APM 产品：PostgreSQL 管理数据、正式登录授权、Nginx/Compose 部署、客户端生产级文件队列、Protobuf、限流、告警规则和容量压测仍需后续实施。
