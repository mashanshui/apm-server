# 部署与运维

本页维护可复用的启动、发布、数据保护和排障步骤。环境最近核验统一见[当前状态](00-当前实现与验证边界.md#环境最近核验)，部署流水与完整命令输出不追加到本页。

## 当前小规模部署拓扑

```text
一台开发机或云主机（Compose 五容器）
├─ Web / Nginx：Vue 静态资源、HTTP、同源代理
├─ Spring Boot：接收、管理、领域查询、附件清理
├─ PostgreSQL：管理数据、Session、符号表元数据、Token 和分析任务
├─ ClickHouse：遥测事实、详情和聚合对象
└─ TypeScript MCP：独立只读查询服务，外部查询默认关闭
```

mapping 和 HPROF 使用后端持久卷；Grafana 可按[独立接入教程](../operations/grafana-clickhouse-install.md)安装，MinIO 未接入。当前入口仅 HTTP，不包含生产 HTTPS、容量、告警或恢复保障。云端 Compose 将 PostgreSQL 5432、ClickHouse HTTP 8123 绑定 `0.0.0.0`，仅用于受控调试；正式环境须删除公网映射或改用内网/VPN，并检查安全组。

| 文件 | 用途 |
|---|---|
| `compose.yaml` | 仅本地 PostgreSQL |
| `compose.cloud.yaml` | 五服务编排、内部网络、持久卷和健康检查；ClickHouse 内存上限 2 GiB |
| `compose.local.yaml` | 覆盖端口，仅绑定 `127.0.0.1`；Web 默认 8080 |
| `docker/nginx.conf` | 静态资源、history fallback、`/api/`、`/ingest/`、`/mcp` 和 `/healthz` 代理 |
| `scripts/start-dev.sh`、`scripts/stop-dev.sh` | macOS 本地全栈启停 |
| `scripts/deploy-cloud.sh` | 本机构建、打包、上传及云端健康等待 |

## 配置与首次启动

本地脚本读取根目录 `.env.local`；云端在部署目录维护 `.env.cloud`，权限设为 `600`，脚本不上传该文件。两者均不得提交或输出内容。至少配置：

- PostgreSQL、ClickHouse 的库名、用户和密码。
- 稳定的 `APM_APP_KEY_ENCRYPTION_KEY`：Base64 编码的 32 字节随机值，可用 `openssl rand -base64 32` 生成一次；后续启动保持不变并备份。
- 独立的 `APM_DEVICE_HASH_SALT`。
- 引导管理员邮箱、密码和可选显示名称；已存在邮箱不会覆盖密码，未配置则不自动创建。

首次打开网页后，创建唯一 Android 包名的应用，再到设置页查看该应用的永久 App Key。数据库密码和应用主密钥不得跨本地/云端复用。HTTP 调试使用 `APM_SESSION_COOKIE_SECURE=false`；生产 HTTPS 入口须改为 `true`。完整后端配置见[后端构建与运行](../../backend/docs/knowledge-base/05-构建配置与本地运行.md)。

## 本地启动与停止

在仓库根目录执行：

```bash
bash scripts/start-dev.sh
bash scripts/stop-dev.sh
```

启动脚本叠加云端与本地 Compose，校验必需配置后等待五服务健康，默认入口为 `http://127.0.0.1:8080/login`，可由 `WEB_PORT` 覆盖。默认复用已有 JAR 和 `frontend/dist`；缺少产物或传入 `--build` 才执行构建。源码变化后应使用：

```bash
bash scripts/start-dev.sh --build
```

构建要求 Java 21（可设置 `APM_JAVA_HOME`），通过 `bash` 调用 Gradle Wrapper；无本机 npm 时使用 Docker Node 22。后端连接容器内 PostgreSQL/ClickHouse，不会根据 `.env.local` 的远程 JDBC 地址跳过本地数据库。独立 `bootRun`/Vite 和远程数据库调试见[后端配置](../../backend/docs/knowledge-base/05-构建配置与本地运行.md#环境配置与工作目录)与[前端联调](../../frontend/docs/knowledge-base/05-本地开发与联调.md)。

更新已有数据卷前先核对结构并准备数据库和文件卷备份。`start-dev.sh --build` 不会为已有 ClickHouse 卷执行 SQL；缺少 009/010 等结构时，须在启动新后端前按[增量迁移边界](#数据保护与迁移)处理。PostgreSQL 的 Flyway 在后端启动时运行。

停止脚本执行 Compose `down`，保留数据卷；日志可通过以下命令查看：

```bash
docker compose --env-file .env.local -f compose.cloud.yaml -f compose.local.yaml logs --tail=100
```

## 云端发布

连接参数、主机指纹与私钥约定见[SSH 说明](../operations/cloud-ssh.md)，授权范围遵循[仓库规则](../../AGENTS.md#云服务器访问)。保持主机密钥校验，指纹不匹配时停止核实。

发布前确认目标版本、配置、数据卷和所需迁移；构建环境必须具备 Maven Local 的 `rhea-trace-processor:1.0.4`（当前仅本地制品，尚未发布到远程制品仓库）。从仓库根目录执行：

```bash
bash scripts/deploy-cloud.sh --identity-file "$HOME/.ssh/apm_cloud_mac"
```

脚本默认本地执行 `bootJar` 和前端构建，打包 JAR、前端产物、MCP 源码/锁文件、Docker 配置和 ClickHouse SQL。云端按上传源码构建 MCP（Node 24.19.0），随后等待全部五容器 `running healthy`，最长 600 秒；超时输出状态并失败退出。脚本不运行自动化测试或业务验收。

默认主机/用户见 SSH 说明，目录为 `/home/ubuntu/apm-server`，脚本默认私钥路径为 `$HOME/.ssh/apm_cloud`；可用 `--remote-host`、`--remote-user`、`--remote-port`、`--identity-file`、`--remote-directory` 覆盖。仅在确认 JAR 与 `frontend/dist` 对应目标源码时使用 `--skip-build`，远端 MCP 仍重新构建。

服务器手工更新与检查命令（在部署目录执行）：

```bash
sudo docker compose --env-file .env.cloud -f compose.cloud.yaml up -d --build
sudo docker compose --env-file .env.cloud -f compose.cloud.yaml ps
curl -fsS http://127.0.0.1/healthz
```

## 数据保护与迁移

Compose 使用 `apm-postgres-data`、`apm-clickhouse-data`、`apm-memory-report-artifacts`、`apm-symbols` 四个卷，实际名称带 Compose 项目前缀（默认 `apm-server`）。普通更新和镜像重建保留这些卷；切换项目名会使用另一组卷。

镜像清理前核对 Docker context、镜像 ID、容器引用和卷挂载，只处理本项目资源。停止容器仍可能引用镜像；删除容器不应附带卷删除参数。镜像清理、数据清空和备份删除是不同范围，后两者必须有明确授权，不能作为重部署的默认步骤。

- PostgreSQL 使用 Flyway V1～V16，JPA 只校验 schema。不要修改已发布迁移；V16 将 Crash 后台单份发布载荷上限扩展至 4 MiB。
- ClickHouse SQL 不由 Flyway 执行，空库按 001～010 顺序初始化；已有卷不会因镜像更新自动重跑初始化脚本。手工操作统一见[ClickHouse 初始化](../operations/clickhouse-local.md#空库初始化与已有数据边界)。
- `004_application_identity_schema.sql` 要求十张受影响业务表为空，再删除重建对象；不得在有数据的环境重跑全套初始化。005/006 新增内存表，007 追加进程身份列，008 独立创建当前 Crash 事实/状态，009 新增内存运行峰值表，010 为 Crash 事实与状态追加诊断列。执行前核对当前 schema 与数据，按缺失版本增量执行，详见[持久化与迁移](../../backend/docs/knowledge-base/03-持久化与数据库迁移.md)。
- V14 删除旧分析源码登记结构。升级前须停止旧任务入口、结束旧任务，并实际核验未知停止；迁移检测到活动任务或未确认停止的 Run 会拒绝执行。旧报告和停止审计保留，不伪造停止事实。

## 发布验收与回退

按目标环境核验，并在任务结果或发布系统记录版本、环境、命令、结果和局限：

1. 五服务健康且无异常重启；核对运行产物属于目标版本。
2. Nginx 配置、首页、`/login`、静态资源及深层路由可用；`/healthz` 返回后端 `UP`。
3. Flyway 成功、ClickHouse 所需列存在；登录/退出、应用授权、上报或查询按本次范围冒烟。
4. Agent/MCP 启用时分别检查有效凭据、跨应用拒绝及无凭据入口；仅收到 401 不能证明业务查询通过。
5. 保留数据的更新应核对原资源和配置；健康接口没有 ClickHouse 贡献者，UP 不代表遥测查询可用。

发布前准备数据库与文件卷的一致备份及可恢复的旧产物；仅保存备份不等于恢复演练通过。应用与迁移兼容时才可回退旧镜像。V14 删除旧结构后，不能直接运行依赖该结构的旧版本，恢复需使用匹配的数据库/文件备份并单独验收。

单独运行 JAR 时先复制到按版本或摘要区分的运行目录，避免后续 `bootJar` 覆盖 JVM 正在读取的文件；排障见[后端运行](../../backend/docs/knowledge-base/05-构建配置与本地运行.md#常见排查)。

## Agent 服务运行边界

`APM_AGENT_QUERY_ENABLED` 与 `MCP_ENABLED` 默认 false，需分别开启，并配置 MCP Host/Origin 白名单。MCP 仅通过内部网络连接 backend，不配置数据库凭据、不直接暴露端口。关闭外部查询后，网页仍可列出和撤销查询 Token；回退不恢复已撤销 Token。

`APM_AGENT_ANALYSIS_ENABLED` 默认 false，仅开放控制面；源码分析/明确修复在宿主本地执行，不向 Java、网页或 MCP 注入模型密钥。工具升级须保留 Skill 本地配置，并先结束旧活动/待回传任务；停止未知、原结果幂等回传和恢复规则见[分析专题](../../backend/docs/knowledge-base/local-analysis.md)与[Worker 说明](../../agent-skills/apm-crash-analyze/worker/README.md)。

## Crash 后台还原协调切换与独立恢复

1. 先关闭旧分析任务入口，使用原工具结束活动/待回传任务，核验本次宿主分析及本地工具均已停止并保存审计。不能以工具关闭或模型回答代替宿主停止。
2. 核对备份与目标环境。PostgreSQL 执行新增 V15（不修改已发布迁移）；已有 ClickHouse 仅增量执行 008。全新空库按 001～008，绝不在有数据环境重跑 004。
3. 同步更新后端、网页、MCP、Worker 0.5.0 与 Skill，保留 Skill 本地配置/凭据。当前只接受详情单份 stack、证据 3、报告 4；旧任务不进入当前 API，旧恢复记录不升级、不重跑、不只读渲染。
4. 先核验新表列、登录与隔离应用，再验证新启动/Crash、mapping 后台推进、固定来源、删除重传与新分析流程。当前统计从新事实数据集开始，不混入旧启动、旧 Crash 或旧聚合，也不自动清空它们。

后台重启由 PostgreSQL 租约到期重新领取；先恢复唯一已登记发布的同版本同字节载荷，再选择当前活动文件计算新候选。确认未知不得删 pending_payload 或重新选 mapping；读回摘要确认后才清载荷。通知失败由持久化轮转补偿，不按事件时间永久推进游标。恢复步骤不依赖重新上传全部客户端事件；保留 eventId/buildId/occurredAt 的原请求可补齐接收缺失侧。首次成功即使选错 mapping 也保持固定，这是当前取舍。

没有旧程序兼容/降级路径。需恢复旧版本时只能在独立环境恢复与旧产物匹配的数据库/文件一致备份并验收，不能让旧程序直接读写当前新模型或覆盖当前发布记录。物理旧版本/旧表/备份的清理属于另行授权范围。

2026-11-05 的[隔离演练](../validation/background-crash/README.md)验证了新库初始化、各消费者一次性切换、实际停止审计、旧数据隔离及确认丢失后恢复；该隔离演练不修改现有开发/云端数据。现有本地服务的部署版本和业务冒烟范围见[环境最近核验](00-当前实现与验证边界.md#环境最近核验)。生产备份还原、长期故障与多实例文件协调未被该演练证明。

## 生产运维与扩容边界

生产前须落实 HTTPS/证书续期、配置隔离、密钥托管、PostgreSQL 与文件卷备份恢复、ClickHouse TTL/磁盘/慢查询、错误率/延迟/拒绝率监控、日志轮转、告警及 CI/CD。当前单机 HTTP 部署不证明这些能力已完成。

容量不足时先优化批次和表设计、隔离数据库资源，再按实际瓶颈扩容后端；需要故障期间持续接收、削峰或回放时再引入 Kafka，接收与查询相互影响时再拆服务。具体触发条件见[路线图](09-实施路线图.md#平台容量与服务扩展)。
