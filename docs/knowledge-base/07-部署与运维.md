# 部署与运维

## 第一版拓扑

```text
一台开发机或云主机
├─ Nginx：HTTPS、反向代理、限流
├─ Spring Boot：接收、管理、查询、后台任务
├─ PostgreSQL：事务数据
├─ ClickHouse：APM 原始和聚合数据
├─ Grafana：Dashboard 与告警
└─ MinIO：mapping、符号表和附件（按需）
```

本地和小规模内测使用 Docker Compose。正式对外后，优先把 PostgreSQL 与 ClickHouse 放到独立磁盘或托管服务，再根据负载横向扩容 Spring Boot。

仓库中的 `compose.yaml` 用于本地 PostgreSQL 16；`compose.cloud.yaml` 提供云服务器的小规模部署形态，包括 PostgreSQL、ClickHouse、Spring Boot、Nginx 和 Vue 静态资源。内存异常报告的 ClickHouse 增量表为 `006_memory_leak_reports.sql`，必须在前五个脚本之后执行；附件默认位于独立持久卷，不通过静态资源暴露。Spring Boot 正常启动需要 PostgreSQL，Crash 存储按云端配置使用 ClickHouse。当前云端入口为 HTTP 80，尚未配置域名、HTTPS 证书或生产监控，不能把本次部署表述为正式生产就绪。当前云端仅用于调试，Compose 另外将 PostgreSQL 5432 和 ClickHouse HTTP 8123 映射到公网，供本地后端直接连接；切换到正式环境前必须删除公网数据库映射或改用内网/VPN。前端本地端口、开发代理和数据准备见[前端本地开发与联调](../../frontend/docs/knowledge-base/05-本地开发与联调.md)。

本地开发可在仓库根目录使用 PowerShell 脚本：

```powershell
.\scripts\start-dev.ps1
.\scripts\stop-dev.ps1
```

启动脚本先读取被 Git 忽略的 `.env.local`（显式进程环境变量优先），默认使用 ClickHouse 模式和远程 PostgreSQL 启动 Spring Boot 和 Vite 前端；ClickHouse 密码通过安全提示或 `CLICKHOUSE_PASSWORD` 环境变量取得，也会复用 `.env.local` 中的 `CLICKHOUSE_ADMIN_USER`、`CLICKHOUSE_ADMIN_PASSWORD` 和 `CLICKHOUSE_HTTP_URL`。`-DatabaseMode auto` 会根据 `APM_DATABASE_URL` 判断是否使用本地 PostgreSQL；`-DatabaseMode local` 可显式恢复本地管理库，`-DatabaseMode remote` 是默认值，也可显式要求远程管理库。脚本会在启动后端前选择并校验 JDK 21，在当前进程内覆盖 `JAVA_HOME` 后再预热 Gradle Wrapper，不修改系统级 `JAVA_HOME`；也可通过 `APM_JAVA_HOME` 指定 JDK 21 路径。失败清理会递归结束本次启动的 `cmd`、Gradle 和 Java 子进程。`-StorageMode memory` 可切换 Crash 内存模式（管理库仍使用 PostgreSQL），`-NoFrontend` 可只启动后端。管理员、数据库和 Cookie 参数见[后端构建配置](../../backend/docs/knowledge-base/05-构建配置与本地运行.md)。脚本状态和日志保存在被 Git 忽略的 `build/dev-services/` 下，启动超时会自动清理本次启动的进程。

启动前必须在 `.env.local` 持久配置 `APM_APP_KEY_ENCRYPTION_KEY=<Base64 编码的 32 字节随机值>`。可以用 `[Convert]::ToBase64String([Security.Cryptography.RandomNumberGenerator]::GetBytes(32))` 生成一次；不得每次启动重新生成，必须备份且不能提交。启动脚本会在启动外部服务前校验其格式和长度。服务启动后先在网页创建输入唯一 Android application ID 的应用，再到设置页获取该应用 App Key 用于 Android 联调。

首次管理员创建是显式配置驱动且幂等的：不配置邮箱/密码不会自动创建账号，已存在的邮箱不会覆盖密码。完整接口和安全配置见[登录与项目管理 API](../api/app-api.md)。

## 云服务器部署形态

云端部署文件如下：

- `compose.cloud.yaml`：Web 容器映射 80 端口，调试阶段同时映射 PostgreSQL 5432 和 ClickHouse HTTP 8123 到公网；Spring Boot 仍只加入内部 Docker 网络。云厂商安全组还必须放行本地调试机到这两个 TCP 端口的入站访问。正式环境不得沿用数据库公网映射。
- `scripts/deploy-cloud.ps1`：在 Windows 本地完成 Boot JAR/前端构建、最小部署包打包、SCP 上传和云端 Compose 更新；脚本只负责部署，不运行测试、健康检查或业务验收。
- `docker/backend-runtime.Dockerfile`：使用部署前构建的 Spring Boot JAR，以非 root 用户运行，并持久化内存泄漏报告附件。
- `docker/frontend-runtime.Dockerfile` 与 `docker/nginx.conf`：提供 Vue history fallback，并将 `/api`、`/ingest` 同源代理到后端；上传请求体上限与后端内存报告边界保持一致。

部署前需要在具备内部 `rhea-trace-processor:1.0.1` Maven 制品的环境执行 `bootJar`，并执行前端 `npm run build`。将 JAR、`frontend/dist`、ClickHouse 初始化脚本和上述部署文件传到服务器后，在部署目录使用：

```bash
sudo docker compose --env-file .env.cloud -f compose.cloud.yaml up -d --build
sudo docker compose --env-file .env.cloud -f compose.cloud.yaml ps
curl -fsS http://127.0.0.1/healthz
```

上述手工命令也可以由本地脚本完成。脚本不会上传 `.env.cloud`，不会删除 Docker 数据卷，也不会执行验收：

```powershell
.\scripts\deploy-cloud.ps1
```

脚本默认使用 `AGENTS.md` 中的 SSH 主机、用户和私钥，部署目录为 `/home/ubuntu/apm-server`；可通过 `-RemoteHost`、`-RemoteUser`、`-RemotePort`、`-IdentityFile` 和 `-RemoteDirectory` 覆盖。默认会执行 `bootJar` 和 `npm run build`，不运行测试；`-SkipBuild` 只在已有最新 JAR 和 `frontend/dist` 时使用。部署结束后如需验收，单独执行本页后续的 Compose 状态、健康和业务接口检查。

`.env.cloud` 必须只保存在服务器并设置为 `600` 权限；至少配置数据库密码、ClickHouse 密码、`APM_APP_KEY_ENCRYPTION_KEY`、`APM_DEVICE_HASH_SALT` 和引导管理员账号。数据库密码和应用主密钥不得复用本地开发值。首次以 HTTP 访问时 `APM_SESSION_COOKIE_SECURE=false`；切换到 HTTPS 后必须改为 `true`，并在网关上保留 `/api`、`/ingest` 同源代理。Compose 数据卷名称固定为 `apm-postgres-data`、`apm-clickhouse-data` 和 `apm-memory-report-artifacts`，更新镜像不应删除这些卷。

当前调试环境允许本地后端直接使用云端两个数据库：`APM_DATABASE_URL=jdbc:postgresql://124.221.252.121:5432/apm`，ClickHouse 使用 `http://124.221.252.121:8123`。本地 `.env.local` 只保存被 Git 忽略的连接参数和密码，不能复制到仓库或日志；启动脚本会根据远程 JDBC 地址跳过本地 PostgreSQL。该模式下本地后端的迁移、登录、应用管理、上报和查询都作用于云端调试数据。

本次云服务器验收至少记录：四个应用容器为 `running (healthy)`、`/healthz` 返回后端 `UP`、首页与 `/login` 返回 200、ClickHouse 六个初始化脚本执行成功、PostgreSQL Flyway 完成，以及从外部网络访问 Web 入口的结果。HTTP 入口可用不代表已经完成 HTTPS、备份恢复、容量、告警或生产安全验收。

- HTTPS 证书管理。
- 环境变量或密钥服务管理敏感配置。
- PostgreSQL 定期备份与恢复演练。
- ClickHouse TTL、磁盘容量和慢查询监控。
- Spring Boot Actuator、JVM 与进程监控。
- 上报错误率、写入延迟、拒绝率和端到端数据延迟监控。
- 二进制堆栈解析耗时、繁忙拒绝率、JVM 堆和临时目录容量监控。
- 开发、测试和生产环境隔离。
- CI/CD 流程。
- 日志轮转与错误追踪。

## 服务健康基线

全栈验收需要检查后端健康和指标；具体端点、监控项及实现限制由后端维护。详见[后端知识库](../../backend/docs/knowledge-base/05-构建配置与本地运行.md)。

## 扩容顺序

1. 优化 Android 批次、服务端批量写入和 ClickHouse 表设计。
2. 将数据库迁移到独立资源或托管服务。
3. 横向扩容 Spring Boot 接收节点。
4. 需要削峰、回放或多消费者时加入 Kafka。
5. 接收与查询互相影响时拆分 `apm-ingest` 和 `apm-query`。
6. 多服务需要独立扩缩容、频繁滚动发布和复杂治理时再评估 Kubernetes。

## 故障与恢复关注点

- ClickHouse 不可用时，客户端队列能否保留并重试数据。
- PostgreSQL 是否能从备份恢复，恢复点目标需明确。
- 磁盘接近满载前是否提前告警。
- 数据 TTL 和归档是否按计划执行。
- 发布失败是否有可验证的回滚路径。
- 无数据究竟来自业务低谷、SDK 故障、接收故障还是入库故障。

## 后端工程迁移后的路径

统一启停命令不变，启动脚本使用 `backend/` 作为后端工作目录，根目录 `.env.local`、`.gradle-local/`、Compose 和 `build/dev-services/` 保持原位。后端 `clean` 只清理 `backend/build/`；独立构建、外部资源绝对路径配置和排障见[后端构建与运行](../../backend/docs/knowledge-base/05-构建配置与本地运行.md)。
