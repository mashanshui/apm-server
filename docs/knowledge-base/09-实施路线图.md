## 推荐实施顺序

继续按“问题 → 指标口径 → 协议 → 存储 → 查询 → 页面 → 验收”推进。当前 Crash 与卡顿已经打通 JSON/gzip 最短链路，完整 btrace 堆栈产物也已打通原始二进制同步解析。下一步优先补二进制解析与既有接收链路的生产容量、监控和故障边界，再根据客户端兼容和吞吐需求决定异步对象存储、Protobuf、Kafka 与服务拆分；启动、网络等新信号沿用同一顺序接入。

[APM Agent 平台方案](../../apm-agent-platform-design.md)已按当前模块化单体、PostgreSQL/Flyway、应用成员授权和 Jank 查询链路收敛；当前没有已验收的 Agent Worker、审批修复或 CI 闭环。

独立的应用查询 Token、Agent HTTP 和只读 MCP 已实现；以下阶段仅指修复平台，不否定当前只读查询能力。

1. 先人工选择 Jank Issue，登记构建与精确源码版本，冻结证据，完成单个只读 Worker 的分析与离线质量评估。
2. 分析达到预先确认的质量门槛后，再增加 START_FIX 审批、按 Run 隔离的修改环境、不可变交付物和确定性 CI 验证。
3. 自动触发、多模型、自动 PR、真机回归、修复平台的 MCP 调度集成和消息队列由实际需求触发，不作为前两个阶段的前置条件。

实施不得改变现有同步接收、应用身份或客户端上报契约。证据快照必须考虑历史 ZIP 未保留、mapping 替换和原事件 TTL；编译通过与性能已改善分别验收。完整约束与验收场景维护在方案中，本页只记录阶段。

阶段 A 交付需包含真实模型评估、权限与隔离、任务恢复证据；阶段 B 默认由人分别触发 FIX 和 VERIFY，不自动循环修复。设计已明确只读证据分析与源码定位两种模式、源码产物二次授权，以及 Claim/完成幂等、审批过期和安全撤销的验收条件；这些均为待实现约束。

### 平台容量与服务扩展

| 观察到的需求或瓶颈 | 建议动作 |
|---|---|
| ClickHouse 不可用时仍必须接收 | 加入 Kafka |
| 接收与查询互相影响 | 拆分接收与查询服务 |
| 多个消费者处理同一事件 | 使用 Kafka Topic 与消费者组 |
| 需要评论、应用管理和完整产品交互 | 扩展 Vue 产品界面 |
| 单机数据库容量、IO 或可用性不足 | 使用托管集群、分片副本或冷热分层 |
| 多服务需要复杂编排和独立扩缩容 | 评估 Kubernetes |

扩展应由可测量的负载或业务需求触发，不按“最终架构想象”提前实施。

## 二进制堆栈解析实施进度

`POST /ingest/v1/stack-artifacts:parse` 当前使用 `application/vnd.shanshui.rheajank+zip` 接收 v3 卡顿产物，复用 App Key、双重字节上限、基于 `appId/buildId` 的应用隔离 mapping、同步并发许可和稳定错误语义。服务端调用 processor 一次，从目标主线程派生 expected/parsed/missing，写入原始事实、卡顿事实和详情，只返回 accepted/duplicate；不保存 ZIP，也不提供异步任务。

服务端 manifest v3 接收契约已经冻结；`attemptedSampleCount` 仍按 processor 要求上传，但服务端业务忽略。批量入口中的结构化 jank 已退出契约。processor `1.0.2` 与客户端实际设备 ZIP 已完成 UUID v4 主线程-only 解析、云端 HTTP 首次接受、重复和 Jank 详情验证；之后仍需进行 Android 生产上传冒烟、受控制品仓库与 mapping 发布治理、容量压测和故障恢复演练。旧 `1.0.1` 数值 PID/UUID 失败记录仅保留为历史边界证据。

进入生产灰度前仍需确定受控 processor 制品仓库、mapping 发布与清理流程，补齐解析耗时/繁忙/临时磁盘指标并完成代表性设备、产物大小和并发下的 p95/p99、JVM 堆与临时磁盘压测。同步解析影响接收实例稳定性或需要断点续传、长期保存、多人复用结果时，再切换为预签名对象存储上传和异步解析任务。
