## 推荐实施顺序

继续按“问题 → 指标口径 → 协议 → 存储 → 查询 → 页面 → 验收”推进。当前 Crash 与卡顿已经打通 JSON/gzip 最短链路，完整 btrace 堆栈产物也已打通原始二进制同步解析。下一步优先补二进制解析与既有接收链路的生产容量、监控和故障边界，再根据客户端兼容和吞吐需求决定异步对象存储、Protobuf、Kafka 与服务拆分；启动、网络等新信号沿用同一顺序接入。

## 产品化三阶段

### 第一阶段：Grafana 与 Crash 前端最小闭环

完成上报、ClickHouse 存储、聚合 SQL、Grafana Dashboard 和 Crash 前端最小闭环。当前该闭环已具备开发验收条件；后端查询仍未使用小时聚合表，告警规则和多租户数据源隔离仍待实施。前端实现状态见[前端知识库](../../frontend/docs/knowledge-base/README.md)。

### 第二阶段：管理能力

当前已完成网页管理的最小子集：PostgreSQL 用户/应用/成员模型、引导管理员、邮箱密码登录、Session/CSRF、应用列表/搜索/创建/基础设置、永久 App Key 查看，以及 Crash 与卡顿查询的成员授权；Vue 前端已提供浅色 PC 应用工作区。二进制解析能够按应用读取运维预置 mapping，但仍需补齐用户与团队、成员邀请/角色编辑、mapping 上传/版本/清理、数据保留和告警规则管理。

### 第三阶段：Vue 产品化

Vue 已承担登录权限、应用管理、Crash 排障和卡顿指标/问题/证据下钻；后续产品化继续补齐堆栈反混淆、Issue 工作流、版本回归报告和多租户体验。Grafana 保留内部趋势、临时分析、运维和告警用途；具体前端待办由[维护约定与待办](../../frontend/docs/knowledge-base/08-维护约定与待办.md)维护。

## 扩展触发条件

| 观察到的需求或瓶颈 | 建议动作 |
|---|---|
| ClickHouse 不可用时仍必须接收 | 加入 Kafka |
| 接收与查询互相影响 | 拆分接收与查询服务 |
| 多个消费者处理同一事件 | 使用 Kafka Topic 与消费者组 |
| 需要评论、应用管理和完整产品交互 | 扩展 Vue 产品界面 |
| 单机数据库容量、IO 或可用性不足 | 使用托管集群、分片副本或冷热分层 |
| 多服务需要复杂编排和独立扩缩容 | 评估 Kubernetes |

扩展应由可测量的负载或业务需求触发，不按“最终架构想象”提前实施。

## JVM Crash 实施进度

Crash 首期从原空骨架直接落地了协议模型、内存可运行闭环、ClickHouse schema/HTTP 适配器、查询 API、Grafana Dashboard 资源、Vue Crash 前端、Android 联调样例、自动化测试和本地一键启动/停止脚本。当前服务默认使用 ClickHouse，测试使用内存仓库；后端统计仍在 JVM 内完成，ClickHouse 小时聚合对象尚未接入查询适配器。

生产灰度前仍需完成：真实 PostgreSQL/ClickHouse 写入与故障恢复演练（当前 PostgreSQL Testcontainers 需要 Docker）、聚合查询接入或明确容量边界、开放注册/OIDC（如需要）、客户端文件持久队列、密钥与盐值清理、限流/告警、Nginx/HTTPS/备份部署和容量/SLA 确认。

## 卡顿服务端实施进度

卡顿服务端闭环已经调整为两条入口：卡顿个例的正式契约为 v3 `.rheajank.zip`，FPS 与前台挂起汇总继续走 JSON/gzip v2 批次。服务端具备脱敏、`jank-v1` 指纹、`jank-artifact-v2` 证据算法、内存/ClickHouse 幂等仓库、FPS/设备日挂起率聚合、质量指标、请求限制和应用成员查询授权；Vue 已展示期望、已解析、缺失采样质量。

旧 ClickHouse 001～003 结构的固定数据集写入、`FINAL` 去重、Issue/FPS/挂起率分位数、趋势和事实/详情一致性曾完成验收；本次 004 结构切换后需重新验证 UUID `app_id`、`package_name` 和空表保护。进入生产灰度前仍需完成生产规格的聚合性能压测，并确认卡顿明细/聚合 TTL、采样体积、算法版本演进、限流告警和事实/详情补偿策略。

## 二进制堆栈解析实施进度

`POST /ingest/v1/stack-artifacts:parse` 当前使用 `application/vnd.shanshui.rheajank+zip` 接收 v3 卡顿产物，复用 App Key、双重字节上限、基于 `appId/buildId` 的应用隔离 mapping、同步并发许可和稳定错误语义。服务端调用 processor 一次，从目标主线程派生 expected/parsed/missing，写入原始事实、卡顿事实和详情，只返回 accepted/duplicate；不保存 ZIP，也不提供异步任务。

服务端 manifest v3 接收契约已经冻结；`attemptedSampleCount` 仍按 processor 要求上传，但服务端业务忽略。批量入口中的结构化 jank 已退出契约。processor `1.0.2` 与客户端实际设备 ZIP 已完成 UUID v4 主线程-only 解析、云端 HTTP 首次接受、重复和 Jank 详情验证；之后仍需进行 Android 生产上传冒烟、受控制品仓库与 mapping 发布治理、容量压测和故障恢复演练。旧 `1.0.1` 数值 PID/UUID 失败记录仅保留为历史边界证据。

进入生产灰度前仍需确定受控 processor 制品仓库、mapping 发布与清理流程，补齐解析耗时/繁忙/临时磁盘指标并完成代表性设备、产物大小和并发下的 p95/p99、JVM 堆与临时磁盘压测。同步解析影响接收实例稳定性或需要断点续传、长期保存、多人复用结果时，再切换为预签名对象存储上传和异步解析任务。

## 内存指标实施进度

PSS、VSS 和 Java 堆已通过 `memory_sample` 接入既有 JSON/gzip 批次，完成内存模式的幂等写入、summary/trend 查询、UTC 空桶和前后台/进程筛选；Vue 页面提供三个固定页签、五张统计卡片和百分位趋势切换。005 ClickHouse 表、适配器和 `quantileExactInclusiveIf` 精确插值 SQL 已在资源测试和 ClickHouse 26.7.3.19 固定数据集对照中验证；Android 采集/持久队列、生产容量和故障恢复仍待外部验收。

应用级永久 App Key 与不可变包名绑定已进入当前实现。后续若产品需要泄露处置，必须作为新变更设计应用删除或 Key 撤销/轮换，不能在本期永久 Key 契约下静默改变；旧项目数据不提供迁移兼容。
