## 推荐实施顺序

继续按“问题 → 指标口径 → 协议 → 存储 → 查询 → 页面 → 验收”推进。当前 Crash 与指标已经打通 JSON/gzip 最短链路，完整 btrace 堆栈产物也已打通原始二进制同步解析。下一步优先补二进制解析与既有接收链路的生产容量、监控和故障边界，再根据客户端兼容和吞吐需求决定异步对象存储、Protobuf、Kafka 与服务拆分；启动、网络等新信号沿用同一顺序接入。

## 扩展触发条件

### Agent 辅助分析与修复

已实现单事件 JVM Crash 证据、应用 Worker、Task/Run、宿主当前工作区分析及明确授权的本地修复；不要求构建源码登记，不再采集全仓快照。Python 管理任务、租约和报告，修改/验证为宿主自报，当前代码与历史 APK 的对应关系未知。行为见[分析专题](../../backend/docs/knowledge-base/local-analysis.md)，有限验证见[专项证据](../validation/analysis/README.md)。

后续独立交付范围为生产缺陷质量集、其他宿主/系统兼容、审批、隔离的云端执行、不可变交付物和确定性 CI。是否扩展到 Jank、自动触发、多模型、PR 或真机回归，须由实际需求与质量门槛触发，不以已有只读查询或报告保存成功推断已完成。总体目标见[Agent 平台方案](../../apm-agent-platform-design.md)。

### 平台容量与服务扩展

| 观察到的需求或瓶颈 | 建议动作 |
|---|---|
| ClickHouse 不可用时仍必须接收 | 加入 Kafka |
| 接收与查询互相影响 | 拆分接收与查询服务 |
| 多个消费者处理同一事件 | 使用 Kafka Topic 与消费者组 |
| 需要评论、应用管理和完整产品交互 | 扩展 Vue 产品界面 |
| 单机数据库容量、IO 或可用性不足 | 使用托管集群、分片副本或冷热分层 |
| 多服务需要复杂编排和独立扩缩容 | 评估 Kubernetes |

扩展应由可测量的负载或业务需求触发，不按“最终架构想象”提前实施。

## 当前生产化优先项

1. 完成 Android SDK 生命周期、持久队列与代表性真机产物接入；稳定 processor 制品来源和发布流程。
2. 按真实分布验证 Crash、卡顿、FPS/挂起率、内存采样及报告的容量和故障恢复，分别确认预算与 TTL。
3. 补齐 HTTPS、数据库网络隔离、密钥托管、备份恢复、监控告警和发布回退。
4. 根据业务需求扩展用户/团队、成员管理、Key 泄露处置、Issue 工作流和新信号页面。

具体参数只在[待确认事项](13-待确认事项.md)维护，已实现能力只在[状态页](00-当前实现与验证边界.md)汇总；本页不追加任务完成数量或归档流水。
