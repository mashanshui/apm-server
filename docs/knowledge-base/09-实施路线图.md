# 实施路线图

## 开发阶段

| 阶段 | 主要工作 | 验收结果 |
|---|---|---|
| 0. 指标定义 | 选定启动、网络、卡顿/ANR；定义字段和口径 | 事件协议 v1 与示例数据确定 |
| 1. 基础环境 | Spring Boot、Docker Compose、PostgreSQL、ClickHouse、Grafana | 健康检查和数据库连接通过 |
| 2. 管理能力 | 用户、项目、App、版本、密钥、mapping 元数据 | 可创建项目并获取上报 Key |
| 3. 上报链路 | JSON、gzip、批量、校验、脱敏、入库和错误响应 | 模拟数据稳定进入 ClickHouse |
| 4. 协议优化 | Protobuf、Schema 兼容、批次与重试优化 | 不同 SDK 版本兼容上报 |
| 5. 聚合查询 | TTL、小时聚合、分位数、排行、版本对比 | 固定数据集结果正确且查询受限 |
| 6. Dashboard | 总览、启动、网络、卡顿、版本对比、数据质量 | 筛选、下钻、无数据和告警可用 |
| 7. 安全测试 | 隔离、限流、轮换、敏感字段、只读账号 | 越权与隐私测试通过 |
| 8. 部署运维 | HTTPS、备份、监控、CI/CD、容量与故障演练 | 测试环境端到端运行且可恢复 |

## 推荐实施顺序

先从 Dashboard 问题反推事件字段；用 JSON 打通最短链路后，再引入 Protobuf、gzip、限流、兼容和去重；优先完成数据质量 Dashboard，再做启动、网络、卡顿和版本对比。

## 产品化三阶段

### 第一阶段：Grafana 优先

完成上报、ClickHouse 存储、聚合 SQL、Grafana Dashboard 和告警，不开发 Vue。当前已提供 Crash Dashboard 和聚合 SQL 资源，但后端查询仍未使用小时聚合表，告警规则和多租户数据源隔离仍待实施。

### 第二阶段：管理能力

补齐用户与团队、项目与 App、成员角色、上报 Key、mapping、数据保留和告警规则管理；图表继续使用 Grafana。

### 第三阶段：Vue 产品界面

Vue 承担登录权限、项目管理、事件详情、堆栈反混淆、问题归组、评论状态、版本回归报告和多租户体验；Grafana 保留内部趋势、临时分析、运维和告警用途。

## 扩展触发条件

| 观察到的需求或瓶颈 | 建议动作 |
|---|---|
| ClickHouse 不可用时仍必须接收 | 加入 Kafka |
| 接收与查询互相影响 | 拆分接收与查询服务 |
| 多个消费者处理同一事件 | 使用 Kafka Topic 与消费者组 |
| 需要问题归组、评论和产品交互 | 开发 Vue 产品界面 |
| 单机数据库容量、IO 或可用性不足 | 使用托管集群、分片副本或冷热分层 |
| 多服务需要复杂编排和独立扩缩容 | 评估 Kubernetes |

扩展应由可测量的负载或业务需求触发，不按“最终架构想象”提前实施。

## JVM Crash 实施进度

Crash 首期从原空骨架直接落地了协议模型、内存可运行闭环、ClickHouse schema/HTTP 适配器、查询 API、Grafana Dashboard 资源、Android 联调样例和自动化测试。当前服务默认使用 ClickHouse，测试使用内存仓库；后端统计仍在 JVM 内完成，ClickHouse 小时聚合对象尚未接入查询适配器。

生产灰度前仍需完成：真实 ClickHouse 写入/查询与故障恢复压测、聚合查询接入或明确容量边界、正式登录和项目成员授权、客户端文件持久队列、密钥与盐值清理、限流/告警、Compose/Nginx 部署和容量/SLA 确认。
