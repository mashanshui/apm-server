# 架构决策记录

## ADR-JVM-CRASH-001：以 app_start 会话作为 Crash 分母

- 状态：已接受，2026-08-15
- 决策：崩溃会话数除以同一筛选条件下去重的 app_start sessionId，按每千会话和无崩溃会话率展示。
- 原因：会话分母可解释版本影响范围，避免仅用 Crash 事件数掩盖重复上报和同一会话多次异常。
- 约束：没有有效 app_start 时比例必须为空并标记分母不足，不能显示为 0。

## ADR-JVM-CRASH-002：ClickHouse 默认持久化 + 内存测试适配器

- 状态：已接受，2026-08-18 复核
- 决策：默认使用 ClickHouse HTTP JSONEachRow 适配器和版本化 SQL；测试或无外部依赖联调通过 `APM_STORAGE_MODE=memory` 显式启用内存仓库。
- 原因：当前工程需要先保留明确的生产持久化边界，同时让协议、统计和下钻可以在无外部依赖的测试模式中复现；使用 JDK `HttpClient` 避免在首期引入额外驱动。
- 风险：真实 ClickHouse/Grafana 固定数据集验收材料已经存在，但后端查询仍读取原始事件并在 JVM 内计算；未完成容量、故障恢复和正式权限验收前，不能宣称生产链路已上线。

## ADR-JVM-CRASH-003：首期查询保留原始事件计算路径

- 状态：首期暂定，2026-08-18
- 决策：ClickHouse 负责原始事件和 Crash 明细的持久化；后端 `CrashQueryService` 通过 `EventRepository` 读取原始事件，在 JVM 内完成时间过滤、去重、分组和比例计算。小时聚合表与物化视图先作为可重复初始化的存储资源保留，暂不宣称已经接入查询链路。
- 原因：先保证内存模式、MockMvc 和固定数据集能够复现协议与统计口径，并保留统一仓库边界；当前代码尚未实现聚合查询适配器和容量基线。
- 代价：ClickHouse 模式下查询会读取原始事件，无法把当前测试结果直接外推到生产规模；需要在容量压测后决定接入聚合表、增加查询适配器或调整保留策略。
- 重评条件：单项目原始事件量、查询 p95、ClickHouse 扫描量或 Dashboard 并发超过已确认目标。

## 备选方案摘要

### ClickHouse 的替代方案

- 仅 PostgreSQL：适合原型和小规模验证，规模增长后聚合与存储成本较高。
- PostgreSQL + TimescaleDB：保留 PostgreSQL 体验，适合中等规模；高基数分析通常不及 ClickHouse。
- Elasticsearch/OpenSearch：全文搜索强，但资源与运维成本较高。
- Prometheus：适合平台自身指标和告警，不适合大量客户端原始事件。

### 消息队列备选

- Kafka：高吞吐、持久化、削峰、回放、多消费者，规模化阶段首选。
- RabbitMQ：路由和任务队列成熟，长期保留与大规模回放较弱。
- Redis Streams：已有 Redis 时可过渡，不宜成为长期核心遥测总线。
