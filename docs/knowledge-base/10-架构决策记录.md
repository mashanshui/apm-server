# 架构决策记录

## ADR-ARCH-001：按业务域实施单进程模块化单体

- 状态：已接受，2026-09-04
- 背景：旧代码按 `web/service/repository/domain/config/security` 技术层组织，Crash、卡顿、接收、身份、存储和指标职责互相穿透；联合事件模型和联合 ClickHouse 仓储使任一信号变化都扩大影响范围。
- 决策：保持一个仓库、一个 Gradle 工程、一个 Spring Boot 进程和一次部署，代码按 `identity`、`ingest`、`crash`、`jank` 业务域以及 `telemetry`、`platform`、`bootstrap` 支撑边界拆分。跨模块只允许依赖公开 `api`，实现统一放入 `internal`；Crash 与 Jank 分别拥有领域模型、存储端口、ClickHouse/内存适配器和指标端口；`bootstrap` 是唯一组合根。
- 理由：当前规模尚不需要承担多服务发布、网络一致性和运维成本，但需要让身份、接收、Crash 与卡顿可以独立演进，并阻止联合模型和共享仓储继续膨胀。
- 影响：外部 HTTP 路由、JSON、配置键、数据库 schema、指标名称和单进程启动方式保持不变；新增 ArchUnit 测试强制模块依赖白名单、`internal` 隔离和无环。`platform` 只提供无业务表语义的 ClickHouse HTTP 能力，不成为共享业务逻辑收容区。
- 重评条件：接收与查询出现明确不同的扩缩容、故障隔离或发布节奏，且容量数据证明独立部署收益足以覆盖分布式系统成本时，再评估 Gradle 多模块或服务拆分。

## ADR-JVM-CRASH-001：以 app_start 会话作为 Crash 分母

- 状态：已接受，2026-08-15
- 决策：崩溃会话数除以同一筛选条件下去重的 app_start sessionId，按每千会话和无崩溃会话率展示。
- 原因：会话分母可解释版本影响范围，避免仅用 Crash 事件数掩盖重复上报和同一会话多次异常。
- 约束：没有有效 app_start 时比例必须为空并标记分母不足，不能显示为 0。

## ADR-JVM-CRASH-002：ClickHouse 默认持久化 + 内存测试适配器

- 状态：已接受，2026-08-18 复核
- 决策：默认使用 ClickHouse HTTP JSONEachRow 适配器和版本化 SQL；测试或无外部依赖联调通过 `APM_STORAGE_MODE=memory` 显式启用内存仓库。
- 原因：当前工程需要先保留明确的生产持久化边界，同时让协议、统计和下钻可以在无外部依赖的测试模式中复现；使用 JDK `HttpClient` 避免在首期引入额外驱动。
- 风险：后端查询仍读取原始事件并在 JVM 内计算；固定数据集验收不等同于容量、故障恢复和正式权限验收，未完成这些验证前不能宣称生产链路已上线。

## ADR-JVM-CRASH-003：首期查询保留原始事件计算路径

- 状态：首期暂定，2026-08-18
- 决策：ClickHouse 负责原始事件和 Crash 明细的持久化；后端 `CrashQueryService` 通过 Crash 查询端口读取原始事件，在 JVM 内完成时间过滤、去重、分组和比例计算。小时聚合表与物化视图先作为可重复初始化的存储资源保留，暂不宣称已经接入查询链路。
- 原因：先保证内存模式、MockMvc 和固定数据集能够复现 Crash 统计口径，并保留统一仓库边界；卡顿 FPS/挂起率已有独立聚合查询适配器，但 Crash 小时聚合和容量基线仍未接入。
- 代价：ClickHouse 模式下查询会读取原始事件，无法把当前测试结果直接外推到生产规模；需要在容量压测后决定接入聚合表、增加查询适配器或调整保留策略。
- 重评条件：单项目原始事件量、查询 p95、ClickHouse 扫描量或 Dashboard 并发超过已确认目标。

## ADR-JVM-CRASH-004：前端通过后端查询代理访问 ClickHouse

- 状态：已接受，2026-08-19
- 决策：Vue Crash 前端只调用 Spring Boot 查询 API；Spring Boot 通过 Crash 查询端口读取 ClickHouse 或内存仓库，浏览器不直接连接 ClickHouse。
- 原因：避免把 ClickHouse 地址、账号和密码暴露给浏览器，并让应用范围校验、错误语义和未来正式身份认证集中在服务端。
- 当前形态：本地使用开发代理，生产需要同源网关或静态 Web 服务器完成 `/api` 反向代理；具体配置见[前端部署、安全与运行边界](../../frontend/docs/knowledge-base/07-部署安全与运行边界.md)。
- 限制：生产仍需要同源网关、HTTPS 和正式运维配置；OIDC、成员邀请和多租户运营能力尚未实现。

## ADR-JANK-001：卡顿个例由服务端保存精确耗时和采样估算

- 状态：已接受，2026-08-27
- 决策：`jank` 事件的主线程消息总耗时作为精确测量值保存；采样调用树的总耗时、未归属耗时和覆盖/未覆盖区间单独标记为估算证据，不命名为方法精确耗时或 CPU 自耗时。
- 原因：消息起止由客户端直接测量，采样只能推导被覆盖区间；相邻样本存在空洞时不能用总时长或样本数量填充，避免把估算误读为精确剖析。
- 影响：查询响应必须同时返回 `exactMessageDurationNs`、估算字段、采样时间片和质量计数；后续算法版本变更不得静默改变既有统计含义。

## ADR-JANK-002：服务端生成版本化卡顿 Issue 指纹

- 状态：已接受，2026-08-27
- 决策：服务端使用 `jank-v1` 从规范化关键应用调用路径及稳定上下文生成指纹，忽略行号、地址、数字动态值和采样次数；客户端指纹不作为正式 Issue 身份。
- 原因：同一根因应跨采样次数和构建行号变化归组，同时保留每个事件的原始证据；将指纹算法版本写入结果，便于未来兼容迁移。
- 影响：指纹输入只允许白名单维度，路径不稳定或缺失时使用明确的回退路径；跨版本重新归组必须通过新版本算法完成。

## ADR-JANK-003：卡顿存储独立于 Crash 明细表

- 状态：已接受，2026-08-27
- 决策：ClickHouse 使用版本化 `002_jank_schema.sql` 保存卡顿事实、详情、Issue 聚合、场景帧汇总、挂起区间和设备日汇总；查询通过独立 `JankAggregationRepository`，不让任意字段进入 SQL。
- 原因：卡顿采样载荷、FPS 和挂起率的生命周期与查询口径不同，需要独立 TTL、排序键、去重和演进边界；内存仓库继续作为无外部依赖的固定数据集适配器。
- 限制：FPS/挂起率聚合已接通内存和 ClickHouse 适配器，但真实 ClickHouse 大规模性能、TTL 和故障恢复仍待外部验收。

## ADR-AUTH-APP-001：网页使用 PostgreSQL Session 与应用成员关系授权

- 状态：已接受，2026-08-25
- 决策：用户、应用、应用成员和 Spring Session JDBC 表由 PostgreSQL 持久化；网页使用 Spring Security + BCrypt + HttpOnly Session Cookie，应用读取/修改统一依据当前认证主体和 `app_member`。
- 原因：当前是同源单体 Web 应用，需要可撤销、跨重启的会话和服务端可信授权；不能继续把浏览器可伪造的 `X-App-Id` 或 `X-User-App-Ids` 当作身份事实。
- 影响：正常启动新增 PostgreSQL 依赖，Flyway 迁移与本地 Compose/引导管理员配置必须同步；Android 上报仍使用独立 `X-App-Key`，不共享网页 Session。
- 未包含：开放注册、OIDC、成员邀请/角色编辑、mapping 和应用删除。

## ADR-AUTH-APP-002：前端采用浅色 PC-only 应用工作区

- 状态：已接受，2026-08-25
- 决策：登录使用无侧栏浅色双栏外壳；受保护页面使用浅色侧栏、应用切换器、用户菜单和应用级导航；设计基线为宽度不小于 1280 像素的 PC，不实现移动端折叠或窄屏重排。
- 原因：本期目标是完成桌面控制台的应用信息架构和数据闭环，固定宽度可保持 Crash 表格、堆栈和应用设置的稳定可读性。
- 影响：未知路由进入明确的未找到页，不再推断或重定向任何旧项目标识；应用切换进入目标 Crash 总览并由路由变化清理旧查询状态；移动端适配列为未实现范围。

## ADR-STACK-001：完整 btrace 产物使用原始二进制同步解析（已被替代）

- 状态：已被 ADR-STACK-002 替代，历史行为不再是当前接口契约
- 决策：新增 `POST /ingest/v1/stack-artifacts:parse`，以 `application/vnd.shanshui.rheatrace+zip` 原始请求体接收单个 `.rheatrace.zip`；复用 `X-App-Key` 鉴权，可选 `X-Mapping-Id` 只选择应用目录内的运维预置 mapping。服务端受限流式读取并同步调用固定版本 `StackParser`，成功时直接返回 processor 报告。
- 原因：ZIP 本身已经是二进制压缩制品，JSON/Base64 会增加体积和客户端内存，multipart 在单文件且没有其他表单字段时只增加边界解析和契约复杂度；原始正文最贴近 parser 的 `InputStream` 输入，也能保持媒体类型版本和字节上限清晰。
- 影响：接口无事件幂等和持久化副作用，不保存 ZIP、不写 ClickHouse、不创建卡顿 Issue；客户端必须自行持久化文件、处理同步超时，并只对网络失败或 503 重试。mapping 由运维只读预置，管理 API 仍未实现。
- 重评条件：产物超过同步上传/解析的容量目标、解析影响接收实例、需要断点续传或跨请求复用报告时，改为预签名对象存储上传和异步任务；如果未来单次请求确实需要同时提交多个不同类型文件和元数据，再重新评估 multipart。

## ADR-STACK-002：卡顿 ZIP 同步解析并幂等落库

- 状态：已接受，2026-08-30
- 决策：保留 `POST /ingest/v1/stack-artifacts:parse` 路径，只接受 `application/vnd.shanshui.rheajank+zip` 的 v3 卡顿产物；服务端调用 `parseWithMappingResolver` 一次，按认证应用与 manifest `buildId` 选择可选 mapping，从目标主线程证据派生 expected/parsed/missing，再通过 Jank 写入协调器和专属存储端口幂等写入。成功只返回 accepted/duplicate。
- 原因：一个 ZIP 已包含事件事实和 Sampling 证据，服务端可以统一计算质量和指纹，避免客户端再展开 JSON 形成两套事实来源；同步复用现有并发、大小、去重和部分写入修复即可形成首版闭环。
- 影响：批量入口永久拒绝结构化 jank；`attemptedSampleCount` 仅满足 processor 当前契约，业务不使用；原始 ZIP 和完整报告不保存。mapping 缺失不阻塞落库，路径越界与符号链接逃逸拒绝。
- 重评条件：代表性产物和并发压测表明同步链路不能满足接收实例的延迟、堆或临时磁盘目标时，再引入对象存储和异步任务。

## 备选方案摘要

### ClickHouse 的替代方案

- 仅 PostgreSQL：适合原型和小规模验证，规模增长后聚合与存储成本较高。
- PostgreSQL + TimescaleDB：保留 PostgreSQL 体验，适合中等规模；高基数分析通常不及 ClickHouse。
- Elasticsearch/OpenSearch：全文搜索强，但资源与运维成本较高。
- Prometheus：适合平台自身指标和告警，不适合大量客户端原始事件。

### 消息队列备选

- Kafka：高吞吐、持久化、削峰、回放、多消费者，规模化阶段首选。
- RabbitMQ：路由和任务队列成熟，长期保留与大规模回放较弱。
- Redis Streams：已有 Redis 时可过渡，不宜成为长期核心遥测总线。

## ADR-AUTH-002：应用级永久 App Key 与不可变包名

- 状态：采纳。
- 背景：全局 Key 只能映射固定测试应用，无法支撑网页创建的应用隔离，并造成 `appId`、包名和 Key 混用。
- 决策：应用创建事务同时保存 Owner 和一对一凭据；Key 为 `apm_ak_` 加 32 字节随机值的 Base64URL，摘要用于鉴权索引，AES-256-GCM 密文用于授权查看，应用包名进入 AAD。Key 与包名永久不可变，不提供轮换、撤销、过期或旧项目迁移。
- 影响：启动必须注入并备份 `APM_APP_KEY_ENCRYPTION_KEY`；PostgreSQL 故障会使上报鉴权返回可重试 503；JSON 与 ZIP 的 `packageName` 必须匹配绑定包名，系统 `appId` 只来自鉴权结果。
- 重评条件：出现真实泄露处置、应用删除、多 Key、吞吐缓存或基础设施主密钥轮换需求。
