# 安全与隐私

## 三类身份

| 身份 | 推荐机制 | 关键控制 |
|---|---|---|
| Android 上报端 | App Key + HTTPS + 限流；可选 Play Integrity | 永久 Key 与包名绑定、配额、大小限制、时间窗口、异常设备/IP |
| 网页用户 | Spring Security + Session + HttpOnly Cookie | CSRF、Secure、SameSite、角色、应用权限 |
| Grafana 用户 | 独立登录或统一 OIDC | 组织、文件夹、Dashboard、数据源权限 |

APK 中的 App Key 可以被逆向，只能作为应用识别与配额控制手段，不能视作绝对安全的客户端秘密。

## 网页登录与授权

当前仓库使用 Spring Security、Spring Session JDBC 和 PostgreSQL。网页认证采用服务端 Session、HttpOnly Cookie、可配置 Secure/SameSite Cookie，并通过 `XSRF-TOKEN` Cookie + `X-XSRF-TOKEN` 请求头启用 SPA CSRF 防护；生产应设置 `APM_SESSION_COOKIE_SECURE=true` 并通过同源网关部署。OIDC、开放注册和找回密码尚未实现。

建议角色：

```text
Owner → Admin → Developer → Viewer
```

每次访问应用资源都必须在服务端执行：

```text
当前用户 → 是否属于目标应用 → 当前角色 → 是否有资源操作权限
```

应用列表、应用详情、应用修改和 Crash 查询均按该链路执行。不能把前端路由、`X-App-Id`、`X-User-App-Ids` 或 Grafana 变量当作身份/成员证明。多服务、第三方登录或开放 API 成为明确需求后，再引入 OIDC/JWT。

## 默认禁止采集

- 完整 URL 查询参数。
- Cookie、Authorization 等敏感请求头。
- 请求体和响应体。
- 用户输入内容。
- 手机号、邮箱和明文用户 ID。
- 可直接识别个人的设备标识。

## 脱敏与最小化原则

- URL 转为 `/users/{id}` 等路径模板。
- 用户与设备标识使用按应用加盐的哈希。
- 对属性名和字段名使用白名单。
- mapping 文件、符号表和堆栈信息实施访问控制。
- 日志不得输出完整上报 Key 或完整事件体。
- 明确原始数据与聚合数据的保留、删除和归档策略。
- 只采集能回答产品、排障或合规问题的数据。

## 多租户注意事项

- PostgreSQL 的所有业务资源必须关联租户或应用边界。
- ClickHouse 查询必须强制注入并校验应用范围。
- Grafana 对外使用时需采用真实的数据隔离能力，而不是仅隐藏变量。
- 越权测试必须包含 `appId` 枚举和跨应用事件详情访问。

## JVM Crash 脱敏与访问实现状态

当前查询 API 已使用登录主体和 PostgreSQL `app_member` 成员关系授权：所有角色可读取，只有 `OWNER`/`ADMIN` 可修改应用名称和描述，`DEVELOPER`/`VIEWER` 修改返回 403，无成员关系按 404 返回。`X-App-Id` 和 `X-User-App-Ids` 被忽略，不能伪造跨应用访问。Android 上报仍使用独立的 `X-App-Key`，不会把网页 Session 带入上报端。

前端只调用 Spring Boot 管理/查询 API，不接触 ClickHouse URL、用户名或密码。前端通过同源 Cookie 携带 Session，状态变更请求附加 CSRF Token；收到 401 时清理用户和应用状态并回到登录页。浏览器代码、存储和日志不得保存密码、Session 标识、CSRF Token 或 Android App Key。

## 卡顿载荷的安全边界

卡顿场景、堆栈类名/方法名和属性沿用服务端长度、白名单、规范化和哈希边界；场景、采样数、字典规模、堆栈深度、总帧数、单事件和请求解压体积均有配置上限。`anonymousDeviceId` 仍按应用盐哈希后存储，详情 API 不还原客户端设备标识；指纹只使用规范化关键路径和稳定上下文，不把客户端指纹作为授权或身份事实。日志只保留事件 ID、错误类别和计数，不输出完整卡顿载荷、堆栈或设备标识。

## 二进制堆栈产物的安全边界

完整 App Key 只由 `OWNER`/`ADMIN` 通过禁止缓存接口按需读取；普通应用响应和鉴权投影不包含密文、摘要或 nonce。前端只在应用设置组件局部内存短暂持有 Key，并在应用切换、请求失败、会话失效和组件卸载时清空。Key 永久有效且当前不可轮换或撤销，因此不能被描述为可快速处置的强客户端秘密；更强身份需要另行引入签名证明或 Play Integrity。
