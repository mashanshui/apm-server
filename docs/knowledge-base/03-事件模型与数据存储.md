# 事件模型与数据存储

## 三类存储的职责

| 存储 | 保存内容 | 数据特征 |
|---|---|---|
| PostgreSQL | 当前已实现的用户、应用、应用成员、App Key 凭据和 Spring Session；版本、环境、渠道、告警规则、制品元数据仍是后续模型 | 已通过 Flyway 创建最小管理 schema；JPA 运行时只做 schema 校验 |
| ClickHouse | 当前的 `app_start`、JVM Crash 原始事件、Crash 明细和聚合对象 | 已接入 HTTP JSONEachRow；高体量、追加写、时间范围和多维聚合 |
| S3 / MinIO | R8 `mapping.txt`、NDK 符号表、大附件与归档 | 目标架构；当前二进制解析只读取运维预置的本地应用 mapping 目录，不使用对象存储，也不保存上传产物 |

## 公共事件信封

每条事件至少包含身份、时间、版本、设备环境、测量值和属性：

```json
{
  "schemaVersion": 2,
  "eventId": "全局唯一ID",
  "eventType": "app_start",
  "occurredAt": 1786675200000,
  "sessionId": "会话ID",
  "processId": "进程实例 UUID v4",
  "anonymousDeviceId": "匿名设备ID",
  "packageName": "com.example.app",
  "appVersion": "3.2.0",
  "versionCode": 320,
  "buildId": "构建ID",
  "environment": "production",
  "channel": "official",
  "osVersion": "16",
  "deviceModel": "设备型号",
  "networkType": "wifi",
  "measurements": { "durationMs": 823.4 },
  "attributes": { "startType": "cold" }
}
```

## 进程实例身份边界

客户端身份按三个不同生命周期维护：`anonymousDeviceId` 是安装级 UUID v4，首次生成后持久化并由各进程共用；`sessionId` 是每次应用启动生成的 UUID v4；主进程的 `processId` 等于本次启动 ID，子进程每次创建都生成独立 UUID v4。`processId` 不是 Android 数值 PID，也不能使用进程名称代替。

JSON 批量事件、卡顿 ZIP manifest 和内存泄漏报告 metadata 都必须携带标准连字符形式的 UUID v4 `processId`。服务端只校验、传递并保存客户端提供的进程实例值，不在缺失时随机生成、不从当前上传连接推断，也不在重试时替换；事件入队时应冻结三个身份字段。`processId` 原值保留大小写，`anonymousDeviceId` 继续按现有应用盐哈希后保存。

主进程出现 `processId == sessionId` 是客户端生命周期约定，不是服务端拒绝条件；子进程的跨进程启动归属协调不在本版范围内。本版不新增身份关联查询、身份索引或跳转路由。内存泄漏报告的 `sessionId` 继续可选，缺失时返回缺失值；其他现有入口的 `sessionId` 必填规则不变。

## 内存采样事件

`eventType=memory_sample` 使用同一公共信封，并且只携带 `memorySample` 专用载荷。载荷包含 `processName`、`foreground` 和可选 `scene`；其中 `scene` 固定表示采样时当前应用的 Activity 名称。PSS、VSS、Java 堆分别使用 `pssBytes`、`vssBytes`、`javaHeapUsedBytes` 字段。至少一项指标非 null；零合法；缺失或 null 不参与对应指标统计。三项值都是采样时刻的字节整数，最大值为 `9007199254740991`，以保证 JavaScript 安全整数范围。

服务端新增 `apm_memory_sample` ClickHouse 表，Nullable 数值列保留缺失信息，按 `event_time` 月份分区，以 `(app_id,event_id)` 排序并使用 `ReplacingMergeTree(received_time)`。内存查询使用 `FINAL`，按采样时间而不是接收时间过滤。具体列和迁移脚本见[后端持久化与数据库迁移](../../backend/docs/knowledge-base/03-持久化与数据库迁移.md)和[内存指标 API](../api/memory-metrics-api.md)。

## 内存异常报告

内存异常报告使用独立的 `POST /ingest/v1/memory-reports` multipart 接口，`metadata` JSON part 承载事件参数，必填的 `report` JSON 文件保存受限 SDK `hprof.json` 原文到 `report_json`，规范化的 `gcPaths` 保存到 `gc_paths_json`，并写入新增的 `apm_memory_report`。报告事实按 `(app_id,event_id)` 使用 `ReplacingMergeTree(received_time)` 去重；问题查询按 `(eventId,signature)` 计一次，不把 `instanceCount` 或 `leakObjects.size` 当作泄漏字节。可选 HPROF 只落到受限本地目录并保存 SHA-256 摘要，不进入 ClickHouse，也不触发解析任务。表和适配器细节见[后端持久化与数据库迁移](../../backend/docs/knowledge-base/03-持久化与数据库迁移.md)。

## 分区、排序与保留

- 按月分区：`PARTITION BY toYYYYMM(event_time)`。
- 排序键优先覆盖 `app_id`、`event_type`、`event_time`。
- 原始数据 TTL 建议范围为 7 至 90 天，最终值需结合事件量和预算确认。
- 小时和天级聚合可保留一年或更久。
- 目标架构中 Dashboard 应默认查聚合表，仅在详情下钻时查原始表。
- 当前 Grafana JSON 直接查询 `apm_event_raw FINAL`；Crash 查询服务仍读取仓库中的原始事件后在 JVM 内计算，因此 Crash 小时聚合表和物化视图目前主要是存储基础设施，尚未成为 Crash 查询路径。卡顿 FPS/挂起率查询使用独立的指标仓库和 ClickHouse 聚合 SQL。

典型聚合键与指标：

```text
app_id + event_type + app_version + channel + hour
  → count
  → avg
  → p50 / p90 / p95 / p99
  → error_count
  → affected_device_count
```

## 写入与重复数据

- Android 和服务端都使用批处理，避免逐条写入 ClickHouse。
- 可启用 ClickHouse 异步插入以合并并发小批次。
- 第一版在 ClickHouse 确认写入后再响应成功。
- 整体语义为“至少一次”，网络重试可能重复到达；当前内存仓库用 `putIfAbsent`，ClickHouse 适配器先查询已有 `eventId` 再写入新事件。
- ClickHouse 原始表和明细表使用 `ReplacingMergeTree(received_time)`，查询使用 `FINAL`；写入原始表和 Crash 明细表不是跨表事务，真实故障恢复仍需压测和演练。
- 不为绝对去重引入跨系统全局事务。

## 从问题反推字段

事件字段必须服务于明确的查询问题。例如回答“新版本冷启动是否退化”至少需要：

```text
app_id, app_version, version_code, event_time, start_type,
duration_ms, device_model, os_version, channel, anonymous_device_id
```

若字段没有查询、聚合、排障、合规或运营用途，不应仅因“以后可能有用”而采集。
