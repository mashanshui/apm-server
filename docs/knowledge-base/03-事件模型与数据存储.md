# 事件模型与数据存储

## 三类存储的职责

| 存储 | 保存内容 | 数据特征 |
|---|---|---|
| PostgreSQL | 当前已实现的用户、应用、应用成员、App Key 凭据和 Spring Session；版本、环境、渠道、告警规则、制品元数据仍是后续模型 | 已通过 Flyway 创建最小管理 schema；JPA 运行时只做 schema 校验 |
| ClickHouse | 当前的 `app_start`、JVM Crash 原始事件、Crash 明细和聚合对象 | 已接入 HTTP JSONEachRow；高体量、追加写、时间范围和多维聚合 |
| S3 / MinIO | R8 `mapping.txt`、NDK 符号表、大附件与归档 | 目标架构；当前二进制解析只读取运维预置的本地应用 mapping 目录，不使用对象存储，也不保存上传产物 |

## 公共事件信封

每条事件至少包含身份、时间、版本、设备环境、测量值和属性：

```json
{
  "schemaVersion": 2,
  "eventId": "全局唯一ID",
  "eventType": "app_start",
  "occurredAt": 1786675200000,
  "sessionId": "会话ID",
  "anonymousDeviceId": "匿名设备ID",
  "packageName": "com.example.app",
  "appVersion": "3.2.0",
  "versionCode": 320,
  "buildId": "构建ID",
  "environment": "production",
  "channel": "official",
  "osVersion": "16",
  "deviceModel": "设备型号",
  "networkType": "wifi",
  "measurements": { "durationMs": 823.4 },
  "attributes": { "startType": "cold" }
}
```

## ClickHouse 原始事件表草案

```text
apm_event_raw
├─ app_id                 # 系统生成的 UUID 应用隔离标识
├─ package_name          # Android application ID
├─ event_id
├─ event_type
├─ event_time
├─ received_time
├─ schema_version
├─ app_version
├─ version_code
├─ build_id
├─ channel
├─ environment
├─ session_id
├─ anonymous_device_id
├─ os_version
├─ device_model
├─ network_type
├─ duration_ms
├─ status
├─ measurements Map(String, Float64)
├─ attributes   Map(String, String)
├─ crash_kind / crash_fatal
├─ crash_exception_type / crash_fingerprint
├─ fingerprint_version
└─ symbolication_status
```

### 建模规则

- 高频筛选或聚合字段使用明确的强类型列。
- 不稳定、低频属性放入 `Map` 或 JSON。
- 不将整个事件塞入单一 JSON 字符串。
- 第一版使用统一原始表；热点事件类型稳定后再建立专用事实表或物化视图。
- `eventId` 用于识别重复事件，`schemaVersion` 用于协议演进。

## 分区、排序与保留

- 按月分区：`PARTITION BY toYYYYMM(event_time)`。
- 排序键优先覆盖 `app_id`、`event_type`、`event_time`。
- 原始数据 TTL 建议范围为 7 至 90 天，最终值需结合事件量和预算确认。
- 小时和天级聚合可保留一年或更久。
- 目标架构中 Dashboard 应默认查聚合表，仅在详情下钻时查原始表。
- 当前 Grafana JSON 直接查询 `apm_event_raw FINAL`；Crash 查询服务仍读取仓库中的原始事件后在 JVM 内计算，因此 Crash 小时聚合表和物化视图目前主要是存储基础设施，尚未成为 Crash 查询路径。卡顿 FPS/挂起率查询使用独立的指标仓库和 ClickHouse 聚合 SQL。

典型聚合键与指标：

```text
app_id + event_type + app_version + channel + hour
  → count
  → avg
  → p50 / p90 / p95 / p99
  → error_count
  → affected_device_count
```

## 写入与重复数据

- Android 和服务端都使用批处理，避免逐条写入 ClickHouse。
- 可启用 ClickHouse 异步插入以合并并发小批次。
- 第一版在 ClickHouse 确认写入后再响应成功。
- 整体语义为“至少一次”，网络重试可能重复到达；当前内存仓库用 `putIfAbsent`，ClickHouse 适配器先查询已有 `eventId` 再写入新事件。
- ClickHouse 原始表和明细表使用 `ReplacingMergeTree(received_time)`，查询使用 `FINAL`；写入原始表和 Crash 明细表不是跨表事务，真实故障恢复仍需压测和演练。
- 不为绝对去重引入跨系统全局事务。

## 从问题反推字段

事件字段必须服务于明确的查询问题。例如回答“新版本冷启动是否退化”至少需要：

```text
app_id, app_version, version_code, event_time, start_type,
duration_ms, device_model, os_version, channel, anonymous_device_id
```

若字段没有查询、聚合、排障、合规或运营用途，不应仅因“以后可能有用”而采集。

## 卡顿事件与存储实现

卡顿个例的正式输入是 v3 `.rheajank.zip`，服务端将其解析为内部 `eventType=jank` 事实。`messageDurationNs` 是 manifest 消息边界之差；`samples[].offsetNs` 与调用树来自 `processId` 对应主线程证据；`stackDictionary` 使用稳定 stackId 去重完整帧列表。当前证据算法标识仍为 `jank-artifact-v2`，指纹版本仍为 `jank-v1`；这两个算法版本不等于 manifest 版本。采样质量只保存服务端派生的 `expectedSampleCount`、`parsedSampleCount` 和 `missingSampleCount`，不保存客户端 `attemptedSampleCount`。processor 1.0.1 已用真实 v3 fixture 验证 `sourceManifest` 版本、包名、主线程 segments、调用树和报告可解析性；本地真实服务已继续验证 HTTP 首次/重复、应用级 mapping、错误 Key/包名、v2 拒绝和重启。

`002_jank_schema.sql` 创建卡顿事实、详情和指标对象；`003_jank_sampling_quality.sql` 向 `apm_jank_event` 新增 `parsed_sample_count` 与 `missing_sample_count`。旧 attempted/successful/dropped 物理列仅为已部署环境回滚保留，新代码不读写。卡顿事实和详情使用 `ReplacingMergeTree(received_time)`，重复上传可补齐原始事实、卡顿事实或详情，不生成新的事件身份。

场景帧汇总和前台挂起汇总的载荷、Schema、校验和专用表已冻结。`JankMetricsQueryService` 已提供 FPS 与设备日挂起率汇总、多维和统一时间桶趋势：内存实现用于固定数据集，ClickHouse 实现使用 `FINAL` 和受限聚合 SQL；FPS 按算法版本隔离、支持 UTC 小时/天并按高到低计算分位数，挂起率先按 `app_id`/匿名设备/UTC 日期/稳定维度合并再按 UTC 天计算。固定数据集的 ClickHouse 结果必须在 004 结构上重新验收，生产容量、并发 p95/p99 和故障恢复仍待验证。

`.rheajank.zip` 是卡顿个例的正式输入：服务端验证 App Key、请求体、ZIP、v3 manifest、哈希和 Sampling 后，通过 `parseWithMappingResolver` 解析一次，将必要事实和证据写入 `apm_event_raw`、`apm_jank_event` 与 `apm_jank_detail`。原始 ZIP 和完整 processor 报告不保存。服务端在 mapping、指纹、归一化和写入前校验 manifest `packageName`；真实 v3 processor 解析门禁以及本地 HTTP 首次接受、重复、mapping 和重启验证均已通过，生产容量与 Android 端仍需单独验收。

## JVM Crash 事件与存储实现

Crash 事件使用 eventType=crash、crash.kind=jvm、crash.fatal=true，并在 throwableChain 中保存异常类型、脱敏消息和结构化堆栈帧。服务端抽取 crash_exception_type、crash_fingerprint、fingerprint_version 和 symbolication_status 等强类型查询列；较大的异常链写入 apm_crash_detail。

ClickHouse 初始化脚本位于 `src/main/resources/db/clickhouse/001_crash_schema.sql`，原始表和 Crash 明细表按事件月分区、TTL 示例为 30 天；小时聚合和 Crash 问题聚合按月分区、TTL 示例为 365 天。重复初始化使用 `IF NOT EXISTS`；保留期限仍需结合容量确认。

当前默认实现是 ClickHouse 持久化。无业务语义的 `ClickHouseHttpClient` 负责 HTTP、认证、超时和 JSONEachRow 基础能力；Crash 的原始事件、明细和查询映射由 `ClickHouseCrashRepository` 负责，卡顿事实/详情、Issue 查询和指标分别由 `ClickHouseJankEventRepository`、`ClickHouseJankAggregationRepository`、`ClickHouseJankMetricsRepository` 负责。各适配器直接实现所属领域端口，不共享联合事件仓储。内存适配器用于固定数据集或无外部依赖联调，可通过 `APM_STORAGE_MODE=memory` 显式启用；真实大数据量的聚合查询、容量和故障恢复仍不能由内存测试推断。

PostgreSQL `app_ingest_credential` 与 `apm_app` 一对一并级联删除，字段为 `app_id`、32 字节 Key 摘要、AES-GCM 密文、12 字节 nonce 和创建时间。不可变 `packageName` 只保存在 `apm_app`，全平台唯一；每个应用必须恰有一个凭据。该表不保存明文 Key，ClickHouse 事件表也不保存 Key。
