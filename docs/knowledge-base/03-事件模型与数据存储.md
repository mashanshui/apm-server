# 事件模型与数据存储

## 当前与目标存储职责

| 存储 | 保存内容 | 数据特征 |
|---|---|---|
| PostgreSQL | 用户、应用、成员、App Key 凭据、Spring Session、符号表当前版本/替换审计和查询 Token；独立版本、环境、渠道与告警规则模型仍未实现 | 已通过 Flyway 创建最小管理 schema；JPA 运行时只做 schema 校验 |
| ClickHouse | `app_start`、Crash/卡顿事实与详情、FPS/挂起汇总、内存采样和 SDK 内存异常报告，以及已有聚合对象 | 已接入 HTTP JSONEachRow；高体量、追加写、时间范围和多维聚合 |
| 本地持久卷 | 当前 mapping 文件和可选 HPROF 附件 | 文件受应用授权、路径和大小约束；HPROF 仅保存和定时清理，不解析、不提供下载 |
| S3 / MinIO | 目标中的 mapping、NDK 符号表、大附件与归档 | 尚未接入；NDK 符号表和长期归档仍未实现 |

## 公共事件信封

公共事件包含身份、时间、版本和设备环境，各事件再携带对应测量值或专用载荷。下例是单条 `app_start` 结构示意，时间需在上传时替换为实际发生时间（服务端默认只接受最近 7 天至未来 15 分钟）：

```json
{
  "schemaVersion": 2,
  "eventId": "全局唯一ID",
  "eventType": "app_start",
  "occurredAt": 1786675200000,
  "sessionId": "会话ID",
  "processId": "11111111-1111-4111-8111-111111111111",
  "anonymousDeviceId": "匿名设备ID",
  "packageName": "com.example.app",
  "appVersion": "3.2.0",
  "versionCode": 320,
  "buildId": "构建ID",
  "environment": "production",
  "channel": "official",
  "osVersion": "16",
  "deviceModel": "设备型号",
  "networkType": "wifi",
  "measurements": { "durationMs": 823.4 },
  "attributes": { "startType": "cold" }
}
```

## 进程实例身份边界

客户端身份按三个不同生命周期维护：`anonymousDeviceId` 是安装级 UUID v4，首次生成后持久化并由各进程共用；`sessionId` 是每次应用启动生成的 UUID v4；主进程的 `processId` 等于本次启动 ID，子进程每次创建都生成独立 UUID v4。`processId` 不是 Android 数值 PID，也不能使用进程名称代替。

JSON 批量事件、卡顿 ZIP manifest 和内存泄漏报告 metadata 都必须携带标准连字符形式的 UUID v4 `processId`。服务端只校验、传递并保存客户端提供的进程实例值，不在缺失时随机生成、不从当前上传连接推断，也不在重试时替换；事件入队时应冻结三个身份字段。`processId` 原值保留大小写，Crash、卡顿和内存采样的 `anonymousDeviceId` 使用现有部署级盐哈希后保存；内存异常报告保留 metadata 原值，不能泛化为相同脱敏行为。

主进程出现 `processId == sessionId` 是客户端生命周期约定，不是服务端拒绝条件；子进程的跨进程启动归属协调不在本版范围内。本版不新增身份关联查询、身份索引或跳转路由。内存泄漏报告的 `sessionId` 继续可选，缺失时返回缺失值；其他现有入口的 `sessionId` 必填规则不变。

## 内存采样事件

`eventType=memory_sample` 使用同一公共信封，并且只携带 `memorySample` 专用载荷。载荷包含 `processName`、`foreground` 和可选 `scene`；其中 `scene` 固定表示采样时当前应用的 Activity 名称。PSS、VSS、Java 堆分别使用 `pssBytes`、`vssBytes`、`javaHeapUsedBytes` 字段。至少一项指标非 null；零合法；缺失或 null 不参与对应指标统计。三项值都是采样时刻的字节整数，最大值为 `9007199254740991`，以保证 JavaScript 安全整数范围。

服务端新增 `apm_memory_sample` ClickHouse 表，Nullable 数值列保留缺失信息，按 `event_time` 月份分区，以 `(app_id,event_id)` 排序并使用 `ReplacingMergeTree(received_time)`。内存查询使用 `FINAL`，按采样时间而不是接收时间过滤。具体列和迁移脚本见[后端持久化与数据库迁移](../../backend/docs/knowledge-base/03-持久化与数据库迁移.md)和[内存指标 API](../api/memory-metrics-api.md)。

## 内存异常报告

内存异常报告使用独立的 `POST /ingest/v1/memory-reports` multipart 接口，`metadata` JSON part 承载事件参数，必填的 `report` JSON 文件保存受限 SDK `hprof.json` 原文到 `report_json`，规范化的 `gcPaths` 保存到 `gc_paths_json`，并写入新增的 `apm_memory_report`。报告表按 `sipHash64(app_id,event_id) % 32` 哈希分区，事实按 `(app_id,event_id)` 使用 `ReplacingMergeTree(received_time)` 去重；问题查询按 `(eventId,signature)` 计一次，不把 `instanceCount` 或 `leakObjects.size` 当作泄漏字节。可选 HPROF 只落到受限本地目录并保存 SHA-256 摘要，不进入 ClickHouse，也不触发解析任务。表和适配器细节见[后端持久化与数据库迁移](../../backend/docs/knowledge-base/03-持久化与数据库迁移.md)。

## 分区、排序与保留

- Crash/卡顿原始事实、详情及内存采样按事件月分区；内存报告按应用和事件 ID 哈希分区，设备日汇总按 UTC 日期月份分区。
- 排序键由各表查询和去重用途决定；内存采样/报告使用 `(app_id,event_id)`，并非所有表都包含 `event_type`、`event_time`。
- 当前 SQL 的 Crash/卡顿原始事实和详情 TTL 为 30 天，指标汇总、内存采样/报告为 90 天，小时/设备日聚合为 365 天；生产保留期限仍需容量与预算确认。
- 目标架构中 Dashboard 应默认查聚合表，仅在详情下钻时查原始表。
- 当前 Grafana JSON 直接查询 `apm_event_raw FINAL`；Crash API 已在 ClickHouse 内过滤、按逻辑事件去重、聚合排序和分页，小时聚合表仍未接入。卡顿 FPS/挂起率及内存采样使用领域聚合 SQL；内存异常报告在数据库筛选后读取报告，由 Java 聚合和分页，生产规模下的扫描/结果上限仍需补齐，见[待确认事项](13-待确认事项.md)。

典型聚合键与指标：

```text
app_id + event_type + app_version + channel + hour
  → count
  → avg
  → p50 / p90 / p95 / p99
  → error_count
  → affected_device_count
```

## 写入与重复数据

- Android 和服务端都使用批处理，避免逐条写入 ClickHouse。
- 当前采用同步写入确认，没有启用异步插入；后续若采用异步插入，需要保持写入完成后才确认的可靠性边界。
- 第一版在 ClickHouse 确认写入后再响应成功。
- 整体语义为“至少一次”，网络重试可能重复到达；当前内存仓库用 `putIfAbsent`，ClickHouse 适配器先查询已有 `eventId` 再写入新事件。
- ClickHouse 原始表和明细表使用 `ReplacingMergeTree(received_time)`，查询使用 `FINAL`；写入原始表和 Crash 明细表不是跨表事务，真实故障恢复仍需压测和演练。
- 不为绝对去重引入跨系统全局事务。

## 从问题反推字段

事件字段必须服务于明确的查询问题。例如回答“新版本冷启动是否退化”至少需要：

```text
app_id, app_version, version_code, event_time, start_type,
duration_ms, device_model, os_version, channel, anonymous_device_id
```

若字段没有查询、聚合、排障、合规或运营用途，不应仅因“以后可能有用”而采集。
