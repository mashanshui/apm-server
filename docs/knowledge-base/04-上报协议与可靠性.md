# 上报协议与可靠性

## 目标端到端数据流

1. Android 在本地队列积累一个事件批次。
2. 使用 gzip 压缩，通过 HTTPS 上传。
3. 接入层限制请求大小并进行限流。
4. 服务端检查应用鉴权、Schema 版本、事件时间和字段合法性。
5. 服务端对 URL、用户标识、设备标识等内容脱敏和标准化。
6. 服务端批量写入 ClickHouse。
7. 写入确认后返回成功；失败时明确是否可重试。
8. Android 对可重试错误执行指数退避并加入随机抖动。

## 当前事件与卡顿服务端链路

当前 JSON 批次与卡顿 ZIP 都采用同步确认链路，平台不包含 Kafka 或通用限流器。详见[后端知识库](../../backend/docs/knowledge-base/02-接收解析与查询链路.md)。

`anonymousDeviceId`、`sessionId` 和 `processId` 必须在事件产生时冻结：设备 ID 是安装级 UUID v4，启动 ID 是每次启动生成的 UUID v4，进程 ID 是进程实例 UUID v4。主进程可以令 `processId=sessionId`，子进程每次创建必须生成新的进程 UUID；服务端不使用 Android 数值 PID、不补造缺失值，也不在重试时替换身份。

## 上报接口（当前实现）

```http
POST /ingest/v1/batches
Content-Type: application/json
Content-Encoding: gzip
X-App-Key: 应用永久上报凭据
X-Schema-Version: 2
```

```json
{
  "requestId": "请求ID",
  "accepted": 500,
  "rejected": 2,
  "retryable": false,
  "retryAfterSeconds": null
}
```

当前批量入口只接受 `application/json`，`Content-Encoding` 可省略、使用 `identity` 或 `gzip`；`frame_scene_summary` 和 `foreground_suspension_summary` 与 Crash/启动事件共用部分接受响应。`eventType=jank` 返回不可重试的 `JANK_ARTIFACT_REQUIRED`。Protobuf、`X-SDK-Version` 和通用限流器尚未实现。

## 内存指标上传格式和策略

内存采样继续进入 `/ingest/v1/batches`，不新增上传路由。事件的公共信封与 `memorySample` 示例、字段范围和错误语义见[内存指标 API](../api/memory-metrics-api.md)；`scene` 使用采样时当前应用的 Activity 名称。Android 采集、队列和重试步骤见[内存指标上传接入](../client-integration/memory-metrics.md)。服务端只接收原始单次采样，不接收客户端平均值、分位数或跨进程求和结果。

客户端应在本地持久化完整事件和三个身份字段后再加入批次，使用稳定的 `eventId`；批次成功响应后删除 `accepted` 和 `duplicate` 事件，事件级永久错误不重试。网络中断、HTTP 503/超时等不确定或临时失败保留原事件和原身份，按 `Retry-After` 或指数退避加随机抖动重试。服务端以 `appId+eventId` 去重，因此重试不得生成新 ID 或改用上传时的新身份；存储失败返回可重试 503，不能被客户端当作无数据成功。

## 内存异常报告上传格式和策略

异常报告使用独立的 `/ingest/v1/memory-reports` multipart 接口，必填 `metadata` JSON part 和 `report` JSON 文件 part，可选 `hprof` 文件 part；metadata 的 `processId` 必须是 UUID v4，原有可选 `sessionId` 继续可选；不再支持 JSON-only。服务端以 `appId+eventId`、metadata+report 规范摘要和 HPROF SHA-256 实现重试幂等；相同内容返回 `duplicate`，修改内容返回 409。metadata、report、附件、深度、数组和引用链均按配置限制，未知 metadata 字段拒绝，未知 report 内部字段保留。HPROF 保存失败返回可重试 503，仅上传 metadata/report 不依赖附件目录；默认附件保留 7 天并由后台清理。客户端步骤见[内存泄漏报告上传接入](../client-integration/memory-leak-reports.md)，正式字段见[内存泄漏报告 API](../api/memory-leak-reports-api.md)。

## 卡顿压缩包解析落库接口（当前实现）

```http
POST /ingest/v1/stack-artifacts:parse
Content-Type: application/vnd.shanshui.rheajank+zip
X-App-Key: 应用永久上报凭据

<原始 .rheajank.zip 字节>
```

该入口不使用 JSON、Base64、外层 gzip 或 multipart。服务端先鉴权和检查媒体类型/`Content-Length`，再通过默认 64 MiB 的受限流读取；当前服务端还要求 manifest `processId` 为 UUID v4。processor `1.0.2` 已用客户端实际设备 ZIP 完成主线程-only UUID v4 解析，并完成云端 HTTP 首次写入、同字节重复和详情回传；生产受控制品仓库、容量与长期故障恢复仍是外部验收项。同步解析默认并发 2，满载返回 `Retry-After: 1` 的可重试 503；服务端按 manifest `buildId` 选择可选应用 mapping，归一化并幂等落库。详见[卡顿压缩包解析与落库 API](../api/stack-artifact-api.md)。

## 协议演进策略

- 调试期先用 JSON + gzip，降低联调成本。
- 稳定后使用 Protobuf + gzip，减少体积并加强类型约束。
- 同时限制压缩前的 HTTP 请求大小和解压后的内容大小，防止压缩炸弹。
- 每条事件带 `schemaVersion`；服务端明确支持的版本范围。
- 永久错误与临时错误必须有稳定的响应语义。
- 对可重试错误返回 `Retry-After` 或 `retryAfterSeconds`。
- 字段命名尽量参考 OpenTelemetry，但 Android 专有事件第一版继续使用自有信封。

## 建议的错误分类

| 情况 | 是否重试 | 处理原则 |
|---|---|---|
| App Key 无效或应用不可用 | 否 | 拒绝整个批次，避免无意义重试 |
| Schema 版本不支持 | 否 | 返回稳定错误码，指导 SDK 升级或降级 |
| 字段缺失、类型非法（包括 `processId` 缺失或非 UUID v4） | 否 | 可按策略拒绝单条或整个批次，并返回数量 |
| 请求或解压内容过大 | 否 | SDK 减小批次 |
| 服务端限流 | 是 | 按 `Retry-After` 延迟 |
| ClickHouse 超时或暂时不可用 | 是 | 保留本地队列并退避重试 |
| 网络中断 | 是 | 使用原 `eventId` 重试，接受至少一次语义 |

当前 HTTP 语义已经由代码固定：无效 App Key 返回 401，JSON/gzip 或批次结构错误返回 400，未知媒体类型返回 415，大小超限返回 413，事件存储不可用返回 503 并附带 `Retry-After: 30`。二进制堆栈产物错误返回 422，解析并发满返回可重试 503 和 `Retry-After: 1`。事件级校验错误在批次响应中以 HTTP 200 部分接受返回；请求头中的不支持 Schema 版本则返回 400。429 通用限流响应仍未实现，不能按已上线能力对外承诺。

## 为什么第一版直接写 ClickHouse

直接写入组件少、链路短，最容易定位丢数和校验问题。只有 ClickHouse 成功写入才响应成功；数据库短时失败由 Android 本地队列承担重试。

## 引入 Kafka 的触发条件

- ClickHouse 不可用时仍必须持续接收数据。
- 峰值上报超过数据库实时写入能力。
- 同一事件需要供存储、告警、异常检测、导出等多个消费者处理。
- 需要回放历史数据重新计算。
- 接收与处理必须完全解耦。

在这些条件出现前，Kafka 的 Topic、Partition、Offset、消费者组与积压监控会增加不必要的系统成本。

## JVM Crash 协议实现

首期调试协议已经实现 JSON 和 JSON+gzip 批量上报，Protobuf 仍属于后续兼容项。服务端默认限制压缩前请求 1 MiB、解压后请求 4 MiB、单事件 256 KiB、异常消息 4096 字符、异常链 16 个节点、总堆栈帧 200 帧，并限制事件时间为最近 7 天至未来 15 分钟。永久错误按事件部分接受返回，事件存储不可用返回可重试的 503 和 `Retry-After`。

Crash Handler 的客户端联调样例位于 docs/examples/AndroidCrashHandler.kt。样例要求先同步持久化，再发送；临时错误保留原 eventId 重试，永久错误确认删除。实际 Android SDK 仍需将样例队列替换为文件原子写入实现并进行设备级灰度。

卡顿客户端上传字段、单位、Schema、大小限制、批量和重试流程见[Android 卡顿监控上传接入](../client-integration/jank-monitoring.md)；服务端查询和统计口径见[卡顿监控服务端 API](../api/jank-server-api.md)。客户端采集实现仍不在本仓库，`occurredAt` 的 UTC 墙上时间与卡顿样本的相对单调时间不能混用；服务端不接受跨设备单调时钟比较。

btrace 卡顿产物的原始请求体、客户端队列、幂等和重试边界见[Android 卡顿压缩包上传接入](../client-integration/stack-artifact-upload.md)。该入口已经替代结构化 `jank` JSON；指标汇总仍走 JSON 批量入口。
