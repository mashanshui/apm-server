# 构建测试与本地发布

[返回导航](README.md)

本页维护 Android 构建、测试和本地发布方法，以及最近完整主机基线和可复用的专项证据。跨端能力、联合验收及本地/云端部署结论统一见[平台状态](../../../docs/knowledge-base/00-当前实现与验证边界.md)；协议联调步骤见[接入文档](../../../docs/client-integration/README.md)。普通任务的构建输出和逐轮计数由 Git、OpenSpec 归档或 CI 追溯，不再在本页累积。

## 当前工程入口与本地签名

Android Studio 打开平台仓库的 `android/`。从平台根目录执行 `bash android/gradlew -p android ...`；进入 Android 目录后使用 `bash gradlew ...`。Android 与后端分别维护 Gradle Wrapper，不共用 settings。SDK、NDK、CMake 和兼容 JDK 按本页说明准备；Rhea/KOOM 的 Maven Local 准备条件继续生效。

App Release 和三个独立消费者通过 Gradle Providers 读取 `performance.signing.storeFile`、`performance.signing.storePassword`、`performance.signing.keyAlias`、`performance.signing.keyPassword`。显式 Gradle 属性优先，缺少的字段从未跟踪的 `android/.signing/signing.properties` 读取；该文件及证书仅保存在本机，权限限制为当前用户。示例仅使用占位值：

```properties
performance.signing.storeFile=/本机私有目录/测试证书.keystore
performance.signing.storePassword=<本机填写>
performance.signing.keyAlias=<本机填写>
performance.signing.keyPassword=<本机填写>
```

`storeFile` 必须是绝对路径。默认 App Debug 不要求 Release 配置；显式 Release 和消费者签名任务要求完整配置，缺少时明确失败，不自动换证书。迁移保持原测试证书，本地原文件保留；Git 原始历史仍含既有测试签名资产，当前文件外置不代表历史已清理。证书与凭据不进入 Git 或日志。独立消费者使用同一配置，详见[验证入口](../../verification/modular-consumer/README.md)。

## 常用命令

以下 PowerShell 命令在 `android/` 目录执行，属于操作指南。从平台根执行时使用 `bash android/gradlew -p android <任务>`；最近实际执行范围见[最近完整主机基线](#最近完整主机基线)。

~~~powershell
# 核对 Wrapper 和实际运行 JVM。
.\gradlew.bat --version

# 库 JVM 单测与示例应用构建。
.\gradlew.bat :performance-core:testDebugUnitTest :performance-transport:testDebugUnitTest :performance-crash:testDebugUnitTest :performance-jank:testDebugUnitTest :performance-metrics:testDebugUnitTest :performance-leak:testDebugUnitTest :performance-sdk:testDebugUnitTest
.\gradlew.bat :app:testDebugUnitTest :app:assembleDebug

# 按变更范围运行项目检查。
.\gradlew.bat check

# 默认构建 Release 仪器包；Debug 需显式选择测试类型。
.\gradlew.bat :app:assembleRelease :app:assembleReleaseAndroidTest
.\gradlew.bat -Pperformance.testBuildType=debug :app:assembleDebug :app:assembleDebugAndroidTest

# 仅在有明确设备验证任务和可用设备时运行。
.\gradlew.bat :app:connectedReleaseAndroidTest
~~~

构建失败先复现具体任务，再处理运行 JDK、依赖解析或模块配置。缓存写入失败时检查实际 Gradle user home 的权限；不要把切换缓存目录误当成已经准备好 Rhea Maven Local。

## App 编译期 buildId

`app/build.gradle.kts` 在 Gradle 配置阶段生成一次 `PERFORMANCE_BUILD_ID`，并通过
`BuildConfig.PERFORMANCE_BUILD_ID` 编译进 App。格式为
`versionName-versionCode-UTC时间戳-8位随机十六进制`。同一次 Gradle 命令生成的 Debug、Release
等变体共用该值，重新执行命令会生成新的值。

`App.onCreate` 将这个字段传给 `CrashConfig.buildId`。SDK 会把它作为 Crash、Jank、FPS、内存和
内存泄漏 report 的公共 buildId。Release APK、`app/build/outputs/mapping/release/mapping.txt`
和本次构建的 buildId 必须作为同一发布记录保存，服务端才能按 buildId 选择对应 mapping。

### 打包时导出 buildId

[app/build.gradle.kts](../../app/build.gradle.kts) 的 `ExportPerformanceBuildInfo.export()` 通过
`androidComponents` 监听最终 APK 产物；运行 `:app:assembleDebug`、`:app:assembleRelease`
或 Android Studio 的 APK 打包后，分别生成：

- Debug：`app/build/outputs/build-info/debug/build-info.json`。
- Release：`app/build/outputs/build-info/release/build-info.json`。

文件包含 `buildId`、`applicationId`、`variantName` 和 `outputs`；每个 APK 输出项包含
`outputFile`（APK 文件名）、`versionCode`、`versionName`。其中 `buildId` 直接复用同次配置中
注入 `BuildConfig.PERFORMANCE_BUILD_ID` 的值，版本信息通过 AGP 的 `BuiltArtifactsLoader`
读取。此文件位于独立目录，不修改 AGP 的 `output-metadata.json`，也不导出 App Key。

Release 发布时，将该 JSON、同次生成的 APK 和 `mapping.txt` 一起归档。不要重新运行 Gradle
命令来查询旧 APK 的 buildId，因为新命令会重新生成标识。当前监听对象仅为 APK，单独执行
`bundleRelease` 不会触发该导出任务；仅执行配置、同步或编译也不会生成新的 JSON。

## App Release 签名构建

`app` 的 Release 使用[本地签名配置](#当前工程入口与本地签名)指定的原测试证书；签名文件和凭据保持未跟踪，不在知识库中记录真实值。

~~~powershell
# 查看 release 变体使用的签名配置。
.\gradlew.bat :app:signingReport

# 构建已签名的 release APK。
.\gradlew.bat :app:assembleRelease
~~~

`app` 的 Release 开启 R8 代码压缩与资源收缩；各 `performance-*` 的所有构建类型关闭自身混淆。
SDK 在最终宿主 R8 中也完整保留类名、方法名和字段名，并禁止删除与优化 SDK 自身类及成员。
由于示例 App 与 SDK 共用 `com.shanshui.performance` 包，不能使用整包 keep，否则 App 也会被保留。

[根构建](../../build.gradle.kts) 的 `GenerateSdkKeepRules.generate()` 通过 AGP
`ScopedArtifact.CLASSES` 的 `PROJECT` 范围读取各变体实际编译的类，逐类生成
`-keep class <完整类名> { *; }`，包含内部类、匿名类和 Kotlin 文件门面等编译生成类。
规则输出到各模块 `build/generated/sdk-keep/<变体>/consumer-rules.pro`，与手写规则合并进入
各 AAR 根目录的 `proguard.txt`。根构建同时连接 AGP 8.13 的 `export<变体>ConsumerProguardFiles`
（源码依赖）、`merge<变体>ConsumerProguardFiles`（AAR 打包）与对应 Lint 任务的生成依赖。
源码依赖、单模块 Maven 接入和聚合 SDK 接入采用相同策略，新增 SDK 类无需手工登记。
当前 SDK 没有产品风味；以后若引入，需同步按完整变体注册规则路径，构建会主动拒绝未适配的配置。
该策略以保留完整 SDK 为目标，会增加最终包体，并限制 SDK 的 R8 优化；App 自身仍按原规则混淆。

各模块原有 `consumer-rules.pro` 继续传递 JNI、Gson 字段/泛型及第三方反射要求。
Leak AAR 额外保留 KOOM 反射读取 `MonitorConfig` 泛型所需的类型；不整包保留 Gson、OkHttp 等第三方依赖。
规则适用于正常消费 AAR/项目依赖的 Android R8 构建；手动删除规则、抽取裸字节码或其他工具再次处理制品时，需显式携带相同规则。

构建和检查混淆产物：

~~~powershell
# 检查 AAR 中的消费者规则，并使用该规则构建最终混淆 APK。
.\gradlew.bat :performance-native-tools:bundleReleaseAar :performance-sdk:bundleReleaseAar :app:assembleRelease

# Smoke test 绑定 Release APK；需要 ABI 与本库 arm64-v8a 原生实现匹配的已授权设备。
.\gradlew.bat :app:connectedAndroidTest '-Pandroid.testInstrumentationRunnerArguments.class=com.shanshui.performance.ObfuscationSmokeTest'
~~~

Release R8 mapping 位于 `app/build/outputs/mapping/release/mapping.txt`。每次发布必须将该文件与
对应的 APK 一并归档；后续构建产生的 mapping 不能用于还原旧 APK 的堆栈。发布 AAR 时，手写与
自动生成的消费者规则统一位于 AAR 根目录 `proguard.txt`，下游应用启用代码压缩后由 R8 自动合并。
示例 App 的 `app/proguard-rules.pro` 另保留 Release 仪器 runner、资源 R 类、NativeLib JNI、LooperMonitor
以及测试 APK 与宿主共用的 Kotlin/Guava 运行时 ABI；这些是演示应用的测试运行时配置，不属于 SDK AAR
消费者规则。

## Maven Local 发布

八个模块统一使用 `performance.groupId`、`performance.version` 发布，默认坐标前缀为 `com.shanshui.nativelib`，artifactId 为模块目录名。一次发布全部 Release AAR、sources JAR、POM 和 Gradle module metadata：

~~~powershell
.\gradlew.bat publishToMavenLocal -Pperformance.version=1.0.0 --no-daemon
~~~

具体 artifact 坐标和精简消费者示例以 [SDK 模块化拆分说明](15-SDK模块化拆分说明.md) 为准；旧 `nativelib` artifact 不再发布。消费者必须能够从 Maven Local 解析 Rhea、KOOM 和其他传递依赖。

消费者的依赖范围、APK/Manifest 和受控 Native 恢复检查见[独立消费者说明](../../verification/modular-consumer/README.md)。Native 采集库与独立 dumper 支持的 ABI、16 KiB 对齐及设备执行范围见[Native 验证](../../../docs/validation/native-crash/README.md)；旧版本 Crash-only 不包含原生库的结论不能用于当前版本。
