# Crash 后台符号还原规范

## Purpose

让当前事件模型中的 JVM 致命崩溃在接收成功后通过独立且可恢复的后台流程完成符号还原，将缺少符号表、处理失败与已完成状态明确持久化；保障待处理事件补还原、符号表更换和失败重试期间的事件身份、统计结果及首次成功堆栈保持一致，不承担旧版本数据或业务链路适配。

## Requirements

### Requirement: 仅处理当前事件模型
系统 MUST 只读写当前 Crash 事实和状态结构，保留 pending、failed、symbolicated 三态；JVM 使用原始链或完整还原文本，Native 使用保留现场及逐单元结果的 native_stack。旧 raw_only 数据、旧详情表或旧字段 MUST NOT 被后台自动扫描、转换、双写或作为新模型缺失时的回退来源。新结构缺失或当前记录非法 MUST 明确失败，不通过旧逻辑兜底。旧存储数据 MUST NOT 因拒绝兼容而被默认启动或任务执行隐式清空。

#### Scenario: 旧存储存在待还原记录
- **WHEN** 旧 Crash 表中仍有 raw_only 数据，而当前结构中有 pending 事件
- **THEN** 后台只处理当前事件，不导入旧数据，不把旧事件或旧会话混入新统计，也不删除旧存储

#### Scenario: 当前结构或状态不合法
- **WHEN** 缺少新结构，或当前记录使用不支持的状态/载荷格式
- **THEN** 明确报告初始化或处理错误，不回退读取旧表，不把未知状态默认为 pending

### Requirement: 接收与后台还原分离
系统 MUST 对所有合法 JVM/Native fatal Crash 先完成脱敏原始异常链或 Native 核心、主辅栈和事件事实的可靠保存，以 pending 状态返回接收结果，不论对应 SO 或 mapping 是否已经存在。上报接口、符号表上传接口、事件详情和分析任务创建 MUST NOT 同步执行新旧事件的符号还原。accepted MUST 表示事件已持久化，不表示还原完成；持久化未完成 MUST 按既有可重试错误处理。

#### Scenario: 已有符号表仍异步接收
- **WHEN** 新 Crash 的应用构建已有可用 mapping
- **THEN** 接收请求保存 pending 事件并返回，不等待该事件还原，随后由后台独立处理

#### Scenario: 没有符号表
- **WHEN** 接收事件时找不到对应应用和 buildId 的 mapping
- **THEN** 保存脱敏原始异常链和等待原因，事件可查询并参与临时问题排行

#### Scenario: 接收部分写入后重试
- **WHEN** 事件事实和堆栈状态只有一侧写入成功，随后原 eventId 重试
- **THEN** 系统修复缺失数据后才确认接收，不重复计数，不用原始输入重置已成功还原结果

#### Scenario: Native 已有全部符号文件
- **WHEN** Native 事件的 SO 和 Java mapping 都已上传
- **THEN** 接收仍先保存原材料并返回，随后 Native 与 Java 后台独立处理，详情查询不触发计算

### Requirement: 持久化还原状态与首次成功终态
对于 JVM 事件，系统 MUST 持久化 pending、failed、symbolicated 主异常状态及安全原因。pending/failed MUST 保留可重试的脱敏原始异常链；symbolicated MUST 仅提供单份完整主异常还原堆栈，并记录实际符号表唯一身份、版本或摘要及处理时间。首次主异常成功结果 MUST 固定；重复执行、替换、删除和重新上传 mapping MUST NOT 再次还原或覆盖该事件。其他线程的当前堆栈和独立处理状态 MUST 随该次成功发布固定，未成功的辅助栈 MUST 明确保留原始帧及失败原因，不能伪装成全部已还原；非堆栈诊断上下文 MUST 不随还原改变。

#### Scenario: 成功后只使用固定结果
- **WHEN** 某事件已成功还原，随后 mapping 被替换或删除后重新上传
- **THEN** 主异常堆栈、正式指纹、处理来源和已发布辅助线程结果保持原值，后续详情及后台任务不重新执行该事件的 Retrace

#### Scenario: 失败保留材料
- **WHEN** 主异常解析失败、输出超限或存储临时不可用
- **THEN** 系统保留原始异常链、其他线程材料和可解释原因，不发布截断结果，不标记主异常成功

#### Scenario: 完整候选与未变化输出
- **WHEN** R8 返回内联、多候选或与输入相同的完整输出
- **THEN** 系统保留完整输出，按明确的成功处理语义记录来源，不任取候选，不将输出未变化直接视为失败，也不声称所有帧都已正确还原

#### Scenario: 主异常成功而辅助线程失败
- **WHEN** 主异常完整还原成功，但部分辅助线程失败或耗尽辅助预算
- **THEN** 允许发布主异常成功与正式归组，同时固定辅助线程的原始帧和独立失败原因，页面不能将主异常状态当成辅助线程成功状态

### Requirement: 可靠唤醒与重启恢复
系统 MUST 持久化按 appId、appVersion 和 Crash 类型合并的后台工作、进展与有界轮转位置。版本化 mapping 变更 MUST 唤醒 JVM 及 Native Java 工作；SO 变更 MUST 仅唤醒 Native。重启、通知失败、并发变更及迟到事件 MUST 可恢复，不能仅依赖内存通知。不同版本和类型 MUST 不混用租约、游标和计数；无可处理来源 MUST 等待。活动对账 MUST 包含已登记 SO 和版本化 mapping，排除无版本旧登记；映射选择仍按事件原构建进行。

#### Scenario: 上传完成后重启
- **WHEN** 默认或专用 mapping 和对应应用版本工作已持久化，后台执行前进程退出
- **THEN** 重启后任务继续，上传成功的 mapping 不需要用户再次上传才能触发补处理

#### Scenario: 事件晚于扫描落库
- **WHEN** 一轮补处理结束后，同一应用版本的在途或迟到事件才完成接收，其应用构建仍为非空原值
- **THEN** 系统在后续唤醒或对账中处理该事件，不因旧游标已越过发生时间而永久遗漏

#### Scenario: mapping 被删除
- **WHEN** 删除后本版本待处理事件没有适用的专用或默认 mapping
- **THEN** 版本工作进入等待；重新上传默认或适用的专用文件后恢复尚未成功事件，若仍有其他可处理来源则继续处理它们

#### Scenario: 相同构建标识的不同版本
- **WHEN** 应用的两个版本使用相同 buildId，只有其中一个版本上传了 mapping
- **THEN** 只处理有适用专用或默认 mapping 的版本，另一版本保持等待，进度不混入

#### Scenario: 上传版本默认文件
- **WHEN** 同版本包含不同构建的 pending/failed 事件，管理员上传默认 mapping
- **THEN** 通过同一个版本工作恢复符合该默认来源的事件，不要求为所有历史构建分别上传或创建任务

#### Scenario: 既有 SO 与首次 Native 工作
- **WHEN** 服务升级前已经保存 SO，升级后没有再次上传且 Native 接收通知曾失败
- **THEN** 持久轮转能发现该版本和可处理事件，不要求重传文件或清空遥测

#### Scenario: 单一类型来源可用
- **WHEN** 某版本仅有 SO 或仅有 mapping
- **THEN** 分别推进可处理的 Native 地址或 Java 栈，缺少另一种文件不阻断已有工作

### Requirement: 后台处理有界且失败不阻塞全部数据
JVM 后台 MUST 在数据库限定应用、appVersion、保留期、最新状态及游标分页，先取得最多 100 个轻量候选，再确定实际 mapping，仅为有限可处理身份读取载荷。版本条件 MUST 先于 LIMIT；MUST 不加载全量事件或堆栈。无匹配和同来源确定性失败 MUST 有界跳过并推进持久游标，不阻塞后页；到底后 MUST 轮转，常规唤醒不得反复重置第一页。临时失败 MUST 退避，实际来源变更可重试。MUST 保持查询、执行、并发及结果预算，只处理未过期、未成功的 JVM Crash。

#### Scenario: 大量历史待处理事件
- **WHEN** 某应用版本存在大量不同构建的 pending 事件并上传适用 mapping
- **THEN** 上传请求不等待历史数量相关的处理，后台逐批推进，不把该应用全部事件或堆栈加载到应用内存

#### Scenario: 单条异常与资源预算
- **WHEN** 一条事件无法解析或一次查询耗尽预算
- **THEN** 记录失败或延期并保留材料，其他合法事件能够继续；资源失败不能被报告成全部完成

#### Scenario: 最新状态筛选
- **WHEN** 同一事件存在旧 pending 和新 symbolicated 的物理版本
- **THEN** 先确定最新逻辑状态再筛选，已成功事件不被旧 pending 重新选中

#### Scenario: 大量其他版本候选
- **WHEN** 同 buildId 的其他版本有大量更早发生的事件，而当前版本有可处理事件
- **THEN** 数据库先限定当前版本再选取有限身份，当前版本不会被其他版本占满批次而永久遗漏

#### Scenario: 前页均无匹配文件
- **WHEN** 一个版本的前多页事件无可用 mapping，而后页事件有专用文件
- **THEN** 工作有界推进并最终处理后页，跳过事件仍保留原始材料，不能重复读取第一页导致饥饿

#### Scenario: 跳过后重启或较早迟到事件
- **WHEN** 工作推进游标后重启，或出现早于当前游标的迟到事件
- **THEN** 重启从持久位置继续，轮末回头发现较早事件；普通对账唤醒不会使后页永久无法到达

### Requirement: 成功发布幂等且可对账
对于 JVM 事件，系统 MUST 在成功发布前确定唯一终态内容，将主异常完整堆栈、正式指纹、状态、来源和其他线程当前堆栈及处理结果作为同一逻辑版本发布。响应未知时 MUST 重放相同版本和相同结果，不重新选 mapping 计算；过期执行者和迟到失败写入 MUST NOT 覆盖已确定的成功结果。事件原身份、发生时间、接收时间及不可变诊断上下文 MUST 保持不变。

#### Scenario: 写入成功但确认丢失
- **WHEN** 已存成功结果但后台未收到确认，任务随后恢复
- **THEN** 对账或重放同一主异常及辅助线程结果，事件保持单个逻辑结果和首次成功来源，统计不增加

#### Scenario: 发布过程中查询
- **WHEN** 用户在后台发布或恢复期间查询事件与问题
- **THEN** 每个响应使用一致的当前主异常、辅助线程和归组版本，不组合新指纹与旧堆栈，不隐藏完整可用的待处理详情

#### Scenario: 事件过期
- **WHEN** 待发布事件超过有效数据保留期
- **THEN** 系统清理或结束对应工作，不通过回放恢复已经过期的遥测事件

### Requirement: 其他线程复用主异常后台处理来源
JVM 事件的其他线程 MUST 使用主异常首次成功尝试持有的同一实际 mapping 处理，保持采集时的线程身份、顺序与元数据；处理 MUST 有线程数、输入、输出和总等待预算。正式指纹 MUST 仅使用主异常还原材料，MUST NOT 混入其他线程的帧、状态或日志。没有 mapping 或主异常尚未成功时，其他线程原始材料 MUST 仍可查看。

辅助线程的单项失败 MUST NOT 使完整可用的主异常失败；成功辅助栈只保留一份当前还原文本，失败栈保留原始帧并标记原因，空帧栈 MUST 明确为不适用还原。主异常成功发布后，本版 MUST NOT 对失败辅助栈另启补算或因新 mapping 改写结果。

#### Scenario: 缺少 mapping
- **WHEN** 带其他线程材料的事件等待 mapping
- **THEN** 主异常和其他线程的已采集原始材料均可查看，详情不调用实时还原

#### Scenario: 同一来源还原多个线程
- **WHEN** 主异常及多个其他线程在本次后台处理中取得完整还原输出
- **THEN** 输出保留线程边界、完整内联和候选，实际 mapping 来源一致，正式指纹只由主异常产生

#### Scenario: 空堆栈和辅助输出超限
- **WHEN** 一个线程为空帧，另一个线程的还原输出超过辅助预算
- **THEN** 空帧线程不被标记为还原失败，超限线程保留原始帧和 output_limit 原因，不截断输出伪造成功

#### Scenario: 辅助结果固定
- **WHEN** 主异常成功时某个辅助线程已记录失败，之后上传新的 mapping
- **THEN** 该事件主异常和辅助结果均保持已发布状态，不为辅助失败重新打开主异常终态

### Requirement: Native 原始事件不进入 JVM 符号还原
Native 核心、Native 主帧和其他 Native 线程帧 MUST NOT 被当作 Throwable 或传入 JVM R8。系统 MUST 为 Native 提供独立的 SO 地址还原工作，并允许其关联 Java 栈及 Java 快照使用适用 mapping 独立执行 R8；Native 地址与 Java 栈不得混用来源或互相等待。SO 不唤醒 JVM 主异常工作，mapping 不改变 Native 地址结果。Native 的原始身份、诊断、指纹和构建内归组 MUST 保持；既有 JVM 首次成功与辅助栈规则 MUST 保持。

#### Scenario: 同构建已有 mapping
- **WHEN** 一个应用版本构建已有 mapping，随后收到 Native 和 JVM 事件
- **THEN** JVM 按原规则处理；Native 内 Java 栈可独立还原，Native 地址没有匹配 SO 时继续等待，不把地址传给 R8

#### Scenario: mapping 变更及服务重启
- **WHEN** 上传、替换、删除 mapping 或重启后端
- **THEN** 可恢复 Native 未成功 Java 栈的处理，已成功栈、Native 地址结果、指纹和原诊断不被改写

#### Scenario: 查询 Native 原始材料
- **WHEN** 查询尚未取得任何还原结果的 Native 事件
- **THEN** 以 native_stack 展示原材料和各自等待原因，不在请求内启动还原，不把已有采集函数名当作后台成功

#### Scenario: 模块 SO 已上传
- **WHEN** 管理员为 Native 事件所属版本上传匹配 ABI 和完整 ELF Build ID 的 SO，随后替换或删除
- **THEN** 可靠推进 Native 未成功帧，已经成功帧保持结果和实际来源，不生成 JVM 主异常任务，原事件构建仍必填

### Requirement: mapping 来源确定性选择与固定
JVM 主异常后台及 Native 内 Java 栈后台 MUST 统一执行同版本构建专用优先、版本默认其次的规则；应用构建仍必填，专用不存在时才用默认。子批 MUST 固定同一实际 symbolId/revision，失败重试根据实际来源和退避判断，来源新增、替换或删除后可重新选择；成功后 MUST 按 JVM 主异常或各条 Native 内 Java 栈分别固定。MUST NOT 猜测其他专用文件、跨版本、SO 或旧无版本登记。升级 MUST 排空旧未确认结果和有效租约，保留原发布字节、来源及序列，不得清空后重新计算。

#### Scenario: 其他版本存在可用 mapping
- **WHEN** 事件版本没有 mapping，但相同 buildId 的另一版本存在合法文件
- **THEN** 当前事件保持原始可查询材料与等待状态，不执行另一版本文件的 R8

#### Scenario: 版本化切换时仍有未确认发布
- **WHEN** 数据结构升级前仍存在未确认首次成功发布或有效在途租约
- **THEN** 切换预检或迁移明确阻止继续，保留原内容，不能清空发布表、重置状态序列或改用新 mapping 重算

#### Scenario: 已成功事件遇到新版本登记
- **WHEN** 旧事件已成功固定，管理员随后按明确版本重新上传同字节或不同字节 mapping
- **THEN** 旧事件保持原 symbolId、修订号、摘要、主辅栈和正式指纹，新登记只影响按选择规则适用的尚未成功事件

#### Scenario: 默认失败后新增专用文件
- **WHEN** build-A 事件使用默认文件确定性失败，随后为 build-A 上传专用 mapping
- **THEN** 可按新的实际来源重试；其他构建仍用默认来源，已经成功事件不重算

#### Scenario: 精确来源不可读
- **WHEN** 专用登记存在但不可读，即使默认文件可用
- **THEN** 保存或报告存储失败并退避，不以默认文件掩盖故障或产生成功来源

### Requirement: Native 候选按剩余工作有界选择
Native 后台 MUST 在数据库限定应用、版本、Native fatal、保留期和最新状态，再有界取得最多 100 个候选身份，之后仅加载有限候选的主辅栈。只要有可处理但未成功的 Native 帧或 Java 栈，即使主栈摘要已成功也 MUST 能再次进入候选。MUST 保持持久游标轮转、连续完成前缀、响应预算减半及迟到事件发现；无匹配与同来源确定性失败不得阻塞后页或形成热重试。

#### Scenario: 主栈成功后补辅助
- **WHEN** 主栈已 symbolicated，但其他 Native 或 Java 线程还等待来源
- **THEN** 后台仍可选择该事件，仅处理未成功单元，不因摘要成功而永久遗漏辅助栈

#### Scenario: 不相关来源占据前页
- **WHEN** 某版本前多页均无适用来源，而后页有匹配 SO 或 mapping
- **THEN** 持久游标推进到后页并处理，轮末回头后能发现新来源及较早迟到事件

#### Scenario: 大量其他版本与大诊断
- **WHEN** 其他版本存在大量更早事件，目标版本的有限事件带有大诊断
- **THEN** 版本过滤先于候选数量限制，第一阶段不读取完整栈或诊断；有限载荷查询耗尽预算时缩小批次而不提高上限

#### Scenario: 同事件前部模块反复超时
- **WHEN** 同一事件前部模块反复触发临时超时，而后部模块或 Java 线程尚未尝试
- **THEN** 后部单元在后续有界轮次获得处理机会，Native 超时不耗尽 Java 独立预算，不反复只处理同一前缀

### Requirement: Native 增量快照只能保留或增加成功结果
每次 Native 发布 MUST 使用同一状态版本包含完整主辅结果、各单元来源、原指纹及采集摘要，并验证所有既有成功单元不变。发布 MUST 检查有效类型/版本租约及基础状态版本，使用单调新版本固定完整字节；过期基础或租约不得覆盖新结果。主栈、Java 栈、其他线程和安全失败状态 MUST 通过同一有序发布路径更新，不能用迟到失败覆盖成功。

#### Scenario: 多轮发布
- **WHEN** 第一轮成功模块 A 的帧，第二轮补模块 B 或 Java 栈
- **THEN** 第二轮完整保留 A 的结果和来源，只改变未成功单元，读者不混合两轮状态

#### Scenario: 旧执行者迟到
- **WHEN** 旧执行者拿着较早基础状态或过期租约，在新结果确定后尝试发布
- **THEN** 拒绝旧发布，不丢失任何已成功帧或 Java 栈，也不重复增加进度

#### Scenario: 输出超过本轮预算
- **WHEN** 添加新结果会使完整快照超限
- **THEN** 已确认成功结果不回退；减少本轮新增结果或保留旧快照并明确延期，不截断函数/内联链或 Java 文本伪造成功

### Requirement: Native 未确认增量必须同字节恢复
系统 MUST 为每个 Native 事件可靠保存最近一代发布的版本、摘要及未确认完整载荷；未确认时 MUST 先重放原字节，不重新选文件或被下一轮覆盖。只有读回完整版本一致后才确认并允许下一轮。确认和进度计数 MUST 幂等；事件过期不得因重放恢复。JVM 原首次成功发布 MUST 保持不可替换，迁移不得清空在途结果或重算成功来源。

#### Scenario: 确认丢失后替换来源
- **WHEN** 增量已写入但确认丢失，管理员又替换 SO 或 mapping 后服务重启
- **THEN** 先重放登记的原版本、原来源和原字节；确认后才为未成功单元开始新一轮

#### Scenario: 重复确认与事件过期
- **WHEN** 同一发布被重复确认，或事件已超出保留期
- **THEN** 重复确认不重复计数，过期事件不被重新恢复为可查询遥测

#### Scenario: 迁移前存在旧在途结果
- **WHEN** 准备升级而存在有效租约或未确认 JVM/Native 发布
- **THEN** 阻止不安全切换，保留租约、来源及原字节，排空后再迁移，不以删除记录绕过

### Requirement: Native 还原失败可解释且资源有界
系统 MUST 对每次后台工作的执行时间、并发、进程资源、输入输出、内联结果及在途发布设限；超时、异常退出、工具不可用和输出超限 MUST 保留材料及明确安全原因，单元故障不得丢弃其他已成功结果。文件处理 MUST 不执行上传 SO，不访问任意外部调试文件或自动远程查找；响应和日志 MUST 不暴露原始 stderr、编译机绝对路径、文件内容或秘密。

#### Scenario: 工具超时或输出膨胀
- **WHEN** 原生解析进程超时、资源耗尽或输出超过上限
- **THEN** 有界停止并回收资源，保存原帧和安全原因，其他可处理单元可在后续轮次继续，不伪造成功

#### Scenario: 工具不可用但 mapping 可用
- **WHEN** Native 地址还原工具或其资源限制不可用，而对应 Java mapping 可用
- **THEN** 地址处理延期，事件接收与 Java 栈还原仍能继续

#### Scenario: 不可信调试路径
- **WHEN** 符号文件引用控制目录之外的附加调试文件或输出编译机绝对路径
- **THEN** 不读取该外部文件，发布的源码位置不泄露绝对目录，不记录原始工具错误文本
