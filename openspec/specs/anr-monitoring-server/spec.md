# anr-monitoring-server Specification

## Purpose

接收 Android SDK 已判定的 ANR，持久保存事件及其有界诊断现场，并向拥有应用查看权限的用户提供统计、事件列表和诊断详情查询。

## Requirements

### Requirement: 接收独立的 ANR 批次事件

服务端 MUST 通过 `POST /ingest/v1/batches` 接收 Schema v2 的 `eventType=anr` 和独立的 `anr` 载荷。服务端 MUST 按公共批次规则认证 App Key、匹配包名、校验事件身份和时间，并将该事件分派到 ANR。判定来源 MUST 为消息超时或系统进程错误状态。ANR 载荷 MUST 与其他事件载荷互斥。

#### Scenario: 合法的两种判定来源

- **WHEN** 有效应用批次中包含两种合法 ANR 判定来源的事件，并带有各自原始身份
- **THEN** 两种事件均进入 ANR 接收，且各自判定来源可查询

#### Scenario: 批次包含事件级无效 ANR

- **WHEN** 一条事件缺少 ANR 载荷、带有互斥载荷、判定来源无效，或 ANR 载荷出现在其他事件类型上
- **THEN** 服务端按事件级永久错误拒绝对应事件，其余合法事件保持公共批次确认语义

#### Scenario: 包名与凭据绑定不符

- **WHEN** 批次中的 ANR 包名与 App Key 所绑定的包名不一致
- **THEN** 服务端按公共包名规则拒绝整个批次，且不写入任何事件

### Requirement: 校验并保存有界的 ANR 诊断

服务端 MUST 保存主线程 Java 栈、消息及诊断状态，并允许 `anrInfo`、trace、Logcat、内存、FD、进程、设备各分区独立缺失。服务端 MUST 校验分区结构、状态和实际 JSON 字节上限，存储前按公共诊断规则脱敏。诊断正文与凭据 MUST NOT 进入接收日志、错误响应或列表摘要。

#### Scenario: 诊断包含真实零值、缺失或截断

- **WHEN** 合法事件的内存值为零，trace 是裁剪后的采集片段，且 `ANR_INFO` 未取得
- **THEN** 详情保留零值、trace 的来源与截断状态，以及 `ANR_INFO` 的不可用状态，事件正常接收

#### Scenario: 合法结构中的诊断内容超限或无效

- **WHEN** 独立 ANR 分区超出字节限制或分区状态与内容不匹配
- **THEN** 服务端按事件级永久错误拒绝该事件，错误正文不回显对应输入文本

#### Scenario: 诊断包含可识别的敏感字符串

- **WHEN** `ANR_INFO`、trace、Logcat 或消息中出现受支持规则识别的凭据或敏感路径
- **THEN** 持久化和详情仅保留脱敏文本，日志及错误响应中没有原文

### Requirement: 事件持久化确认与重试幂等

服务端 MUST 按 `appId + eventId` 对 ANR 幂等，首次有效写入后的事件正文保持冻结。服务端 MUST 在持久化确认后返回 `accepted`，在已存事件上返回 `duplicate`，在存储未确认时返回公共可重试错误。逻辑事件详情与统计 MUST 同时按相同身份去重。

#### Scenario: 写入成功但响应丢失

- **WHEN** 第一次请求已使事件持久化但客户端没收到响应，随后用原事件重试
- **THEN** 重试收到 `duplicate`，列表、详情和统计只反映一次事件

#### Scenario: 同一应用重复提交已存 ID

- **WHEN** 同一应用再次使用已存的 `eventId` 且正文与首次有效写入不同
- **THEN** 首次有效正文保持可查，后续提交不能覆盖或追加诊断

#### Scenario: 存储暂时不可用

- **WHEN** 存储不可用或写入结果未得到确认
- **THEN** 服务端返回可重试错误且不确认相应事件，随后原事件可重试

### Requirement: 按应用和有限时间查询 ANR

查询 MUST 复用网页会话和应用查看权限。概览与列表 MUST 使用一致的应用、发生时间、版本和判定来源筛选，且在数据库中完成过滤、聚合、排序和有界分页。统计 MUST 显示去重事件数和匿名设备数。列表 MUST 使用发生时间与事件 ID 作为稳定排序键，并拒绝与当前应用或筛选不匹配的游标。详情 MUST 按应用和事件 ID 单独读取正文。

#### Scenario: 同一设备多次发生且存在时间并列

- **WHEN** 同一应用在筛选窗中有同设备多条 ANR 和发生时间相同的不同事件
- **THEN** 概览分别统计事件和去重设备，列表可稳定分页且不会带出诊断正文

#### Scenario: 跨应用访问和游标重用

- **WHEN** 用户用无权应用的 ID 访问任一 ANR 接口，或把另一应用、时间窗或筛选的游标用于当前列表
- **THEN** 服务端拒绝请求，且不返回不属于当前授权范围的摘要或诊断

### Requirement: 按事件构建在后台还原 ANR 的 Java 栈

服务端 MUST 先保存原始诊断并确认接收，再后台还原主线程 Java 栈及系统 trace 中可可靠识别的 Java 帧。服务端 MUST 按事件应用、版本和构建选择 mapping，同版本构建专用优先，专用登记不存在时使用同版本默认。缺少匹配 mapping 时 MUST 保留原文并在有效 mapping 后续可用时补处理。接收和查询请求 MUST NOT 等待或执行还原。

#### Scenario: 事件入库时已有构建专用 mapping

- **WHEN** 应用同时有同版本默认和事件构建专用 mapping
- **THEN** 原始事件可先查询，后台只用该专用文件还原，并记录实际文件标识与修订。专用文件不可读时保留原文并报告失败状态

#### Scenario: 只有默认或晚到的匹配 mapping

- **WHEN** 当前无构建专用登记，且同版本默认 mapping 已存在或随后上传
- **THEN** 后台使用该版本默认文件。只有其他应用或其他版本的文件时，原文保持可查并显示等待状态

#### Scenario: 后台重启和重复发布

- **WHEN** 还原处理中重启，或处理结果写入后确认丢失，或成功后的 mapping 被替换
- **THEN** 待处理事件可恢复，已确认视图和来源保持固定，重复处理不增加事件、设备数或重复视图

### Requirement: 保存原文与有界的 Java 还原视图

接收时保存的脱敏原文 MUST 保持可查。可用还原结果 MUST 单独保存和返回，主线程栈与 trace 分别提供状态、原因及适用的 mapping 来源。系统 trace 的线程身份、锁记录、Native 帧和未识别行 MUST 按原文呈现。还原过程 MUST 限制输入、输出和处理资源，超限或失败时不得改写原事件内容或统计。

#### Scenario: trace 混合 Java、Native 和锁记录

- **WHEN** 系统 trace 带有多个线程、可识别的 Java 帧、锁记录、Native 帧及截断残行，且 R8 返回内联帧或多候选
- **THEN** 可用的 Java 还原结果在原线程位置展示并保留有效候选，其余行按原文展示，原始片段仍可完整查询

#### Scenario: 部分内容无法还原

- **WHEN** 一部分可识别 Java 帧还原成功，其余帧段因格式或预算无法完成，或一个分区整体失败
- **THEN** 各分区报告实际部分成功、失败或不适用状态，未还原内容使用原文，另一分区的可用结果仍可查询
