# JVM Crash 后台还原与持久化

## 变更原因

当前 JVM Crash 使用未反混淆堆栈生成问题指纹，仅在查看详情时实时 Retrace，因此不同混淆构建中的同一问题不能可靠归并，重复详情请求也会重复解析。需要按新需求统一建立后台还原和持久化模型，处理新模型中的新到事件与积压待处理事件，直接删除旧业务链路及版本兼容分支。

## 变更内容

- 新 Crash 校验、脱敏和持久化后即返回接收结果，状态为 `pending`；不在上报、详情查询或分析任务创建请求中执行 Retrace。
- 未成功还原的事件保留脱敏原始异常链，以应用、buildId 和原始指纹临时归组并参与排行；成功后仅保留完整还原输出，按正式指纹归组。
- 在现有后端、PostgreSQL 和 ClickHouse 内实现有界后台处理、可靠唤醒、失败退避和重启恢复；符号表上传只校验、保存并登记任务，不等待历史还原完成。
- 按原 eventId 和发生日期更新问题归属，保持崩溃次数、会话分母和设备统计；避免重试、回填或旧状态残留放大计数。
- 增加授权删除符号表能力，保留来源元数据和审计。删除后重新上传产生新的符号表身份，已成功还原的事件始终固定；已有替换功能遵循同样的固定结果规则。
- **BREAKING**：Crash 详情改为返回单份当前堆栈及其格式、持久化状态和来源，取消原始/实时还原双份展示语义；同步网页、Agent HTTP、MCP 和单事件分析证据消费者。
- **BREAKING**：当前契约只支持新三态、单份 `stack`、证据版本 3 和报告版本 4；删除旧 `raw_only` 状态适配、旧详情字段别名、旧分析证据/报告的解析、展示及执行分支，不提供自动降级。
- **BREAKING**：新 Crash 事实与状态使用新结构一次性切换，不读写旧 Crash 表，不开发旧 `raw_only` 数据自动转换器、双读双写或旧代码回退路径。现有旧数据不自动清空，也不接入新业务查询；新流程的 pending/failed 补处理、首次成功固定和证据冻结仍完整保留。
- 仅覆盖 JVM fatal Crash；卡顿、内存、Native 符号化和 Android 上报 v2 契约不扩展。共享 mapping 删除后，卡顿继续使用既有的“当前无 mapping”行为，既存卡顿事件不回算。

## 能力范围

### 新增能力

- `crash-background-symbolication`：事件持久化状态、后台调度、任务恢复、单次成功发布、失败处理和有界补还原。

### 修改能力

- `jvm-crash-monitoring`：只使用新事件结构的临时/正式归组、单份持久化堆栈、精确统计和详情契约。
- `application-symbol-management`：删除与重新上传、上传后可靠登记后台工作、来源审计和并发文件租约。
- `crash-frontend`：临时问题、持久化还原状态、单份堆栈及后台进度展示。
- `current-code-crash-fix`：只处理当前证据和报告格式，冻结当前已存堆栈，删除旧任务适配与只读展示要求。
- `apm-mcp-query`：按新详情契约返回当前堆栈片段、状态和实际处理来源，移除旧片段别名，保持只读及有界证据语义。

## 影响范围

- 后端 `crash`、`symbol`、`agent`、`agentquery` 的公开契约及内部实现；新增 PostgreSQL/Flyway 与 ClickHouse 迁移，不修改已发布迁移。
- 前端 Crash 页面、符号表页面及相关类型、API 封装和测试；独立 `mcp-server`；仓库中的分析 Worker、Skill 交付及证据版本检查。
- 根、后端、前端知识库，Crash/符号表/Agent/MCP/分析 API，客户端的接收成功与后台还原、mapping 生效说明及相关固定数据集。
- 复用现有 R8 依赖、受控文件卷、数据库和 Spring 调度。规划不包含外部消息队列、缓存、对象存储、多实例部署或云端自动发布。
- 一次性更新后端、网页、MCP 和仓库 Worker，移除只服务旧模型的代码、测试、示例和配置；已发布数据库迁移保持不可变，新结构通过新增迁移建立。此次规划更新不执行服务切换或旧数据删除。
- 本变更接受首次成功还原结果不可纠正的业务取舍；格式合法但与 APK 不匹配的 mapping 可能造成永久错误归组。业务上仅保留当前堆栈，不承诺 ClickHouse 历史版本或既有备份中的原文被立即物理擦除。
