# JVM Crash 后台还原设计

## 背景

动机与已确认范围见 [提案](proposal.md)。现有实现中，`CrashEventProcessor` 保存 `raw_only` 事件并生成原始指纹，`CrashQueryService.analysisSnapshot()` 在请求内调用 R8；`ClickHouseCrashRepository.append()` 跳过已有 eventId，不能用于补还原。摘要、详情分别位于 `apm_event_raw` 和 `apm_crash_detail`，详情读取 `raw_stack_json`，成功文本只存在于响应中。

现有正式规范要求原始堆栈长期保留、每次详情实时还原、指纹不得改变；本变更明确替换这些要求。分析证据版本 2、网页双视图和 MCP 的 `rawCrash`/`symbolicatedStackText` 片段也依赖旧语义。`app_symbol_file_audit` 对符号表主记录存在级联删除外键，不能直接硬删除主记录来实现新功能。

## 目标与边界

- 上报与符号表上传请求不等待事件还原，详情和分析任务创建只读取已存结果。
- 事件只有一份业务上有效的当前堆栈：待处理时为原始异常链，成功时为完整还原输出；成功后不再更正。
- 接收去重、处理结果发布、查询归组和每日统计在重试、崩溃恢复及部分写入时保持一致。
- 首版沿用单后端实例与现有数据库，不建设分布式执行平台。仍使用有限租约和结果发布记录处理进程重启与跨数据库响应未知。
- 运行时只支持本设计的新事件结构、详情契约、证据版本 3 和报告版本 4。直接删除旧同步还原、旧表读写、字段别名、旧证据/报告解析与展示分支，不保留双读双写、按需转换或版本降级。
- 不修改 Android v2 上报信封，不新增客户端混淆声明，不改变卡顿解析与内存上报。旧版本数据不自动转换、不纳入新查询，也不因本次变更自动删除；同一新契约内已冻结证据保持不可变。

## 设计决策

### 1．持久化三态与单份堆栈

事件状态为 `pending`、`symbolicated`、`failed`；处理中的领取状态属于后台任务，不为每次处理额外写入一个事件中间状态。

| 状态 | 当前堆栈 | 问题归组 | 后续处理 |
|---|---|---|---|
| pending | 脱敏原始异常链 | temporary | 有 mapping 时处理；无 mapping 时等待 |
| failed | 脱敏原始异常链 | temporary | 临时错误退避；确定性失败等待新 mapping |
| symbolicated | 完整脱敏 Retrace 输出 | resolved | 终态，永不再次调用 R8 |

堆栈采用一个带格式的载荷：`raw_chain` 保存当前 `CrashPayload` 结构，`retrace_text` 保存完整 R8 标准异常链文本。还原成功后只保留后者，不额外复制原始链或可由文本重建的完整帧集合。事件事实另存 `crashKind`、`fatal`，避免分析资格依赖原始载荷是否存在。指纹所需的规范化关键帧在处理期间生成，不作为第二份完整堆栈持久化。

成功状态表示已用指定 mapping 完成一次受限处理，不保证所有帧都有映射，也不证明 mapping 与 APK 匹配。保留完整原因链、内联展开和多候选结果；不能任取候选、截断输出后宣称成功，输出未变化也不直接判失败。

相比布尔字段，三态能解释没有 mapping 与解析失败；相比永久保存原始和还原两份，本方案遵守已确认的成功后固定取舍。

### 2．事件事实与可变 Crash 当前状态分开

新建 `apm_crash_fact` 保存新流程的 Crash/app_start 不可变事实、接收时间、发生时间及启动会话分母，使用现有事实查询所需的应用、事件类型、时间和 eventId 定位与精确去重字段。新建 `apm_crash_state` 保存单份当前堆栈和归组。运行时只读写这两份新结构，删除旧 `apm_event_raw`/`apm_crash_detail` 的 Crash 适配器、回退查询和重复字段读写，不逐步双写切换。

旧 Crash 数据保留在原存储但不接入新查询、不自动导入；新总览、分母、Issue 和详情必须使用同一份新数据集，不能混入旧启动会话而使崩溃率失真。旧数据备份、导出或物理删除属于单独的数据处置，不由启动、后台对账或新迁移隐式执行。

新表至少包含：

- 定位：`app_id`、`event_id`、`build_id`、原 `event_time`。
- 当前结果：`state_version`、`symbolication_status`、安全错误原因、`stack_format`、`stack_payload`、异常类型、当前指纹、指纹版本、`grouping_kind`。
- 处理来源：实际或最后尝试的 `symbol_id + revision + sha256`、处理时间、下次可重试时间。

使用独立的单调 `state_version` 选择最新逻辑记录，不再用 `received_time` 充当后台修改版本；接收时间不因回填改变。替换键使用不可变的应用、构建、发生时间和 eventId，不能把状态或指纹加入替换键。状态变化后仍然必须是同一个逻辑事件。

把堆栈和指纹放进同一条状态记录，可以一次发布二者，避免分别覆盖现有摘要/详情造成不一致。ClickHouse 按列读取，Issue 和事件摘要查询只选取轻量列，不能读取 `stack_payload`。

### 3．接收成功与可靠唤醒

新 Crash 不论 mapping 是否存在，都先保存 `state_version=0` 的原始 pending 状态和不可变事实，确认两者持久化后才能增加 accepted。采用先状态后事实的写入次序；状态读取及后台选取必须关联已存在的事实，孤立暂存状态不参与统计。重试需要修复缺失的一侧，不能因事实已存在就跳过详情修复，也不能用重复的版本 0 覆盖更高状态版本。

Crash 落库后通过 `symbol.api` 的公开映射可用性检查唤醒该构建。ClickHouse 与 PostgreSQL 不建立伪跨库事务：如果事件已保存但唤醒失败，定时对账仍要发现它。后台索引对账对有活动 mapping 的构建轮转扫描、限定保留期和每次资源，覆盖“上传扫描完成后才落库的事件”、进程退出和错过通知。

符号表校验和文件发布完成后，当前 mapping 元数据与构建任务唤醒在同一个 PostgreSQL 事务中提交。该事务不能执行历史事件查询或 Retrace。上传返回原有 201/200，只表示文件可用；后台状态通过独立查询获取。

### 4．按构建持久化任务与有界执行

新增 `crash_symbolication_job`，按 `app_id + build_id` 合并工作，不为每个上报事件创建一份执行任务。记录任务状态、唤醒代次、租约、下次执行时间和最近一次处理进展。重复上报或重复上传仅增加可合并的唤醒，不无限堆积任务。

建议初始运行参数：每批 100 条、单实例同时处理 1 个构建，复用现有 R8 并发许可及输出上限；这些是待验证的保守默认值，不是容量承诺。使用现有 Spring 调度和受限执行器，禁止无限线程或无限内存队列。任务领取、续租、释放均带代次检查；失去租约后停止新计算和新发布。

每批只在新事实与新状态结构中，按应用、buildId、保留期和最新处理状态查询，使用游标及有限返回；先确定最新逻辑版本，再筛选 pending 或符合重试条件的 failed。旧 raw_only 记录和旧详情表不属于任务输入，也不在扫描时转换为 pending。临时失败退避，确定性错误在同一 mapping 身份下停止热重试；新 mapping 可重新唤醒尚未成功的事件。完成一轮后，后续唤醒从保留期内重新查找，不能让按发生时间推进的游标永久跳过迟到事件。

当前排序键不能高效定位 buildId，新增状态表以应用和构建为查询前缀，并在实际规模数据上验证过滤与列裁剪。每轮最多查询的时间范围为当前 30 天原始事件保留期，执行时间、扫描行数、读取字节和返回字节必须受预算限制。预算触发应延后任务或缩小时间片，不把失败误报为已经处理完成。

### 5．首次成功固定与跨库发布恢复

仅依靠内存锁或“写前再查一次”无法保证响应未知、租约重领时的成功结果固定。增加有限的 PostgreSQL `crash_symbolication_publication` 发布记录，以 `app_id + event_id` 唯一决定首次成功结果，承担跨库提交恢复而不是通用消息队列。

处理开始时取得递增尝试代次；成功计算后，在受保护的短事务内登记唯一终态结果、独立状态版本、实际 mapping 身份、结果摘要和待发布载荷。终态已存在时必须使用既有结果，不得用当前新 mapping 再算一遍。失败状态版本必须早于后来登记的成功终态版本，已登记终态后禁止再分配可覆盖它的失败写入。

发布器把同一份终态记录写入 `apm_crash_state`，再读回核对状态版本和摘要。ClickHouse 写入或确认响应未知时，只能重放相同版本、相同字节；不能重新解码已有还原文本或选择另一份 mapping。确认发布后清空 PostgreSQL 中的完整待发布载荷，仅保留幂等所需的轻量终态元数据，随事件过期和在途期限一并有界清理。发布未确认时禁止清除原始事件的有效读取路径。

该记录解决“PostgreSQL 已提交、ClickHouse 未写”“ClickHouse 已写、确认丢失”“旧请求晚到”等窗口。批量处理逐条提交结果并限制未发布载荷总量；数据库故障时背压，不无限保留计算结果。已经成功还原的事件不会因 job 重跑、mapping 替换或删除而产生第二份逻辑结果。

### 6．临时与正式指纹

- 临时指纹使用独立版本和命名空间，例如 `tmp-v1`，由应用、buildId 和既有规范化原始指纹构造，不跨构建合并。
- 正式指纹使用 `resolved-v1`，由应用、异常类型/原因链、规范化动态消息和最多 8 个关键应用调用位置构造。使用还原后的类与方法身份，排除易变行号、buildId、应用版本及 mapping 版本/摘要。
- R8 适配器同时提供完整文本及用于归组的规范化调用信息。内联与多候选集合按稳定规则表示，不能随意取第一条候选作为唯一根因；没有可靠应用帧时采用明确版本化的完整候选/帧回退规则。
- 同一业务问题调用路径发生实质变化时仍可能拆组，不承诺仅凭堆栈做到根因级自动合并。

后台成功只改变当前状态中的指纹和归组。总览、每日事件数和会话分母从事实表精确去重计算；Issue 与指纹筛选通过数据库侧关联最新 Crash 状态。按某指纹筛选时保留符合其他维度的 app_start 分母。补处理反映在原来的发生日期，不能把处理时间当发生时间。

新 API 只关联 `apm_crash_fact` 与最新 `apm_crash_state`；删除依赖旧 Crash 表和旧小时聚合的运行时代码、专用查询配置及相应旧行为测试，不新增到旧聚合的双写或回填。事件事实只在接收时写一次逻辑内容。未使用的旧库对象不由本次启动或初始化流程自动清空。

### 7．符号表删除、重传及在途处理

保留现有上传、幂等和 revision 条件替换。新增 `DELETE /api/v1/apps/{appId}/symbols/{symbolId}?expectedRevision=N`，需要 Session、CSRF 和 OWNER/ADMIN；成功返回 204，过期 revision 返回现有版本冲突语义，未知或非所属资源返回 404。

删除使用 `deleted_at` 标记主记录，活动记录改为局部唯一约束 `app_id + build_id WHERE deleted_at IS NULL`，保留历史来源及审计；活动列表、注册表查询和后台领取均排除已删除记录。新增删除动作审计，历史记录不进入普通列表，也不新增历史浏览功能。同构建重新上传生成新 symbolId，revision 从 1 开始，通过唯一身份和摘要与旧文件区分。

先让删除在数据库生效，再按现有读取租约退休文件。已经取得旧 mapping 的一批允许完成，并记录旧身份；之后的批次必须重新取得当前活动文件。删除后没有新 mapping 的构建进入等待，重新上传唤醒剩余原始事件。已成功事件和已登记首次成功的发布记录都不受影响。

共享注册表仍服务卡顿：删除后卡顿走既有无 mapping 可选解析，已有卡顿数据不重算，不加入本次后台队列。

### 8．HTTP、网页、MCP 与分析证据

Crash 详情删除 `rawCrash`/`symbolicatedStackText` 双份字段及其兼容别名，使用单一 `stack` 对象：`{format: raw_chain|retrace_text, content: ...}`，并显式提供 `crashKind`、`fatal`、持久化状态、原因、处理时间、实际符号表身份和 groupingKind。列表和 Issue 摘要增加 groupingKind，临时项携带 buildId。成功详情的符号表来源来自事件，而不是当前注册表；文件已删除仍可查看。网页只解析当前契约；收到 raw_only 或仅有旧字段的响应时明确报告协议错误，不兜底渲染旧视图。

原始临时问题转为正式问题后，不建立可能一对多的自动重定向。旧指纹页面没有事件时显示“临时归组可能已变化，请返回问题列表”，事件详情始终通过 eventId 可达。沿用既有非快照分页说明，后台处理过程中允许排行变化，不承诺跨页快照一致。

符号表页新增删除确认和只读构建进度查询：`GET /api/v1/apps/{appId}/symbols/{symbolId}/crash-symbolication`。响应提供稳定状态 `queued/running/waiting_mapping/retry_wait/idle`、本轮累计成功/失败数量、更新时间及错误类别；使用限定应用的已有任务记录，不为每次轮询扫描全部堆栈，`idle` 不承诺未来没有迟到事件。删除成功后停止该行轮询；用户重新上传后读取新 symbolId 对应进度。

MCP 保持 19 个只读工具，Crash 大片段只接受 `stack`，移除 rawCrash、symbolicatedStackText 旧片段和别名；不转换旧后端响应。沿用结果大小、内容摘要和续读校验；状态改变导致片段摘要改变时返回既有证据变化错误，不能拼接前后两个版本。

分析任务只使用当前已发布堆栈、格式和来源，不执行 R8。当前证据 schemaVersion 固定为 3，片段名为 `crash-stack`；报告只接受版本 4，沿用当前租约/停止规则。任务从创建时就标记当前契约，当前任务列表、详情、领取、结果及网页只访问当前契约任务；旧版本任务不提供只读展示、继续执行或自动升级入口。仓库 Worker、统一启动器及网页删除其他证据/报告版本的解析、提示模板和展示适配，遇到不支持的版本明确拒绝。成功事件不能伪造已不存在的原始链，待处理事件也允许分析并说明符号局限。

同一新契约内，任务冻结 pending 材料后事件再完成还原，原任务证据仍保持原字节；这是当前流程的证据一致性要求，不是旧版本兼容。原存储中的旧任务、证据和报告不因拒绝访问而被重写或自动删除。

### 9．模块与数据归属

Crash 拥有新事实、状态、调度、指纹和发布记录；symbol 只校验/管理文件，并通过公开的任务唤醒端口和进度查询端口交互。跨模块禁止访问 internal；已有 symbol API 继续提供不可变文件租约。agentquery、MCP 和前端只消费当前公开契约。新 Flyway/ClickHouse 版本号以实施时最大版本为准递增，不改 V4 或既有 001～007 脚本。已发布迁移属于数据库版本记录，不意味着运行时保留旧实现；新增迁移只建立当前所需结构，不执行旧 Crash/分析数据自动转换或清空。

## 风险与取舍

- 错误 mapping 首次成功后不可纠正：上传页面说明必须匹配同一次 APK 构建；格式校验不能作为匹配证明，保存实际来源便于解释。
- 原始堆栈删除是新流程当前版本替换：ClickHouse 中 pending 的历史物理版本及既有备份不承诺立即物理擦除；运行时不保留原始/还原双份读写。旧存储数据不自动处置，也不为其保留兼容代码。
- 首次成功发布记录增加 PostgreSQL 写入和短时载荷：限制在途数量、按事件保留期清理并测试发布积压；不将长期完整堆栈移入管理库。
- 临时问题回填后变化：明确临时标记、保持 eventId 稳定，不把临时问题数量解释为固定缺陷数。
- 新状态表关联可能增加查询成本：在百万级历史事件和高待处理比例下验证执行计划、列裁剪、查询预算及后台与前台混合负载，保留资源拒绝语义。
- 部分帧无映射或多候选：完整保留输出与解释，避免把“处理完成”宣传为完整准确还原。

## 新结构初始化、切换与验证

1. 通过新增迁移建立新 Crash 事实与状态、后台任务、发布记录、当前任务契约标识、符号表软删除及审计结构。旧 Crash/分析记录不自动搬迁或升级，也不删除现有数据；缺少新结构时明确拒绝启动新链路，不回退旧表。
2. 删除只服务旧模型的生产代码、字段映射、配置、提示模板、测试夹具和只读展示分支，以当前模型重新组织测试；不开发旧 raw_only 导入器、旧证据转换器或旧查询兜底。
3. 在隔离环境仅用当前 v2 上报、新状态和当前分析契约生成数据，核验新事实/状态覆盖、后台恢复及统计；保留一组离线旧表/旧格式样本，证明它们不会被新查询、任务扫描或消费者隐式接入。
4. 后端、前端、MCP、仓库 Worker 和 Skill 交付一次性协调切换。切换前停止旧入口并确认相关在途宿主任务已经停止，不伪造停止事实；新版本不承接旧任务。重新启动应用产生新会话后执行客户端闭环，避免用旧会话数据解释新数据集分母。
5. 验证重复上传、两侧写入中断修复、首次发布响应未知、mapping 删除/重传、迟到事件、失败退避和重启恢复；对照新流程中临时转正式前后的总览、分母、设备数、事件列表及原日期趋势。
6. 部署检查和文档只描述新结构、当前字段及支持版本；部署失败时停止切换并使用独立核验的环境恢复步骤，不在新程序中提供旧结构适配或旧代码降级路径。任何旧数据物理删除都不由本次规划或默认启动步骤执行。

本设计没有需要阻塞规划的未决事项。批量和调度间隔可在不改变契约的情况下通过受控性能测试调小，初始默认值不构成生产 SLA。
