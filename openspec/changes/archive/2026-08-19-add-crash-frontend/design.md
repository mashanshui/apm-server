## Context

后端当前已经提供 Crash 总览、趋势、问题排行、按指纹查询事件和单事件详情五个查询接口，默认查询最近 24 小时，最大时间范围为 31 天；查询需要开发期的 `X-Project-Id` 请求头。仓库没有前端工程，也没有发现可供浏览器直接使用的 CORS 配置，因此前端应通过本地开发代理访问 Spring Boot，而不是直接依赖跨域访问。

本设计实现 proposal.md 中的 Crash 单一纵向闭环，行为要求以 `specs/crash-frontend/spec.md` 为准。

## Goals / Non-Goals

**Goals:**

- 建立可独立启动、构建和验证的 `frontend/` 前端工程。
- 用真实 Crash 查询接口完成总览、筛选、问题下钻、事件列表和堆栈详情。
- 让路由查询参数承载项目和筛选状态，刷新或复制链接后仍能恢复当前页面上下文。
- 集中处理 API 类型、请求头、错误、加载、空数据、分母不足和游标分页。
- 不把项目上报 Key 带入浏览器，不把后端开发期请求头误认为正式认证。

**Non-Goals:**

- 不实现登录、OIDC、成员管理、正式多租户权限或项目管理。
- 不扩展 Spring Boot API，不实现启动、网络、卡顿、ANR 或制品上传页面。
- 不替换或嵌入现有 Grafana Dashboard。
- 不在本次变更中实现 mapping 上传、堆栈反混淆或 Crash Issue 生命周期管理。

## Decisions

### 1. 使用独立的 Vue 3 + TypeScript + Vite 工程

前端放在仓库根目录的 `frontend/`，使用 Vue 3、TypeScript、Vue Router 和 Vite；开发与构建生命周期独立于 Spring Boot。项目方案已经将 Vue 作为产品化页面方向，且当前后端是纯服务端工程，独立目录可以避免把 Node 构建链耦合进 Gradle 任务。

备选方案：

- 将页面作为 Spring Boot 静态资源：部署简单，但会把前端构建和后端打包强耦合，且不适合当前先独立迭代页面的目标。
- 使用 React：同样可行，但不符合项目现有方案中已确定的 Vue 产品化方向。

### 2. 路由以 Crash 分析闭环组织

页面路由采用以下结构，筛选条件统一放在 URL 查询参数中：

```text
/projects/:projectId/crashes
    ├─ /issues/:fingerprint
    └─ /events/:eventId
```

总览页负责统计卡片、趋势和问题排行；问题页负责某个指纹的事件列表；事件页负责事件元数据、异常链和堆栈帧。下钻时保留 `from`、`to`、版本、渠道、环境、系统、设备等筛选参数，返回总览或问题页时可以恢复上下文。指纹和事件 ID 进入 URL 前必须编码。

### 3. 以类型化 API 客户端隔离后端协议

在前端建立与后端响应记录对应的 TypeScript 类型，包括 `CrashStats`、趋势点、问题摘要、事件摘要和事件详情。API 客户端统一负责：

- 拼接 `/api/v1/projects/{projectId}/crashes` 路径并编码路径参数。
- 把 `from`、`to`、维度筛选、`limit`、`cursor` 和 `timeoutMs` 转换为查询参数。
- 每个查询请求发送当前项目的 `X-Project-Id`；禁止发送 `X-Project-Key`。
- 将 HTTP 错误转换为页面可显示的错误对象，不记录完整响应体或堆栈消息到控制台。

总览页首次加载或筛选提交时并行请求 overview、trend 和 issues；任一请求失败时显示统一错误状态，避免将部分旧数据与新的筛选条件混合。连续快速筛选时使用请求取消或请求序列号，旧响应不得覆盖新筛选结果。

### 4. 使用路由状态和局部 composable，不引入全局业务状态库

当前只有 Crash 页面和三个相关路由，项目、筛选、列表分页等状态可以由路由查询参数和页面级 composable 管理。暂不引入 Pinia 等全局状态库，避免为单一闭环增加持久化、失效和跨模块同步成本；当未来出现登录用户、多个业务模块和共享项目上下文时再评估全局状态。

### 5. 使用原生页面布局配合单一趋势图组件

页面布局使用语义化 HTML 和项目内 CSS，包含侧边或顶部页面导航、筛选栏、统计卡片、趋势区域、问题表格和详情区域；趋势图使用 ECharts 封装为单独组件。这样可以快速完成时间序列可视化，同时不绑定完整 UI 组件库，避免组件库主题覆盖堆栈详情和表格的产品样式。

趋势数据为空时不创建伪造的零点；统计卡片将 `null` 映射为“分母不足/不可计算”，`no_data` 映射为“无数据”，但计数型零值仍显示为 0。

### 6. 通过 Vite 代理解决本地联调

开发服务器将 `/api` 代理到 `http://localhost:8080`，前端使用相对路径请求。这样浏览器只访问同源的 Vite 地址，不需要在本次变更中新增后端 CORS 配置。生产构建输出为静态资源，由独立静态服务器或反向代理托管；反向代理需要把 `/api` 转发到 Spring Boot。

### 7. 游标分页只由页面状态推进

问题列表和事件列表使用响应的 `nextCursor` 请求下一页；列表项分别以 fingerprint 和 eventId 去重。分页游标不写入筛选条件，切换任意筛选条件或项目时清空列表和游标；从详情返回时通过路由筛选参数恢复查询上下文，但不保证恢复已加载的所有分页数据。

### 8. 测试聚焦数据语义和关键交互

前端测试覆盖 API 参数与请求头、统计状态格式化、筛选刷新、问题到事件到详情的导航、游标分页、无数据/分母不足/错误状态和项目切换隔离。构建验证覆盖 TypeScript 类型检查和生产构建；浏览器联调使用仓库已有固定 Crash 数据集或真实后端响应，不在前端伪造不可计算的统计结果。

## Risks / Trade-offs

- [开发期请求头不是正式认证] → 在页面和开发文档中明确标注 `X-Project-Id` 仅用于当前联调；生产部署前必须接入正式会话/OIDC 或后端代理权限。
- [后端当前查询服务从原始事件在 JVM 内计算] → 首期页面沿用现有接口，不在前端增加聚合逻辑；通过默认时间范围、服务端 limit 和 timeout 限制返回规模。
- [趋势图新增图表依赖] → 只在独立趋势组件中使用 ECharts，其他页面不依赖图表库；后续可替换组件而不影响 API 层和页面路由。
- [浏览器渲染原始堆栈可能暴露过多内容] → 只展示服务端返回的已脱敏字段，使用文本渲染而非 HTML 注入，不记录详情响应；正式上线前仍需完成权限和隐私审查。
- [筛选请求返回顺序不确定] → 使用请求取消或序列号校验，只有当前筛选上下文的响应可以更新页面状态。
- [独立前端增加 Node 依赖维护成本] → 锁定依赖版本并把 `node_modules/`、构建产物加入忽略规则；前端不改变 Gradle 后端构建链。

## Migration Plan

1. 创建 `frontend/` 工程、API 类型和 Crash 路由，先以当前后端开发接口完成本地联调。
2. 启动 Spring Boot 服务并准备固定 Crash 数据，验证真实接口的正常、无数据、分母不足和错误场景。
3. 执行前端类型检查、单元测试和生产构建；静态检查通过后再进行浏览器手工验收。
4. 部署时将前端静态资源与 `/api` 反向代理一起发布；若前端出现问题，可停止托管前端资源，后端接口和 Grafana Dashboard 不受影响。
