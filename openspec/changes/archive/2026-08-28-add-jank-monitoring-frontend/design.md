## Context

现有前端是 Vue 3 + TypeScript + Vite 的浅色 PC 单页应用，通过共享 `AppLayout`、Vue Router、Pinia Session/Project Store 和统一 HTTP 客户端访问 Spring Boot。Crash 页面已经形成 URL 筛选、并发查询、请求取消、游标分页、ECharts 趋势和详情下钻模式，可以作为卡顿页面的交互基线。

卡顿服务端已提供 Issue/事件查询、FPS 区间汇总、设备日挂起率区间汇总和白名单多维聚合。事件详情包含相对消息开始时间的采样片段、估算调用树、堆栈字典和采集质量，因此无需改变上传协议即可生成时间片、树和火焰图。当前缺口是指标仓库没有时间桶查询，FPS/挂起率响应也没有趋势点；服务端主规格虽要求趋势，但实现尚未兑现。

## Goals / Non-Goals

**Goals:**

- 在不复制 Bugly 私有视觉和工作流的前提下，复用其“指标观察 → 问题聚合 → Issue → 个例证据”的分析路径。
- 保持精确消息耗时、采样估算耗时、未覆盖区间和数据质量在类型、文案与可视化中的证据边界。
- 使用兼容的增量服务端 API 支撑真实趋势，避免前端按多个时间窗循环请求和自行聚合。
- 沿用现有认证、项目隔离、错误处理、URL 状态和 PC 视觉模式，并控制新增依赖和实现复杂度。

**Non-Goals:**

- 不实现移动端或窄屏适配，不嵌入 Grafana。
- 不实现 Issue 负责人、状态、标签、评论、操作日志、现场数据、版本对比、查询对比列表或导出。
- 不改变 Android 上传 Schema、卡顿指纹算法、既有汇总/多维 API 或 ClickHouse 表结构。
- 不把采样估算解释为精确方法耗时、CPU 时间或连续无空洞执行。

## Decisions

### 1. 按四级路由组织卡顿分析闭环

新增指标分析、问题列表、Issue 详情和事件详情四类路由。问题列表作为卡顿问题分析的稳定入口；指标分析是并列入口。Issue 与事件详情只承载下钻上下文，不承担跨 Issue 的全局状态。

选择该结构是因为现有 Crash 路由已经验证“总览 → Issue 事件 → 事件详情”模式，同时指标分析具有不同的状态与统计口径，不适合挤在同一总览组件中。备选方案是在一个超大页面中使用多层页签，但会让 URL 恢复、请求取消和错误区域过度耦合。

### 2. 复用现有分层并为卡顿建立独立类型边界

卡顿使用独立的 TypeScript 类型、API 模块和 composable；统一 HTTP 客户端、Session/Project Store、状态消息、基础表格和格式化工具继续复用。指标筛选与问题筛选共享公共字段，但分别维护 `metric`、`dimension`、`interval`、`scene`、`algorithmVersion`、`fingerprint` 和分页字段白名单。

独立类型可以防止 Crash 与卡顿中名称相似但语义不同的分位数或状态被错误复用。备选方案是扩展现有 Crash 类型与 composable，但会产生大量可选字段并削弱编译期约束。

### 3. 新增统一指标趋势端点而不改变现有汇总响应

在 `/api/v1/projects/{projectId}/jank-metrics/trend` 增加只读查询，使用 `metric=fps|suspension_rate` 和 `interval=hour|day`。FPS 接受小时或天；设备日挂起率只接受 UTC 天。返回对象包含项目、时间范围、指标、粒度、按 `bucketStart + algorithmVersion` 排序的点、整体状态和 `dataSource`。点内只填充对应指标字段，其他指标字段不出现或为明确的空值。

采用新增端点可以保持 `/fps`、`/suspension-rate` 和 `/dimensions` 兼容，也与统一多维入口的 `metric` 模式一致。备选方案是前端把范围切成多个子请求，会放大请求数、产生跨请求快照不一致并绕过服务端查询限额；另一备选方案是分别增加两个趋势端点，类型更直观但会重复参数和响应处理。

### 4. 服务端在存储层完成时间桶聚合

仓库接口增加趋势查询边界。ClickHouse FPS 趋势按 UTC 小时或日期及算法版本分组，继续使用从高到低的分位数口径；挂起率趋势只按 UTC 日期，在内层先以项目、匿名设备、UTC 日期和稳定查询维度合并区间，外层再计算设备日分位数。内存仓库实现相同语义，固定数据集同时验证两条路径的统计期望。

该方案让统计口径集中在服务端，并避免把原始记录暴露给浏览器。需要对最大 31 天小时趋势的点数和 SQL 执行时间继续使用现有范围、`limit` 和 `timeoutMs` 保护。

### 5. 用无新增运行时依赖的组件呈现采样证据

时间片使用可滚动的相对时间轴，按 `covered` 区分覆盖和空洞；调用树使用递归树组件；火焰图使用基于估算时长布局的 SVG 组件。三种视图共享统一的纳秒转毫秒格式、估算标识和选中节点信息，堆栈字典作为时间片详情的事实来源。

选择 SVG/现有 Vue 组件可以避免引入专用火焰图库，并便于测试节点布局、键盘焦点和空洞文案。ECharts 继续用于指标与问题趋势。备选方案是 ECharts custom series，但会把树布局、交互和无障碍语义绑定到较难测试的自定义渲染回调。

### 6. URL 是筛选和下钻上下文的可恢复来源

指标页在 URL 保存指标、粒度、维度与公共筛选；问题列表保存公共筛选和趋势粒度；Issue/事件详情保留返回路径需要的指纹与兼容筛选。页面响应路由变化时取消旧请求并使用请求令牌阻止过期响应覆盖。项目切换从指标页进入目标指标页，从 Issue/事件详情进入目标问题列表并删除项目专属标识。

不把查询结果或认证数据写入浏览器持久化存储。列展示偏好和对比列表不在本期，因此也不引入额外持久化决策。

### 7. 页面只展示正式契约中的事实

Issue 列表只展示服务端已有的事件数、受影响会话/设备、时间、场景、算法版本、精确消息耗时和估算堆栈耗时。事件详情允许从调用树生成可视化布局，但不得推导或命名“负责人”“处理状态”“关键叶子精确耗时”“CPU 自耗时”等服务端没有提供的事实。

这保证页面参考 Bugly 的分析方法而不复制尚未具备的数据能力。未来新增 Issue 工作流或统计分布时应以独立契约演进。

## Risks / Trade-offs

- [趋势查询在 31 天小时粒度下产生较多分组] → 延续时间范围与超时限制，对结果点数设置显式上限，并为 ClickHouse SQL、内存实现和 HTTP 层增加边界测试。
- [挂起率被误按小时解释] → API 明确拒绝 `suspension_rate + hour`，前端切换到挂起率时自动选择 `day` 并在页面解释设备日口径。
- [火焰图让估算值看起来过于精确] → 标题、图例、提示框和节点详情统一标注“采样估算”，空洞不分配给任何调用树节点。
- [超大调用树或堆栈导致页面卡顿] → 默认折叠深层节点、限制初始渲染范围、提供树视图兜底，并用构造的大型响应执行前端性能测试。
- [多区域并发失败造成页面整体不可用] → 指标、总览、趋势、Issue 和维度结果保持独立错误状态，重试仅刷新失败区域或当前查询组合。
- [项目切换后旧请求回写] → 路由变更主动取消并校验请求令牌，所有页面响应在提交状态前核对当前项目和查询键。
- [现有工作区包含未提交改动] → 实施阶段只编辑任务明确列出的卡顿前端、趋势服务端、OpenSpec 和知识库文件，提交前核对最终差异并保留用户已有修改。

## Migration Plan

1. 先以增量方式发布指标趋势端点、内存/ClickHouse 实现和服务端测试，不改变现有三类卡顿上传或既有查询响应。
2. 再发布前端类型、API 和路由骨架；卡顿导航仅指向已经具备错误和空状态处理的页面。
3. 依次启用问题列表、Issue/事件下钻和指标分析，使用固定数据集核对精确/估算文案、FPS 分位数顺序和挂起率单位。
4. 完成类型检查、前端测试与生产构建，并运行服务端测试；在可用环境补充真实 ClickHouse 到浏览器的外部冒烟验证。
5. 回滚前端时移除卡顿导航和静态资源即可；新增趋势端点为只读兼容接口，可随服务端版本保留。若必须回滚服务端，实现可停止暴露趋势路由，无数据库迁移需要撤销。
