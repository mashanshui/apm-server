# Crash 诊断上下文扩展提案

## Why（变更动机）

当前 JVM Crash 只上报主异常链，缺少其他线程、运行日志和资源快照，难以判断并发等待、内存压力与文件描述符耗尽等现场因素。参考 xCrash 的 Java tombstone 和采集实现，补齐已有 Crash 链路中的现场信息，并在事件详情中可读地展示。

## What Changes（变更内容）

- 在 JSON v2 的 `crash` 中增加可缺失的 `diagnostics`，覆盖崩溃线程、其他 JVM 线程及堆栈、当前进程可读的 logcat、内存、文件描述符、进程和设备上下文；缺失诊断不能使合法核心 Crash 被拒收。
- Android 先可靠保存核心异常，再在有限等待和字节预算内补充诊断；采集失败、截断、权限限制和进程中断均有明确结果，恢复及重试保留原事件身份。
- 服务端独立保存不可变上下文和各线程的当前堆栈，沿用现有后台 mapping 处理；其他线程不参与指纹，辅助还原失败不阻塞主异常发布。
- 扩展当前详情 API 和网页的线程、日志、内存、文件描述符与运行环境展示，支持明确的缺失、失败、截断和独立还原状态。
- 保持单事件 256 KiB 上限，增加 SDK 单事件 UTF-8 JSON 预算和端到端大小保护；日志、线程名与路径在持久化前脱敏。
- **BREAKING**：对本变更新接收并记录内容摘要的事件，同 eventId、构建和时间却更换核心异常或诊断的请求返回永久内容冲突，避免部分写入恢复时拼接不同现场；正常冻结记录重试不受影响。
- 实施时同步契约、样例、测试和各端知识库，验证断网补传、重复上报、采集超时、同名线程和后台成功固定等关键场景。

## Capabilities（能力变更）

### New Capabilities（新增能力）

无；扩展已有 Crash 能力。

### Modified Capabilities（修改能力）

- `jvm-crash-monitoring`：增加诊断采集、可恢复落盘、脱敏、大小保护和详情查询约束。
- `crash-background-symbolication`：增加其他线程当前堆栈的处理、独立结果及与主异常一致发布的规则。
- `crash-frontend`：增加诊断详情展示、线程选择和各类采集结果反馈。

## Impact（影响范围）

- Android：`performance-crash` 的模型、异常处理、队列、上传大小选择及测试；示例应用增加受控诊断验证入口。保持仅接入 Crash 可运行，不引入 Metrics、xCrash 或新增原生依赖。
- 后端：Crash 入参、JSON Schema、校验脱敏、事实/状态存储、受限符号还原入口、后台发布与详情响应；新增版本化 ClickHouse 迁移，复用 PostgreSQL 发布记录，并以新迁移将单份登记载荷上限由 2 MiB 调整为 4 MiB，保留既有在途总字节、幂等及查询预算。
- 前端：详情类型、运行时解析、诊断组件和页面测试；Agent HTTP/MCP 的现有详情透传和格式校验需要回归，无需新增查询工具。
- 文档：根、后端、前端、Android 知识库及 Crash API、错误码、接入示例与验证说明；规划阶段仅创建本变更材料，不提前将目标记为已实现。
- 范围边界：只扩展 JVM fatal Crash，不增加 native Crash、系统 ANR、持续日志采集、堆转储、网络连接表或新存储服务；AI 分析任务的证据冻结契约扩展另行确认，本变更保留其现有主异常材料。
