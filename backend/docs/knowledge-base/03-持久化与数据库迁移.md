# 后端持久化与数据库迁移

内存指标使用运行期观测峰值与独立009表，历史窗口默认90天；三项峰值上下文独立，查询按lastSampledAt归属并返回runCount。客户端和联合验收仍待完成，完整契约见[内存API](../../../docs/api/memory-metrics-api.md)。

## 表结构与建模边界

实际表、列、排序键与 TTL 以 `backend/src/main/resources/db/clickhouse/` 的版本化 SQL 为准；不在知识库复制易失效的完整 DDL 或历史字段树。Crash/Jank 保留事实与详情，内存运行峰值和异常报告各用独立表，不是所有信号共用一个原始 JSON 模型。

高频筛选与聚合使用强类型列，低频属性使用有界 Map/JSON；`eventId` 用于逻辑去重，`schemaVersion` 用于协议版本。字段及生命周期只在平台模型/API 中维护，本页解释适配器与迁移前提。

## 卡顿事件与存储实现

卡顿个例的正式输入是 v3 `.rheajank.zip`，服务端将其解析为内部 `eventType=jank` 事实。`messageDurationNs` 是 manifest 消息边界之差；`samples[].offsetNs` 与调用树来自 `processId` 对应主线程证据；`stackDictionary` 使用稳定 stackId 去重完整帧列表。当前证据算法标识仍为 `jank-artifact-v2`，指纹版本仍为 `jank-v1`；这两个算法版本不等于 manifest 版本。采样质量只保存服务端派生的 `expectedSampleCount`、`parsedSampleCount` 和 `missingSampleCount`，不保存客户端 `attemptedSampleCount`。processor 1.0.2 已通过客户端 UUID v4 主线程-only fixture 的本机解析及云端 HTTP/落库验收；生产制品仓库、容量和长期重启恢复仍需单独验证。

`002_jank_schema.sql` 创建卡顿事实、详情和指标对象；`003_jank_sampling_quality.sql` 向 `apm_jank_event` 新增 `parsed_sample_count` 与 `missing_sample_count`。上述脚本保留历史结构；当前 `004_application_identity_schema.sql` 在空表保护下重建应用身份与卡顿对象，不保留旧 attempted/successful/dropped 质量列，007 再追加进程身份。卡顿事实和详情使用 `ReplacingMergeTree(received_time)`，重复上传可补齐原始事实、卡顿事实或详情，不生成新的事件身份。

## 内存运行峰值表与适配器

`009_memory_runtime_peaks.sql` 新增 `apm_memory_peak_summary`，旧005的apm_memory_sample保留但不参与新统计。表按 `toYYYYMM(event_time)` 分区，排序键为 `(app_id,event_id)`，引擎为 `ReplacingMergeTree(received_time)`，PSS、VSS 和 Java 堆列均为 `Nullable(UInt64)`，进程实例 `process_id`、进程名及每项峰值的发生时间、前后台和Activity场景分别存列。ClickHouse 适配器写入 JSONEachRow，概览和趋势查询都使用 `FINAL`、运行观测截止时间左闭右开过滤和固定列白名单；峰值查询启用do_not_merge_across_partitions_select_final，合法eventId的截止时间不可变，因此重复落在同一月份；配合显式月份条件裁剪历史数据。内存适配器使用同一统计公式并通过 `APM_STORAGE_MODE=memory` 装配。

每个指标独立排除 null，平均值为样本算术平均，P50/P90/P95/P99 使用 ClickHouse `quantileExactInclusiveIf` 对应 0.50/0.90/0.95/0.99，并与内存适配器的 `(n-1)×p` 线性插值一致。查询服务负责补齐与范围相交的 UTC 空桶并返回 null，不能用趋势结果二次计算概览。真实 ClickHouse 固定数据集已完成一次写入、并发/跨接收日期/重启去重和适配器对照；生产容量、长期合并开销和故障恢复仍需单独执行。

## 内存异常报告表与适配器

`006_memory_leak_reports.sql` 新增 `apm_memory_report`，按 `sipHash64(app_id,event_id) % 32` 哈希分区、按 `(app_id,event_id)` 排序并使用 `ReplacingMergeTree(received_time)`；`report_json` 和 `gc_paths_json` 保存受限原始/规范化内容，`payload_hash` 与可空附件摘要用于重试冲突判断。`ClickHouseMemoryLeakReportRepository` 的读取使用 `FINAL`，写入前检查已有事件，`InMemoryMemoryLeakReportRepository` 用于不依赖 ClickHouse 的事件联调（管理域仍需 PostgreSQL）。两种适配器都返回 `dataSource`，报告问题页在 ClickHouse 展开规范化路径、字面筛选、去重和聚合后排序分页，不读取 report_json；趋势也由数据库聚合，两者接入统一预算。生产容量边界见[平台待确认事项](../../../docs/knowledge-base/13-待确认事项.md#内存异常报告查询容量)。

`007_event_process_identity.sql` 为 `apm_event_raw`、`apm_jank_event`、`apm_frame_scene_summary`、`apm_device_suspension_segment`、`apm_memory_sample` 和 `apm_memory_report` 增加 `process_id String DEFAULT ''`。新增有效事件在接收层必须是 UUID v4；迁移前记录保留空字符串并在读取 DTO/领域对象时转为缺失值。迁移不修改排序键、TTL、幂等键、聚合维度或 `ReplacingMergeTree` 版本列。

附件不会写入 ClickHouse，`MemoryLeakArtifactStore` 使用服务端生成的 `<appId>-<eventId>.hprof` 文件名和配置根目录，先写临时文件、计算 SHA-256，再优先原子移动；文件系统不支持时回退为普通移动。定时清理跳过存储不可用时的孤立判定，临时文件宽限 24 小时，已引用附件默认保留 7 天；不提供下载路由。

场景帧汇总和前台挂起汇总的载荷、Schema、校验和专用表已冻结。`JankMetricsQueryService` 已提供 FPS 与设备日挂起率汇总、多维和统一时间桶趋势：内存实现用于固定数据集，ClickHouse 实现使用 `FINAL` 和受限聚合 SQL；FPS 按算法版本隔离、支持 UTC 小时/天并按高到低计算分位数，挂起率先按 `app_id`/匿名设备/UTC 日期/稳定维度合并再按 UTC 天计算。004 结构的固定数据集已于 2026-09-01 验收，并于 2026-09-24 使用当前脚本复验；生产容量、并发 p95/p99 和故障恢复仍待验证。

`.rheajank.zip` 是卡顿个例的正式输入：服务端验证 App Key、请求体、ZIP、v3 manifest、UUID v4 `processId`、哈希和 Sampling 后，通过 `parseWithMappingResolver` 解析一次，将必要事实和证据写入 `apm_event_raw`、`apm_jank_event` 与 `apm_jank_detail`。原始 ZIP 和完整 processor 报告不保存。服务端在 mapping、指纹、归一化和写入前校验 manifest `packageName`；processor 1.0.2 已用客户端设备 ZIP 完成真实 UUID 首次落库、重复上传和详情验证，生产 mapping 发布、容量和重启恢复仍需单独验收。

## JVM Crash 事件与存储实现

### 后台还原的新结构

`008_background_crash_symbolication.sql` 独立建立 `apm_crash_fact` 和 `apm_crash_state`，不依赖旧 Crash 表，也不搬迁或删除旧数据。事实表包含当前数据集的 Crash 与 `app_start`；状态表包含单份堆栈、指纹、归组和实际处理来源。两表均按事件月分区，以 `(app_id,build_id,event_time,event_id)` 排序，TTL 为发生时间后 30 天。事实没有后台修改版本；状态使用独立 `UInt64 state_version`，0 为接收时的 pending，后续版本由 PostgreSQL 序列分配，不能用接收时间代替。

`010_crash_diagnostics.sql` 为事实追加压缩诊断上下文和采集摘要，为状态追加压缩辅助线程栈及同一摘要；历史行默认空字符串，不重建现场，原有 TTL 不变。后端启动检查包含这些列，已有库需在启动新版本前按顺序增量执行迁移。

`ClickHouseCrashStateStore` 的接收方法先确认初始状态，再确认事实；原 eventId 重试补齐缺失一侧，已存在更高版本时不重新保存原始载荷。详情和候选必须关联已存在的事实，孤立状态不可见；候选先确定最新逻辑版本，再筛选 pending 或符合 mapping/退避条件的 failed，最后才读取有界堆栈。单批最多 100，时间范围不超过 30 天，查询沿用扫描行数、读取字节、执行时间、内存和响应上限。缺表直接失败，无旧表回退。

当前状态只接受 `pending/failed/symbolicated`：前两者为 `raw_chain + temporary`，成功为 `retrace_text + resolved`，成功记录必须携带实际 `symbol_id/revision/sha256` 及 `processed_at`。堆栈、归组和来源在同一状态版本中发布；同版本重放必须使用相同内容。摘要投影不读取 `stack_payload`。ReplacingMergeTree 的旧物理版本及既有备份不保证立即擦除，业务上的单份当前材料不代表物理安全删除。

V15 新增按应用/构建合并的 `crash_symbolication_job`、首次成功 `crash_symbolication_publication` 和 `crash_symbolication_state_version` 序列；V16 将单份未确认载荷上限由 2 MiB 调整为 4 MiB。任务分别记录唤醒代次、执行租约和本轮计数；成功发布记录以 `(app_id,event_id)` 唯一固定结果，确认后只保留轻量来源及摘要。未确认结果不得提前丢弃，轻量记录在事件保留期内继续承担幂等保护；定时任务清理与保留边界见[符号表专题](symbol-mapping.md#后台处理组件与恢复边界)。另有持久化轮转检查点 `crash_symbolication_reconcile`，每页唤醒与检查点共同提交。

V15 为分析任务追加可空 `contract_version`，只有新建任务显式写 3；旧任务仍为空，证据和报告原字节不改写。当前后台契约为证据版本 3、报告版本 4，不通过数据库迁移自动升级。符号表追加 `deleted_at`，活动构建使用局部唯一索引；删除审计用 `action=DELETE` 并保存删除时的版本和摘要，主记录保留，重传使用新 symbolId、revision=1。后台构建字段支持 v2 接收的 256 字符上限，符号表上传约束仍由符号表 API 独立校验。

后台还原的原有接收、查询和调度链路已有隔离 PostgreSQL/ClickHouse 验证；现有开发/云端环境是否升级仍以平台状态页为准。已有数据库按当前结构增量执行缺失版本至 010，不在有数据环境重跑带空表保护的 004。

### 当前运行链路

Crash 事件使用 eventType=crash、crash.kind=jvm、crash.fatal=true，并在 throwableChain 中保存异常类型、脱敏消息和结构化堆栈帧。服务端将不可变身份和设备维度写入新事实表，将单份异常链和临时指纹写入初始状态；后台成功后单独发布固定状态。当前 Crash 不读写 `apm_event_raw/apm_crash_detail` 或旧小时聚合。旧对象保留供历史数据/其他信号使用。

空库初始化按 `001_crash_schema.sql` 至 `010_crash_diagnostics.sql` 顺序执行；原始表和 Crash 明细表按事件月分区、SQL 中 TTL 为 30 天，内存运行峰值表和内存异常报告表 TTL 为 90 天；小时聚合和 Crash 问题聚合按月分区、TTL 为 365 天。这些期限由 DDL 实际执行，并非仅供展示的示例；生产值仍需结合容量确认。不能在已有业务数据上直接重跑全套初始化：004 先检查十张业务表为空，再删除并重建表和物化视图；它不是通过 `IF NOT EXISTS` 实现的无损增量迁移。

当前默认实现是 ClickHouse 持久化。无业务语义的 `ClickHouseHttpClient` 负责 HTTP、认证、超时和 JSONEachRow 基础能力；Crash 的事实/状态确认由 `ClickHouseCrashStateStore` 负责，摘要查询映射由 `ClickHouseCrashRepository` 负责，卡顿事实/详情、Issue 查询和指标分别由 `ClickHouseJankEventRepository`、`ClickHouseJankAggregationRepository`、`ClickHouseJankMetricsRepository` 负责，内存运行峰值由 `ClickHouseMemoryMetricsRepository` 负责，内存异常报告由 `ClickHouseMemoryLeakReportRepository` 负责。各适配器直接实现所属领域端口，不共享联合事件仓储。内存适配器用于固定数据集或不依赖 ClickHouse 的事件联调，需同时设置 `APM_STORAGE_MODE=memory` 与 `APM_STORAGE_IN_MEMORY_AVAILABLE=true`；管理域仍需 PostgreSQL；真实大数据量的聚合查询、容量和故障恢复仍不能由内存测试推断。

## Android 符号表表与文件卷

`V4__application_symbols.sql` 在 PostgreSQL 创建 `app_symbol_file` 当前版本表和 `app_symbol_file_audit` 替换审计表。V15 后活动记录以 `(app_id, build_id) WHERE deleted_at IS NULL` 局部唯一隔离，`revision`、SHA-256、文件大小、上传用户和更新时间均为元数据；审计表保存旧/新版本摘要和操作者，不保存 mapping 内容。JPA 写入通过 `symbolId + revision` 条件更新，避免并发管理员覆盖。

mapping 内容位于 `apm.symbol.directory` 受控目录，数据库只引用服务端生成的 UUID 文件键。上传先同卷暂存和校验，再优先原子发布；文件系统不支持原子移动时回退为不覆盖目标的普通移动。替换文件在读取租约释放前保留。启动清理只删除数据库未引用且没有租约的 `.mapping` 文件，数据库不可用时跳过清理，避免误删当前版本。Crash 首次成功还原文本持久化到当前状态，后续管理操作不重算，Jank 解析后的证据仍按既有事件表保存。

PostgreSQL `app_ingest_credential` 与 `apm_app` 一对一并级联删除，字段为 `app_id`、32 字节 Key 摘要、AES-GCM 密文、12 字节 nonce 和创建时间。不可变 `packageName` 只保存在 `apm_app`，全平台唯一；每个应用必须恰有一个凭据。该表不保存明文 Key，ClickHouse 事件表也不保存 Key。

## PostgreSQL 与 Flyway

管理域保存用户、应用、成员、凭据、Session、符号表、查询 Token、分析任务及后台还原调度/发布记录。Flyway 脚本位于 `backend/src/main/resources/db/migration/`，当前 V1～V16；JPA 只校验 schema，不代替迁移。H2 测试不证明 PostgreSQL 迁移成立。

| 版本 | 作用与当前边界 |
|---|---|
| V1～V3 | 最小管理 schema、上报凭据与应用身份 |
| V4～V5 | 符号表当前版本/审计，查询 Token 的摘要、期限、撤销及索引 |
| V6～V11 | 分析登记的历史结构、任务证据、应用 Worker、Run/租约、停止审计与内容保留 |
| V12～V13 | 本地工具与宿主停止事实分离，未停止 Worker 部分索引 |
| V14 | 删除分析源码登记表、任务 build/mapping/model 列和 Worker 仓库/类型列；保留旧证据、结果原字节及停止审计，追加历史 snapshot_id 列 |
| V15 | 新建后台还原任务、首次成功发布与状态版本序列，追加当前分析契约标识、符号表软删除及删除审计；不自动升级或清空旧数据 |
| V16 | 将单份后台发布载荷的数据库上限调整为 4 MiB，既有在途总预算不变 |

当前宿主直接流程的新 Run 不写 snapshot_id，结果版本 4 用 evidenceId/runId 绑定；旧列和报告保留原字节但不接入当前接口。V14 升级要求先结束旧活动任务并实际核验全部未知停止，迁移锁表后检测未满足条件会失败；不得修改迁移或伪造停止绕过检查。迁移后旧登记版本不能直接回退，详见[发布回退](../../../docs/knowledge-base/07-部署与运维.md#发布验收与回退)。

## 实现与目标的区别

当前各领域独立维护事实与详情结构，不从原始方案草案推导现有字段。当前 Crash 和 Jank 拥有独立写入/查询端口，ClickHouse 表名、SQL、映射与事实/详情修复分别归属各领域；通用 HTTP 客户端不包含业务表知识。实际 schema 以版本化 SQL 为准，初始化与空表保护操作见根目录部署文档。
