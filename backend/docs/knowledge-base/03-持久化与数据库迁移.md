# 后端持久化与数据库迁移

本页维护后端表结构和存储适配器细节。数据库选型、职责及平台保留策略见[事件模型与数据存储](../../../docs/knowledge-base/03-事件模型与数据存储.md)，共享环境初始化见[ClickHouse 本地初始化](../../../docs/clickhouse-local.md)。

## ClickHouse 原始事件表草案

```text
apm_event_raw
├─ app_id                 # 系统生成的 UUID 应用隔离标识
├─ package_name          # Android application ID
├─ event_id
├─ event_type
├─ event_time
├─ received_time
├─ schema_version
├─ app_version
├─ version_code
├─ build_id
├─ channel
├─ environment
├─ session_id
├─ anonymous_device_id
├─ os_version
├─ device_model
├─ network_type
├─ duration_ms
├─ status
├─ measurements Map(String, Float64)
├─ attributes   Map(String, String)
├─ crash_kind / crash_fatal
├─ crash_exception_type / crash_fingerprint
├─ fingerprint_version
└─ symbolication_status
```

### 建模规则

- 高频筛选或聚合字段使用明确的强类型列。
- 不稳定、低频属性放入 `Map` 或 JSON。
- 不将整个事件塞入单一 JSON 字符串。
- 第一版使用统一原始表；热点事件类型稳定后再建立专用事实表或物化视图。
- `eventId` 用于识别重复事件，`schemaVersion` 用于协议演进。

## 卡顿事件与存储实现

卡顿个例的正式输入是 v3 `.rheajank.zip`，服务端将其解析为内部 `eventType=jank` 事实。`messageDurationNs` 是 manifest 消息边界之差；`samples[].offsetNs` 与调用树来自 `processId` 对应主线程证据；`stackDictionary` 使用稳定 stackId 去重完整帧列表。当前证据算法标识仍为 `jank-artifact-v2`，指纹版本仍为 `jank-v1`；这两个算法版本不等于 manifest 版本。采样质量只保存服务端派生的 `expectedSampleCount`、`parsedSampleCount` 和 `missingSampleCount`，不保存客户端 `attemptedSampleCount`。processor 1.0.1 已用真实 v3 fixture 验证 `sourceManifest` 版本、包名、主线程 segments、调用树和报告可解析性；本地真实服务已继续验证 HTTP 首次/重复、应用级 mapping、错误 Key/包名、v2 拒绝和重启。

`002_jank_schema.sql` 创建卡顿事实、详情和指标对象；`003_jank_sampling_quality.sql` 向 `apm_jank_event` 新增 `parsed_sample_count` 与 `missing_sample_count`。旧 attempted/successful/dropped 物理列仅为已部署环境回滚保留，新代码不读写。卡顿事实和详情使用 `ReplacingMergeTree(received_time)`，重复上传可补齐原始事实、卡顿事实或详情，不生成新的事件身份。

## 内存采样表与适配器

`005_memory_metrics.sql` 新增 `apm_memory_sample`。表按 `toYYYYMM(event_time)` 分区，排序键为 `(app_id,event_id)`，引擎为 `ReplacingMergeTree(received_time)`，PSS、VSS 和 Java 堆列均为 `Nullable(UInt64)`，进程名、前后台和 Activity 名称（`scene`）单独存列。ClickHouse 适配器写入 JSONEachRow，概览和趋势查询都使用 `FINAL`、采样时间左闭右开过滤和固定列白名单；内存适配器使用同一统计公式并通过 `APM_STORAGE_MODE=memory` 装配。

每个指标独立排除 null，平均值为样本算术平均，P50/P90/P95/P99 使用 ClickHouse `quantileExactInclusiveIf` 对应 0.50/0.90/0.95/0.99，并与内存适配器的 `(n-1)×p` 线性插值一致。查询服务负责补齐与范围相交的 UTC 空桶并返回 null，不能用趋势结果二次计算概览。真实 ClickHouse 固定数据集已完成一次写入、并发/跨接收日期/重启去重和适配器对照；生产容量、长期合并开销和故障恢复仍需单独执行。

场景帧汇总和前台挂起汇总的载荷、Schema、校验和专用表已冻结。`JankMetricsQueryService` 已提供 FPS 与设备日挂起率汇总、多维和统一时间桶趋势：内存实现用于固定数据集，ClickHouse 实现使用 `FINAL` 和受限聚合 SQL；FPS 按算法版本隔离、支持 UTC 小时/天并按高到低计算分位数，挂起率先按 `app_id`/匿名设备/UTC 日期/稳定维度合并再按 UTC 天计算。固定数据集的 ClickHouse 结果必须在 004 结构上重新验收，生产容量、并发 p95/p99 和故障恢复仍待验证。

`.rheajank.zip` 是卡顿个例的正式输入：服务端验证 App Key、请求体、ZIP、v3 manifest、哈希和 Sampling 后，通过 `parseWithMappingResolver` 解析一次，将必要事实和证据写入 `apm_event_raw`、`apm_jank_event` 与 `apm_jank_detail`。原始 ZIP 和完整 processor 报告不保存。服务端在 mapping、指纹、归一化和写入前校验 manifest `packageName`；真实 v3 processor 解析门禁以及本地 HTTP 首次接受、重复、mapping 和重启验证均已通过，生产容量与 Android 端仍需单独验收。

## JVM Crash 事件与存储实现

Crash 事件使用 eventType=crash、crash.kind=jvm、crash.fatal=true，并在 throwableChain 中保存异常类型、脱敏消息和结构化堆栈帧。服务端抽取 crash_exception_type、crash_fingerprint、fingerprint_version 和 symbolication_status 等强类型查询列；较大的异常链写入 apm_crash_detail。

ClickHouse 初始化脚本按 `001_crash_schema.sql` 至 `005_memory_metrics.sql` 顺序执行；原始表和 Crash 明细表按事件月分区、TTL 示例为 30 天，内存采样表 TTL 示例为 90 天；小时聚合和 Crash 问题聚合按月分区、TTL 示例为 365 天。重复初始化使用 `IF NOT EXISTS`；保留期限仍需结合容量确认。

当前默认实现是 ClickHouse 持久化。无业务语义的 `ClickHouseHttpClient` 负责 HTTP、认证、超时和 JSONEachRow 基础能力；Crash 的原始事件、明细和查询映射由 `ClickHouseCrashRepository` 负责，卡顿事实/详情、Issue 查询和指标分别由 `ClickHouseJankEventRepository`、`ClickHouseJankAggregationRepository`、`ClickHouseJankMetricsRepository` 负责，内存采样由 `ClickHouseMemoryMetricsRepository` 负责。各适配器直接实现所属领域端口，不共享联合事件仓储。内存适配器用于固定数据集或无外部依赖联调，可通过 `APM_STORAGE_MODE=memory` 显式启用；真实大数据量的聚合查询、容量和故障恢复仍不能由内存测试推断。

PostgreSQL `app_ingest_credential` 与 `apm_app` 一对一并级联删除，字段为 `app_id`、32 字节 Key 摘要、AES-GCM 密文、12 字节 nonce 和创建时间。不可变 `packageName` 只保存在 `apm_app`，全平台唯一；每个应用必须恰有一个凭据。该表不保存明文 Key，ClickHouse 事件表也不保存 Key。

## PostgreSQL 与 Flyway

管理域通过 PostgreSQL 保存用户、应用、成员、凭据与 Session。版本化脚本位于 `backend/src/main/resources/db/migration/`，已有 V1、V2、V3 保持原内容，新增结构必须追加迁移；JPA 在运行时校验 schema，不替代 Flyway。Docker 可用时由 Testcontainers 验证真实 PostgreSQL，H2 结果不代表 PostgreSQL 迁移已验证。

## 实现与目标的区别

上文原始表草案用于保留历史建模依据，不是当前全部业务表的统一模型。当前 Crash 和 Jank 拥有独立写入/查询端口，ClickHouse 表名、SQL、映射与事实/详情修复分别归属各领域；通用 HTTP 客户端不包含业务表知识。实际 schema 以版本化 SQL 为准，初始化与空表保护操作见根目录部署文档。
