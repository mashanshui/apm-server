# 后端接收解析与查询链路

本页记录服务端内部处理过程。HTTP 字段、错误码和统计口径以[API 文档](../../../docs/api/README.md)为准；端到端可靠性见[平台协议与可靠性](../../../docs/knowledge-base/04-上报协议与可靠性.md)。

## 当前事件与卡顿服务端链路

当前代码未包含 Nginx、通用限流器或 Kafka。JSON/gzip 批次由 `ingest` 处理协议、应用鉴权和整批包名校验，再通过公开 API 分派给 Crash、Jank 或 Memory；内存事件经过专属校验、脱敏和 `(appId,eventId)` 幂等写入。卡顿个例由 `jank` 的原始 `.rheajank.zip` 入口同步执行 App Key 校验、受限读取、processor 解析、服务端质量派生、脱敏、指纹和领域端口写入。各领域根据 `apm.storage.mode` 使用内存或 ClickHouse 适配器，存储不可用统一返回可重试 503。

内存异常报告由 `memory.internal.web.MemoryLeakReportController` 独立接收 multipart 的 metadata JSON、必填 report JSON 文件和可选 HPROF。`MemoryLeakReportParser` 对 metadata、SDK 四个顶层字段、GC 路径和大小边界做有界校验，保留受限 report 原始 JSON；`MemoryLeakReportIngestService` 按 `appId/eventId` 串行处理 metadata+report 摘要冲突和 HPROF 摘要，附件由 `MemoryLeakArtifactStore` 流式临时写入后原子移动。`MemoryLeakQueryService` 只从报告事实按 signature 展开问题和 UTC 趋势，不把异常报告送入 `memory_sample`。

## 接收与查询的职责分配

- `ingest` 负责 JSON/gzip 协议、批次编排与信号分派，通过 `identity`、`crash`、`jank`、`memory` 的公开 API 调用业务能力。
- `jank` 负责原始 ZIP 的受限读取、processor 解析、mapping 选择、质量派生、脱敏、指纹以及事实/详情写入；原始 ZIP 和完整报告不作为持久化对象。
- Crash 查询目前读取原始事件并在 JVM 计算；卡顿指标和内存指标通过各自领域专属查询端口实现内存或 ClickHouse 聚合。内存概览与趋势分别统计非缺失原始样本，分位数使用线性插值；公开公式只在 API 文档维护。
- `bootstrap` 负责 Spring 装配、异常翻译和 Micrometer；`platform` 提供无业务表语义的 ClickHouse HTTP 能力。

身份校验与文件访问安全顺序见[安全实现](04-认证授权与安全实现.md)，写入一致性见[持久化](03-持久化与数据库迁移.md)。
