# 后端构建配置与本地运行

本页维护后端独立构建、配置和运行。统一启停和基础设施部署见[平台部署与运维](../../../docs/knowledge-base/07-部署与运维.md)。

## 二进制堆栈解析配置

完整 btrace 产物通过原始请求体同步解析，配置如下：

| 环境变量 | 默认值 | 运维含义 |
|---|---:|---|
| `APM_STACK_PARSER_MAX_ARTIFACT_BYTES` | `67108864` | 原始 `.rheajank.zip` 请求体上限；调高前必须同时验证 processor 限制、堆和临时磁盘 |
| `APM_STACK_PARSER_MAX_CONCURRENT_PARSES` | `2` | 单实例同步解析许可数；满载返回 503 和 `Retry-After` |
| `APM_STACK_PARSER_MAPPING_ROOT` | 空 | 应用级 ProGuard/R8 mapping 根目录；空值只允许不带 mapping 解析 |
| `RHEA_PROCESSOR_REPOSITORY_URL` | 空 | 构建时可选的受控 Maven 仓库地址；运行时无效 |

mapping 目录结构固定为 `<mapping-root>/<appId>/<buildId>.txt`，应由发布流程预置并只读挂载；当前没有 mapping 上传、版本管理或清理 API。服务端解析时会使用系统临时目录，不保存原始 ZIP 和完整报告；解析后同步写入卡顿事实与详情。processor 1.0.1 和真实 v3 fixture 的解析门禁，以及本地真实 HTTP 的 mapping、首次接受、重复、错误 Key/包名、v2 拒绝和重启验证均已通过；生产仍需从受控制品仓库获取该版本，并单独验证解析耗时、503 比例、JVM 堆、临时磁盘、数据库写入和并发容量。接口契约见[卡顿压缩包解析与落库 API](../../../docs/api/stack-artifact-api.md)。

初始化 ClickHouse 时必须按顺序执行 `001_crash_schema.sql`、`002_jank_schema.sql`、`003_jank_sampling_quality.sql`、`004_application_identity_schema.sql` 和增量的 `005_memory_metrics.sql`；004 只允许在受影响业务表为空时执行，旧质量列与旧项目结构不自动迁移，005 只新增内存采样表。

## 服务健康基线

当前已配置并可使用：

```http
GET /actuator/health
GET /actuator/info
GET /actuator/metrics
```

当前没有 `/api/v1/ping` 自定义接口，也没有把 ClickHouse 注册为 Actuator 健康贡献者；ClickHouse 访问失败会在上报或查询请求中体现为存储错误。正式部署前需要补齐依赖健康状态、就绪/存活探针和告警。

Crash 质量指标已经注册到 Micrometer，包括 `apm_ingest_events_received_total`、`apm_ingest_events_rejected_total`、`apm_ingest_events_duplicate_total`、`apm_ingest_retryable_failures_total`、`apm_crash_denominator_insufficient_total`，以及上报/可见延迟 Timer。

卡顿接收还注册了 `apm_jank_events_received_total`、`apm_jank_events_accepted_total`、`apm_jank_events_rejected_total`、`apm_jank_events_duplicate_total`、`apm_jank_events_schema_rejected_total`、`apm_jank_events_algorithm_rejected_total`、按版本标记的 `apm_jank_schema_version_total`/`apm_jank_algorithm_version_total`、`apm_jank_visible_delay` 和 `apm_jank_fact_detail_inconsistency_total`。其中事实/详情不一致计数表示卡顿事实写入成功但详情写入失败的可观测故障，不代表已经完成自动补偿；重复和可见延迟的生产告警阈值仍待确认。

## 工程与命令

以下命令从仓库根目录执行；IDE 应关联 `backend/settings.gradle.kts` 并使用 JDK 21，后端保持 Java 21、Spring Boot 4.1 与单模块 Gradle 构建。

```powershell
$env:GRADLE_USER_HOME = Join-Path (Get-Location) '.gradle-local'
.\backend\gradlew.bat -p backend clean build --no-daemon
.\backend\gradlew.bat -p backend test --no-daemon
.\backend\gradlew.bat -p backend bootJar --no-daemon
.\backend\gradlew.bat -p backend bootRun --no-daemon
```

进入 `backend/` 后可直接执行 `./gradlew.bat test` 等命令。产物位于 `backend/build/libs/`，Gradle 工程缓存位于 `backend/.gradle/`；根目录既有缓存和历史产物不会自动搬迁或删除。

构建需要可用的 `io.github.mashanshui:rhea-trace-processor:1.0.1`，仓库支持 Maven Local 和 `RHEA_PROCESSOR_REPOSITORY_URL`。必要时通过 `-Dmaven.repo.local=<本机仓库绝对路径>` 明确 Maven Local，不能将本机已有缓存视为正式制品仓库验收。

## 环境配置与工作目录

统一脚本读取根目录被忽略的 `.env.local`，显式进程环境变量优先。直接 `bootRun` 不会自动导入该文件，必须先在进程环境提供 PostgreSQL、稳定的 App Key 加密主密钥及所选存储模式需要的配置；推荐本地全栈使用统一脚本。

`scripts/start-dev.ps1` 会在当前 PowerShell 进程内优先使用 `APM_JAVA_HOME`，否则自动选择 `C:\Program Files\Java` 下可用的 JDK 21，并将该 `JAVA_HOME` 传递给 Gradle 和后端子进程；不会修改系统级 `JAVA_HOME`。未安装 JDK 21 时，脚本会在启动前明确报错。

后端工作目录为 `backend/`。mapping 等外部资源建议使用绝对路径；手动使用相对路径时按后端工作目录解析。统一脚本继续使用根目录 `.gradle-local/`，日志和进程状态继续放在根目录 `build/dev-services/`，后端 `clean` 不会删除统一启停记录。

## 常见排查

Wrapper 下载或缓存锁失败时先核对 `GRADLE_USER_HOME`；processor 无法解析时核对制品库和 Maven Local；应用装配失败时检查后端日志与 PostgreSQL/Flyway 配置。健康接口返回 UP 不代表 ClickHouse 查询、ZIP 写入或生产容量已验证。

## 存储开关与账号

ClickHouse 应用账号需要 `SELECT` 和 `INSERT` 权限；Grafana 应使用独立只读账号。当前 `apm.clickhouse.read-only-user` 只是配置约定，代码实际使用 `apm.clickhouse.username/password` 发起读写请求，部署时必须按最小权限配置并通过环境变量注入密码。

存储实现的条件开关实际由 `apm.storage.mode=memory|clickhouse` 控制；当前 `apm.clickhouse.enabled` 没有参与仓库 Bean 的条件选择，不能仅依赖它关闭 ClickHouse 访问，发布前应统一配置并补充启动校验。

## 管理域本地配置

首次管理员可用 `-BootstrapAdminEmail`、`-BootstrapAdminDisplayName` 配合 `APM_BOOTSTRAP_ADMIN_PASSWORD`，或使用 `-PromptForBootstrapAdmin` 安全输入邮箱和密码；`APM_DATABASE_URL`、`APM_DATABASE_USERNAME`、`APM_DATABASE_PASSWORD` 可覆盖数据库连接。脚本在本地默认显式启用 Flyway，并将 Session Cookie 设为非 Secure、SameSite=Lax；生产环境必须覆盖为 HTTPS 安全配置。
